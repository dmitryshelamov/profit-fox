# Design

## Context

В `release/0.1.0` для стенда есть только пустые проекты `ProfitFox.Engine.Strategy`, `ProfitFox.Engine.Simulation`,
`ProfitFox.Bench`, `ProfitFox.Bench.Cli` и тестовые проекты на NUnit (`net10.0`). Удалённые PR #3 и #5 лежат на GitHub
как `refs/pull/3/head` и `refs/pull/5/head`: граф, исполнитель и узлы H0001 оттуда можно брать как черновик, но их
проверка шла на сгенерированных свечах.

Эталон — Python-стенд `../profit-fox-bench` (архив): `outcome.py` (исход сделки), `compare.py` (случайные входы, блоки),
`verdict.py` (вердикт), `ledger.py` (журнал), `hypotheses/H0001-funding-short-4h/event.py` (событие). Сервис данных
`profit-fox-market-data` отдаёт историю потоком gRPC `History` (`candle_feed.proto`, `funding_payment_feed.proto`) на
`192.168.8.213:5237` без авторизации и каталог по REST `api/instruments` на `:5236`. Мотивация — в proposal.md.

## Goals / Non-Goals

**Goals:**

- Один исполнитель графа, пригодный и стенду, и позже боту.
- H0001 на реальной истории совпадает с Python-стендом по событиям, исходам сделок и вердикту.
- Повторный прогон на той же истории даёт тот же результат и тот же хэш данных.

**Non-Goals:**

- Интерфейс, предпросмотр, конструктор, бот, узлы заявок и позиции, составные узлы внутри графа.
- Узлы по всему рынку (ранг, доля пар), открытый интерес, лонг/шорт — для H0004–H0007, отдельными изменениями.
- Корзины по расписанию, проверка на новых данных по дате, перенос результатов Python-журнала.
- Проверка заглядывания вырезанием данных на каждом прогоне (её заменяют тесты узлов, см. ниже).

## Decisions

### 1. Свечи сигнала берутся у сервиса готовыми, минуты — только в окнах сделок

Сигнал считается по свечам интервала гипотезы, которые сервис собирает сам (свеча приходит, только когда покрыты все её
минуты). Минутные свечи читаются только в окнах «блок события + срок», как `spans_for` в Python. Для 4h за три года по
~500 парам это ~3 млн свечей сигнала против ~800 млн минут.

Свечи с объёмом `0` исполнителю не подаются. Python H0001 отбрасывает бары с `minutes_traded = 0`; на листингованных
перпетуалах 4h-свеча без сделок почти не встречается, а сверка покажет расхождение, если оно есть.

*Отвергнуто:* собирать свечи сигнала локально из минут всего рынка — первый прогон читал бы сотни миллионов минут;
снимок Parquet, как в Python, — второе хранилище истории рядом с сервисом.

### 2. Кэш полностью покрытых дней вне репозитория

Сервис говорит, что покрытая история не меняется. Стенд складывает прочитанное по ключу «вид данных, инструмент,
интервал, UTC-день» в каталог из настройки (по умолчанию `~/.cache/profit-fox/history`), только для полностью покрытых
дней. Цены хранятся текстом, как в потоке, поэтому хэш из кэша совпадает с хэшем из сервиса. Чтение идёт по одному
инструменту за вызов, последовательно: память ограничена одной парой, а сервис не держит много вызовов сразу.

*Отвергнуто:* читать всё из сервиса на каждом прогоне — повтор и сверка гоняли бы soyo-02 заново.

### 3. Числа: десятичные в графе, double в исходе сделки

Значения в графе и ставки фандинга — `decimal`: порог `0.0005` и ставка `"0.0005"` из потока сравниваются точно.
Исход сделки и статистика считаются в `double`, как в numpy: так сверка с Python укладывается в допуск `1e-9` по долям
суммы сделки.

### 4. Трёхзначная логика вместо «сравнение с пустым — ложь»

В v2 сравнение с отсутствующим значением давало ложь. Тогда «впервые» срабатывало бы на первой известной ставке
фандинга, а Python H0001 там события не даёт (прошлая ставка `null`). Поэтому сравнение и арифметика с отсутствующим
дают отсутствующее, «и» с ложью — ложь, а «впервые» требует, чтобы на прошлой свече вход был известен и ложен
(spec `strategy-execution`). Узлы заявок позже будут считать отсутствующее «когда» ложью, как в v2.

### 5. Гипотеза: граф сигнала и план рядом, а не узел плана в графе

`hypothesis.json` хранит `signal` (граф с одним выходом-событием) и `plan` (сторона, срок, стоп, цель) отдельными
полями. Узлом «План сделки» на холсте план станет вместе с конструктором; файл гипотезы для этого менять не придётся,
конструктор будет собирать те же два поля. Пример H0001:

```json
{
  "id": "H0001", "name": "funding-short-4h", "created": "2026-11-18",
  "statement": "…", "timeframe": "4h", "block": "week", "randomsPerEvent": 20,
  "measure": "net", "minEffect": 0.003,
  "signal": {
    "formatVersion": 1,
    "parameters": [{ "name": "threshold", "type": "number", "value": 0.0005 }],
    "outputs": [{ "name": "entry", "type": "event" }],
    "nodes": [
      { "id": "p", "kind": "parameters" },
      { "id": "rate", "kind": "funding-rate" },
      { "id": "high", "kind": "compare", "settings": { "operation": "ge" } },
      { "id": "first", "kind": "first-time" },
      { "id": "out", "kind": "outputs" }
    ],
    "wires": [
      { "from": "rate.value", "to": "high.a" }, { "from": "p.threshold", "to": "high.b" },
      { "from": "high.result", "to": "first.value" }, { "from": "first.event", "to": "out.entry" }
    ]
  },
  "plan": { "side": "short", "horizon": "4h" }
}
```

*Отвергнуто:* узел плана внутри графа уже сейчас — пришлось бы вводить узлы действий и их проверку без конструктора.

### 6. Случайные входы — свой детерминированный генератор

Зерно — SHA-256 от хэша гипотезы и символа пары, генератор — простой и переносимый (SplitMix64). Совпасть с numpy по
розыгрышу он не обязан: сверка сравнивает исходы на тех же моментах входа, а правила розыгрыша закрепляют тесты.

### 7. Сверка с Python на тех же данных

Вердикт окончателен, поэтому сверка не должна его тратить. Она идёт в два шага:

1. **Вслепую, до вердикта.** `bench parity <папка гипотезы> --out <папка>` читает разведку, считает события и исходы
   только случайных входов и пишет в CSV свечи сигнала, выплаты, минуты окон, события, случайные входы с исходами и
   средние «ложных событий» за блоки. Исходы событий не считаются, вердикта нет, в журнал идёт строка `parity`, которая
   не считается попыткой. Скрипт `bench/parity/check.py` (запуск `uv run --project ../profit-fox-bench`) собирает из CSV
   данные в формате Python-стенда и сверяет: события `event.py` H0001 с событиями графа — точно; `simulate` на каждом
   моменте случайного входа — по всем полям исхода в допуске `1e-9`; `planned_power` на средних «ложных событий» —
   мощность и нужный t.
2. **После вердикта.** `bench run` пишет ту же выгрузку с исходами событий и средними за блоки; `check.py` сверяет ещё
   исходы событий и `decide`. Расхождение здесь — ошибка расчёта: она исправляется новой строкой журнала со ссылкой на
   прогон, а исправленный узел выходит новым видом (spec `strategy-execution`).

Сверка идёт на разведке. Если разведка не покрыта историей, сверка останавливается, отложенный период для неё не
берётся.

### 8. Журнал и отчёты в репозитории, прогон только на чистом дереве

`bench/ledger.jsonl` и `bench/reports/` коммитятся: вердикт повторяем по гипотезе, коммиту и хэшу данных. Прогон с
вердиктом отклоняется при незакоммиченных изменениях (`git status --porcelain`), иначе коммит в журнале не описывал бы
код расчёта.

### 9. Раскладка по проектам

- `ProfitFox.Engine.Strategy` — формат и проверка графа, каталог узлов, исполнитель. Без зависимостей.
- `ProfitFox.Engine.Simulation` — план сделки, минутный путь, исход с издержками. Без зависимостей.
- `ProfitFox.Bench` — клиент `History` и каталога, кэш, гипотезы, периоды, случайные входы, блоки, вердикт, журнал,
  отчёт, выгрузка для сверки. Зависит от двух проектов Engine.
- `ProfitFox.Bench.Cli` — консольное приложение с командой `bench run`, настройки в `appsettings.json`
  (`MarketData:GrpcUrl`, `MarketData:RestUrl`, `Bench:CacheDirectory`).

Engine не ссылается на Bench и Bot; проверка зон из удалённого PR #2 сюда не входит.

### 10. Заглядывание вперёд проверяется тестами узлов

Узел видит только закрытые свечи и выплаты до закрытия, поэтому заглянуть по устройству нельзя. Для каждого узла
пишется тест «две истории совпадают до свечи N — выходы до N равны»; отдельной проверки вырезанием на прогоне нет.

## Risks / Trade-offs

- [История разведки не загружена: на 16 ноября минуты большинства пар шли примерно с 2026-10-01] → первая задача —
  прочитать покрытие из потока и до кода прогона сказать владельцу, сколько пар и недель есть до `2026-05-15`.
- [Python-стенд в архиве может не запускаться] → проверить `uv run` в `../profit-fox-bench` в начале, до сверки.
- [Свеча с объёмом 0 против `minutes_traded = 0`] → расхождение покажет сверка событий; тогда правило подгоняется
  к Python до первого вердикта.
- [Нагрузка на soyo-02 при первом чтении] → чтение по одному инструменту, кэш; повтор не ходит в сервис.
- [Исходы событий H0001 сверяются только после вердикта] → всё, что можно, сверяется вслепую до него: события,
  исходы случайных входов (те же правила исхода), мощность; `decide` закрепляется тестами на синтетических блоках.

## Migration Plan

Миграций нет: новое консольное приложение, ничего не разворачивается. Откат — удалить ветку.
