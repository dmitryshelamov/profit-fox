# Design

## Context

Шаг 1 (`add-hypothesis-bench`, в архиве) дал:

- формат графа и `StrategyGraph.ReadSignal` с полным списком ошибок;
- исполнитель `SignalExecutor`;
- чтение истории `MarketHistory`: гранится концом периода, без кэша;
- каталог пар `InstrumentCatalog`;
- `HypothesisReader` и CLI `bench`.

Расчёт событий пары лежит закрытым методом `HypothesisRunner.Events`. Веб-API в репозитории нет, кроме пустого шаблона
`ProfitFox.Bot.Presentation`; фронтенда нет. Мотивация — в proposal.md, требования — в `specs/signal-preview`.

Решения владельца от 2026-11-18:

- стенд — отдельное приложение, а не часть бота;
- пока оно запускается локально на Маке;
- фронтенд на стеке profit-fox-v2;
- граф берётся из гипотезы и правится как JSON.

## Goals / Non-Goals

**Goals:**

- События предпросмотра совпадают с событиями прогона, потому что их считает один и тот же код.
- Предпросмотр одной пары отвечает за секунды на реальных данных soyo-02.
- API и страница переживают шаг 3: конструктор заменит поле JSON, а запрос и ответ останутся теми же.

**Non-Goals:**

- Предпросмотр по всем парам сразу, ранжирование пар по числу событий.
- Сохранение графов, черновики, конструктор, проверка на стенде из UI.
- Docker, развёртывание, авторизация, доступ не с localhost.
- Исходы сделок, план сделки, отложенный период и новые данные.

## Decisions

### 1. Отдельное приложение `ProfitFox.Bench.Presentation` в зоне bench

Новый веб-проект `backend/src/bench/ProfitFox.Bench.Presentation` ссылается на `ProfitFox.Bench`. Он устроен как
`ProfitFox.Bot.Presentation`:

- явный `Main`;
- контроллеры в `Controllers/`, пути в нижнем регистре;
- порт `localhost:5240` в `launchSettings.json`;
- OpenAPI в разработке.

Настройки в `appsettings.json`:

- `MarketData:GrpcUrl` и `MarketData:RestUrl` — как у CLI;
- `Bench:Folder` — путь к `bench/` в репозитории, по умолчанию относительно корня.

Бот торгует деньгами круглые сутки, а стенд надолго занимает чтение истории. В старом проекте исследования внутри
продового процесса роняли сканер, поэтому процессы держатся раздельно. Сюда же в шаге 4 придёт проверка из
конструктора, а сервисом рядом с данными на soyo-02 приложение станет отдельным изменением.

*Отвергнуто:*

- эндпоинт в `ProfitFox.Bot.Presentation` — бот стал бы зависеть от чтения истории стенда;
- команда CLI, которая пишет HTML, — шагу 3 всё равно нужен API.

### 2. Один расчёт событий для прогона и предпросмотра

Тело `HypothesisRunner.Events` переносится в публичный класс `ProfitFox.Bench.Signals.PairEvents`. Он принимает сигнал,
таймфрейм, символ, прочитанные свечи и выплаты и возвращает все события по порядку. Внутри:

- исполнителю подаются только свечи со сделками;
- с каждой свечой подаётся последняя выплата не позже её закрытия.

Фильтр «сделка умещается в период» остаётся у прогона и применяется к результату `PairEvents`. Предпросмотр его не
применяет: у него нет плана сделки. Поэтому событие у самого конца разведки предпросмотр показывает, а прогон нет. Это
сценарий «Событие у конца разведки» в спецификации.

Совпадение со стендом держится на том, что код один, а не на сверке двух реализаций. Тест закрепляет его на поддельных
данных. Проверка на реальных данных сравнивает предпросмотр с событиями сверочного прогона `f3659dd4` по трём парам.

### 3. Чтение: одна пара, вся разведка, без кэша

Запрос предпросмотра читает через `MarketHistory`, у которого конец периода — `ExplorationEnd` (`2026-05-16 00:00`
UTC):

- свечи таймфрейма за `[DataStart, ExplorationEnd)`;
- выплаты через `FundingThrough(DataStart, ExplorationEnd)` — так же, как прогон разведки.

`FundingThrough` захватывает выплату ровно в `00:00` конца, окно запроса к сервису кончается на `00:00:01`. Более
поздних данных быть не может: проверка конца периода в `MarketHistory` из шага 1 бросает исключение раньше запроса.

Хэш прочитанного не нужен, но `MarketHistory` его требует, поэтому передаётся новый `HistoryHash`, который потом
выбрасывается. Минутки не читаются. Каталог пар читается при каждом запросе списка и при проверке пары. Там 824 записи
по REST, лишний кэш ради этого не нужен.

### 4. Контракт API

- `GET /api/instruments` — каталог в порядке символа. Поля: `id`, `symbol`.
- `GET /api/hypotheses` — гипотезы в порядке id. Поля: `id`, `name`, `timeframe`, `signal` (граф как JSON-объект) или
  `error` (текст ошибки чтения файла).
- `POST /api/preview` — запрос `{ instrument, timeframe, signal }`. Ответ:
  - `candles: [{ openTime, open, high, low, close, volume }]` — время в мс UTC, цены числами для графика;
  - `coverage: [{ from, to }]`;
  - `events: [{ moment }]`;
  - `periodEnd`.
- Ошибки — `400` с `errors: [{ code, reason, field?, parameter?, node?, pin?, setting?, wire? }]`, поля как у
  `GraphError`. Неизвестная пара и таймфрейм — те же записи с `field` = `instrument` или `timeframe`.

OpenAPI-документ отдаётся на `/openapi/v1.json`. Типы фронтенда генерирует из него `openapi-typescript` и коммитятся.
Поле `signal` в схеме — свободный JSON-объект: формат графа описан в `strategy-graph`, а не в OpenAPI.

### 5. Фронтенд как в v2, одна страница

`frontend/` в корне репозитория:

- **Стек:** React 19, Vite, TypeScript, Tailwind 4, `@tanstack/react-query`, `openapi-fetch`, lightweight-charts 5
  (метки через `createSeriesMarkers`).
- **Проверки:** ESLint и Prettier, Vitest с Testing Library.
- **Связь с API:** Vite проксирует `/api` на `localhost:5240`, поэтому CORS в API нет.
- **Маршруты:** роутера нет, страница одна.

На странице:

- выбор гипотезы, поле JSON (моноширинное), таймфрейм, поиск пары по подстроке;
- кнопка «Показать», график, список событий, список ошибок;
- подпись «Разведка до 2026-05-15 включительно, история пары с …».

Время показывается в UTC, как в отчётах стенда и в спецификациях.

Логика страницы проверяется тестами без графика: что подставляет гипотеза, как показываются ошибки, какие метки
получаются из событий. Сам график lightweight-charts в jsdom не рисуется; его проверяют руками на реальных данных
(задача 4.1).

*Отвергнуто:* страница внутри API с библиотекой из CDN — в шаге 3 её всё равно пришлось бы переписать.

### 6. Запуск

Два процесса на Маке:

```bash
dotnet run --project backend/src/bench/ProfitFox.Bench.Presentation
```

```bash
npm --prefix frontend run dev
```

Порядок запуска записывается в `README.md` и в `.claude/launch.json` для превью в приложении.

## Risks / Trade-offs

- **[Чтение одной пары может оказаться небыстрым: весь прогон шёл 2,5 ч, но почти всё это минутки]** → в задаче 4.1
  время предпросмотра замеряется на трёх парах и записывается сюда. Если оно больше 10 с, владелец решает про кэш
  отдельным изменением.

  **Замер 2026-11-18** (задача 4.1), H0001 на `4h`, soyo-02, с Мака:

  | Пара | Событий | Ответ API | Свечи 4h с 2023-01-01 | Фандинг | Свечи 4h с 2025-11-01 |
  |---|---|---|---|---|---|
  | PRLUSDT | 6 | 13,5 с | 299 за 7,6 с | 368 за 4,7 с | 299 за 1,7 с |
  | ALPINEUSDT | 1 | 12,2 с | 1 074 за 7,6 с | 1 649 за 5,0 с | 1 074 за 1,8 с |
  | 4USDT | 102 | 12,5 с | 1 074 за 8,0 с | 1 318 за 4,8 с | 1 074 за 1,8 с |

  Каталог пар читается за 0,4 с, расчёт событий ничего не стоит. Почти всё время уходит на сервис данных:
  - свечи 4h с начала данных идут 7,5 с, хотя со свечами только последние полгода, а с 2025-11 — 1,8 с;
  - около 1 000 выплат фандинга идут 5 с.

  Сервис отдаёт окно покрытия с 2023-11-18, в котором нет ни одной свечи. Медленные потоки и пустое покрытие — вопрос
  к `profit-fox-market-data`, а не к стенду.
- **[История минуток и 4h у большинства пар только с 2025-11-24]** → страница пишет, с какой даты у пары есть история,
  чтобы пустая левая часть графика не читалась как «сигнал не срабатывал».
- **[Правка графа сырым JSON неудобна]** → это временно, до конструктора в шаге 3. Ошибки показываются с местом, чтобы
  править было можно.
- **[Предпросмотр смотрит на разведку без ограничений и может подтолкнуть к подгонке порога]** → разведка для этого и
  нужна. Защита от подгонки — новая гипотеза с новым id на каждую правку и порог t по числу попыток на стенде.
  Отложенный период предпросмотру недоступен.
- **[Нет авторизации]** → API слушает только localhost. Доступ по сети — вместе с развёртыванием, отдельно.

## Migration Plan

Миграций нет: новое приложение и новая папка, прод и бот не меняются. Откат — удалить проект и `frontend/`, вернуть
`HypothesisRunner.Events` на место.
