# Tasks

Тесты бэкенда запускаются из `backend/`: `dotnet test ProfitFox.slnx`; фронтенда — из `frontend/`: `npm test`,
`npm run typecheck`, `npm run lint`, `npm run format:check`, `npm run build`. Каждая задача начинается с теста, который
без неё падает, и каждая группа заканчивается зелёным прогоном всех тестов своей части.

Ожидания — числа, исходы и отпечатки — не правятся ни в одной задаче: `EngineVersionTests`, `H0001ParityTests`,
`H0001StrategyParityTests`, `SignalNodeParityTests`, `HypothesisRunTests`, `OverlapRunTests`,
`ParityThroughWorkerTests`, `TradeSimulatorTests`, `TradeExitTests`, `OutcomeParityTests`, `PairPositionTests`,
`PairEvaluationTests`, `PairOrdersTests`. У `TradeSimulatorTests`, `TradeExitTests` и `OutcomeParityTests` меняется
только то, что они зовут (задача 5.4). `EngineVersion.Number` и `Tests.Integration/Fixtures/EngineVersions.json`
меняются только задачей 5.5 и только по её правилу. Если задача требует иного — остановиться и записать это в «Открыто
после применения».

  состояние позиции и этот момент.
- **3.3, «впервые» на пересчёте.** Узел помнит условие двух последних закрытий: на пересчёте после свечи N он сравнивает
  пересчитанное условие с условием закрытия свечи N−1 (design.md, решение 7: «с тем, что было на закрытии прошлой
  свечи») и ничего не сдвигает; «предыдущее» на пересчёте отдаёт то же, что отдало на закрытии N.
- **4.2, причина закрытия цикла.** Новые причины (лимитная заявка, рыночная заявка, закрытие по условию) не добавлены в
  `ExitReason`: `TradeExitTests` (закреплён) проверяет, что его случаи покрывают все значения этого перечисления. У цикла
  своё перечисление `CycleExit`; `CycleOutcome.ToTrade()` переводит стоп, цель и срок в `ExitReason`.
- **4.2, `CycleRun` рядом с `TradeSimulator`.** Тест точного равенства — в двух местах: unit-тест на 1200 сделках
  `Fixtures/Outcomes` (`CycleRunTests`) и интеграционный `CycleRunParityTests` на событиях и случайных входах H0001 и
  H0002 эталонной истории, по путям блоков, как их строит стенд. Сверка с исходами, которые посчитал стенд, идёт только на
  путях блоков: на пути всей истории фандинг расходится в последнем бите (накопленная сумма выплат начинается с другого
  места) — это свойство `MinutePath`, а не расчёта цикла.
- **4.3, событие входа на пересчёте.** «Впервые» на пересчёте внутри свечи события снова даёт событие (решение 7: оно
  сравнивает с закрытием прошлой свечи), и `enter` выдавал бы новую заявку после каждого исполнения в этой свече. Узел
  `enter` выдаёт не больше одной заявки на свечу: событие принадлежит своей свече.
- **4.3, проверка выходов.** Срок, стоп и цель берутся с расчёта, на котором выдана заявка; заявка `market-order` или
  `limit-order`, которая открыла бы цикл при недопустимых значениях узлов выхода (узел есть, значение отсутствует или вне
  границ), не исполняется и даёт отказ `plan`, как заявка `enter`. Размер заявки `enter` проверяется на её расчёте.
- **4.4, неоднозначность.** Минута неоднозначна, если в ней по ценам могли исполниться заявки разного действия:
  увеличение и уменьшение, стоп и что-либо ещё (в том числе цель — как у сделки по плану).
- **4.4, продажа всего количества.** Количество для узла позиции переводится в `decimal` и обратно; продажа, которой не
  хватает до всего количества меньше `1e-12` его доли, закрывает позицию целиком, чтобы не оставалась пыль.
- **4.5, сценарий «Стоп после докупки».** Сценарий spec `strategy-position` (стоп `0.05` от `100`, докупка по `90`)
  противоречит порядку «стоп раньше докупки»: цена `90` ниже стопа `95`, и в той же минуте сначала исполнится стоп. Тест
  проверяет то же правило с другими числами (стоп `0.15`, докупка по `90`, новый стоп — средняя × `0.85`, ниже прежних
  `85`); текст сценария не менялся.
- **4.6, после дыры.** Цикл, открытый в дыре минутной истории, отдан со статусом `coverage` и своими исполнениями; все
  заявки сняты; граф считается заново в первую известную минуту после дыры, и новые заявки участвуют со следующей.
  Заявка `enter`, не исполненная к концу истории, получает исход «не дала сделки» с причиной `period`.
- **4.5, ставка мейкера.** `TradeCosts` получил `MakerFee` (по умолчанию `0.0002`) последним параметром: прежние вызовы и
  стенд не меняются. Мейкера платят исполнения `limit-order` (вход, докупка, продажа); рыночные, стоп, срок и цель —
  тейкера. У цикла без исполнений мейкера комиссия считается прежним выражением, побитно как у `TradeSimulator`.
- **4.x, фандинг.** Расчёт стратегии с заявками считает фандинг по известным выплатам и не исключает цикл, если покрытие
  фандинга кончилось раньше (у сделки по плану это причина `funding`).
- **5.1, размер в шаге.** `StrategyStep` получил `Size` свойством со значением по умолчанию `100` (`DefaultSize`), а не
  позиционным параметром: так шаги, которые собирают закреплённые `PairPositionTests`, `PairEvaluationTests` и
  `PairOrdersTests`, не меняются. `StrategyRun` пишет размер узла, чья заявка, а в шаге без заявки — размер первого
  `enter`; `EntryPlan.Of` даёт отказ `plan` без положительного размера. `PairSteps` получил признак `byPlan` (по
  умолчанию истина): `At` на стратегии с заявками бросает.
- **5.3, 5.4, 5.5 не сделаны — противоречие с правилами запуска.** Меня запустили с жёсткими правилами: стратегия по плану
  считается прежним путём (`StrategyRun` → `EntryPlan` → `PairPosition` → `TradeSimulator`), H0001 не уводится на новый
  расчёт вне теста равенства, `TradeSimulatorTests` не правятся, `EngineVersion.Number` остаётся `2`; при противоречии —
  остановить задачу и записать. Редакция `a1e09f6` (решение 5, «Один расчёт сразу») требует ровно этого: 5.3 переводит
  `Cycle.Open` и `PairPosition` стенда на `CycleRun`, 5.4 удаляет `TradeSimulator` и переводит его тесты на `CycleRun`,
  5.5 — правило номера версии. Эти три задачи оставлены открытыми для основной сессии. Что для них уже готово:
  `CycleRun.Simulate` и `CycleRun.Exit` дают побитно те же исходы, что `TradeSimulator.Simulate` и `TradeSimulator.Exit`, на
  1200 сделках эталона Python и на всех 2709 циклах H0001 и H0002 (задача 4.2, «Замеры»); `CycleOutcome.ToTrade()`
  собирает `TradeOutcome`. Значит, переключение `Cycle.Open` — замена двух вызовов, и по этим тестам отпечатки версии 2
  должны остаться (тогда 5.5 — «ничего не менять»). Пока 5.3 не сделана, стенд и предпросмотр стратегии по плану считают
  `TradeSimulator`; предпросмотр собирает цикл по плану из `TradeOutcome` (задача 7.1).
- **5.3 закрыто.** Правила запуска прежней сессии сняты решением 5 («Один расчёт сразу»), задача сделана отдельной
  сессией. `Cycle.Open` считает цикл через `CycleRun.Simulate`, а без результата — через `CycleRun.Exit`. У `Cycle`
  позиционный параметр теперь `Result` (`CycleOutcome`, как его посчитал `CycleRun`), а `Outcome` (`TradeOutcome`) —
  свойство, собранное из него через `ToTrade()`: `PairEvaluation`, `ExecuteRunCommandHandler`, журнал и отчёт читают
  `Outcome` как раньше и не менялись. `PairPosition` не менялся: он открывает цикл через `Cycle.Open`. Размер цикла —

- **11.1, конец посчитанной истории.** `PositionRun` получил необязательный параметр `end` — конец посчитанной истории

  исполнения, как у отказа `plan`. Заявка `enter` стратегии без срока, не исполненная к концу истории, по-прежнему
  получает `period` в `Finish`.
- **11.1, заявки после выхода по сроку посреди свечи.** Срок, истёкший в начале минуты не на закрытии свечи, закрывает
  цикл по закрытию прошлой минуты со сделками, граф считается заново в этот момент, и выданные им заявки участвуют с
  этой же минуты — как заявки расчёта на закрытии свечи (раньше — со следующей минуты). Заявки пересчёта после
  исполнения и после дыры по-прежнему участвуют со следующей минуты.
- **11.2, вход без сделок за срок.** Отказ `no_trade` заявки `enter` несёт момент заявки; он выдаётся в момент, когда
  срок истёк: перед расчётом графа на закрытии свечи, в начале минуты или в `Finish`. Дыра в истории до этого момента
  по-прежнему даёт заявке `coverage` — как у сделки по плану, где покрытие проверяется раньше сделок.
- **11.3, правило неоднозначности.** Перед каждым исполнением минуты смотрится, что может исполниться сейчас, вместе с
  тем, что в этой минуте уже сделали с циклом исполнения лимитных заявок: лимитный вход или докупка считаются
  увеличением, лимитное уменьшение — уменьшением до конца минуты. Правило прежнее: увеличение и уменьшение (цель — среди
  уменьшений) либо стоп и что-либо ещё. Рыночное исполнение в счёт уже случившегося не идёт: оно по открытию минуты и
  потому раньше остального, так что рыночный вход и стоп или цель в той же минуте цикл неоднозначным не делают — как у
  сделки по плану (`trade-plan-outcome`: неоднозначны только стоп и цель вместе). Заявка `enter`, стоящая при открытой
  позиции, действием не считается: она будет пропущена.
- **11.4, отказ `period` тоже раз за свечу.** Правило «не чаще одного раза на узел за свечу» действует на оба отказа
  заявки `market-order` и `limit-order`, которая открыла бы цикл: `plan` (задача) и `period` (появился в 11.1). Без
  этого рыночный вход стратегии со сроком давал бы отказ `period` каждую минуту последних часов разведки. В spec
  `strategy-preview` «Только разведка» добавлены фраза и сценарий «Рыночный вход со сроком у конца разведки». Свеча —
  от расчёта графа на закрытии до следующего закрытия; отказ несёт момент первого несостоявшегося исполнения в ней.
- **11.6, что осталось квадратичным.** Накопленными суммами ведутся количество и вложенное — то, что граф читает после
  каждого исполнения. Тест на 20 000 исполнений — 20 000 рыночных докупок подряд (случай из design.md: условие
  «Рыночной заявки» не зависит от позиции). Частичное уменьшение по-прежнему проходит по всем входам цикла и пишет по
  записи на каждый: цикл из тысяч входов с тысячами частичных уменьшений считается за время и память, растущие как их
  произведение. Правило «уменьшение закрывает одну долю каждого входа» можно свернуть в накопленные суммы и там, но это
  меняет порядок сложений в результате цикла, в том числе с одним входом, и в задачу не входило. После частичного
  уменьшения количество и вложенное цикла из нескольких входов могут отличаться от прежних в последнем знаке; у цикла
  без частичных уменьшений (лесенка, цикл по плану) они побитно прежние.
- **11.6, отмена.** Токен проверяется на каждой свече (`PairCycles.Of`), каждой минуте и каждом исполнении
  (`PositionRun`); отменённый запрос бросает `OperationCanceledException`. Путь стратегии по плану (`PairOrders`) не
  менялся: он и раньше получал токен при чтении минут каждой недели.
- **12.8, порядок проверок заявки `enter`.** У стратегии с заявками, как у стратегии по плану (`PairOrders`): сначала
  конец разведки (`period`), затем открытая позиция («пропущена»), затем план (`plan`). Переполнение десятичного числа
  ловится у всех трёх арифметических узлов, не только у `multiply`; в spec `strategy-execution` «Арифметические узлы»
  добавлены фраза и сценарий «Результат не помещается в число».
- **12.3, отступление от design.md, решение 11.** Решение 11 говорило: «редактор получает поднятый граф как сохранённый
  и показывает „сохранено“». Теперь ответ `GET /api/strategies/{name}` (и ответы сохранения и переименования) несёт
  поле `raised`: истина, когда в базе граф прежнего вида, а в ответе он поднят (`StrategyDocument.Raised`, ставится в
  `StrategyDbConverter.ToDomain` по `StrategyUpgrade.IsFormer`); после сохранения — ложь. Редактор открывает такую
  стратегию с состоянием «не сохранено» и включённой «Сохранить»; сохранение без правок пишет следующую версию. Мои
  выборы сверх направления задачи: «Отбросить» у поднятой стратегии без правок выключена (отбрасывать нечего);
  вопрос «Есть несохранённые правки. Уйти?» и черновик в браузере появляются только после настоящей правки — уход с
  поднятой стратегии ничего не теряет, подъём повторится при следующем чтении. Контракт изменился: `schema.d.ts`
  пересобран из запущенного API, отличие — одно поле `raised: boolean` у `StrategyResponse`; новые SHA-256 — в «Замерах».
  В spec `strategy-constructor` «Подъём не переписывает версии» добавлены фраза и сценарий «Поднятая стратегия в
  редакторе».
