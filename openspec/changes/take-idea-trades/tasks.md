# Tasks

Тесты бэкенда запускаются из `backend/`: `dotnet test ProfitFox.slnx`; фронтенда — из `frontend/`: `npm test`, `npm run
typecheck`, `npm run lint`, `npm run format:check`, `npm run build`. Каждая задача начинается с теста, который без неё
падает, и каждая группа заканчивается зелёным прогоном всех тестов своей части.

Порядок групп — порядок работы. Слои и папки — по README, «Слои». Макеты — `mockups/`. Настоящий Bybit участвует только
в группе 11 и только при владельце. Секреты и мастер-ключ не попадают ни в репозиторий, ни в журнал, ни в вывод задач.

Ожидания прежних тестов расчёта не правятся: `EngineVersionTests` с `Fixtures/EngineVersions.json`, тесты `Idea*`,
`CycleRunTests`, паритеты. Если задача требует иного — остановиться и записать это в «Открыто после применения».

Расхождения с design (решения приняты при применении, владельцем не подтверждены):

- Решение 3, порядок сверки REST: сначала исполнения с курсора (минус минута на расхождение часов), потом позиции, потом
  незавершённые заявки — а не «позиции, исполнения, заявки». Так сравнение позиции со сделкой видит уже записанные
  исполнения, и частичное закрытие не выглядит «Ошибкой». Курсор двигают исполнения REST и исполнения потока — последние
  только пока аккаунт на потоке после сверки, чтобы разрыв не перепрыгнул пропущенные исполнения.
- Решение 12, хранение: в `trades` сверх перечисленного — `entered` и `held` (сколько куплено входом и сколько держится
  сейчас), `close_reason` отдельно от `reason`, `flat_since` (с какого момента биржа показывает пустую позицию при
  непустой сделке — для `Trading:CloseWait`); в `trade_orders` — `refusal` (причина отказа Bybit). Ограничения `CHECK` на
  слова состояний и причин.
- Решения 5 и 10, сверка: снимок позиции у сделки «Ждёт входа» не сравнивается; «позиция больше сделки» считается только
  когда заявка входа исполнена целиком — рыночный вход приходит несколькими исполнениями, и снимок между ними не «Ошибка».
  Исполнение, увеличивающее позицию не входом стенда, сразу переводит сделку в «Ошибку». Поздний филл заявки стенда другой,
  уже закрытой сделки к новой сделке пары не приписывается.
- Решение 11: проверка стоп-крана идёт на каждом тике Worker'а (`Trading:Tick`, 1 с), а не на каждом сообщении цены —
  то же «не чаще раза в секунду». У аккаунта на опросе результат открытых — `unrealisedPnl` позиций последнего круга.
  `GET api/risk/state` считает убыток дня по `trades.unrealised`, которое Worker пишет раз в 3 с: экран отстаёт до 3 с.
- Решение 8: стоп по пределу округляется к шагу цены в сторону цены клика (никогда не дальше предела) — у шорта XRP из
  макета 16 это `1.4549`, а не `1.4550`; стоп идеи — к ближайшему шагу.
- Решение 7: расчётная цена ликвидации в проверке «Стоп ближе ликвидации (≈ …)» — `цена × (1 − знак × (1/плечо − 0.5 %))`,
  поддерживающая маржа первого уровня Bybit взята постоянной; нужные свободные USDT — залог плюс комиссия тейкера входа и
  выхода от стоимости позиции (у макета 16 «из 33.40» — иллюстрация). Без счёта и без суммы в запросе берутся аккаунт по
  умолчанию (или первый) и сумма по умолчанию (или предел на сделку).
- Настройки сверх design: `Bybit:SocketAddress` (адрес потока, пустой — боевой Bybit; тесты ставят недостижимый адрес);
  `Trading:MarkInterval` (3 с, как пишется `trades.unrealised`) и `Trading:MaxBackoff` (60 с, предел паузы повторов и
  переоткрытия потока) — в `appsettings.json` их нет, действуют умолчания.
