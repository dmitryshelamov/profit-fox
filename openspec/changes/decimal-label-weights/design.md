# Design

## Context

Change add-idea-score (архив `2026-11-28-add-idea-score`) ввёл веса меток `label_weights(text, long_weight smallint,
short_weight smallint)` с проверкой `−3…3` и балл `ideas.score smallint`, который хранится в идее и пересчитывается
при смене веса (решение 2 того `design.md`). На проде 68 меток и «⚡ всплеск»; у части меток веса `±1`.

Владелец 2026-11-28 хочет дробные веса со старшинством таймфрейма: «1 балл дает только старший таймфрейм», шаг — сотые,
потолок — 100.

## Goals / Non-Goals

**Goals:** дробный вес от −100 до +100 с шагом 0.01; дробный балл везде, где балл виден или отбирается; итоги по баллу,
по которым при дробных баллах можно что-то сравнить.

**Non-Goals:** подбор весов по данным; веса по стратегиям или таймфреймам идеи; изменение того, когда и как балл
пересчитывается.

## Decisions

### 1. Хранение — `numeric`, а не целые сотые

`label_weights.long_weight`, `short_weight` → `numeric(5,2) NOT NULL DEFAULT 0` с проверкой `BETWEEN -100 AND 100`;
`ideas.score` → `numeric(7,2) NOT NULL DEFAULT 0`. Сумма `numeric(5,2)` остаётся точной: `0.1 + 0.2` даёт `0.30`, без
ошибок двоичной дроби. `numeric(7,2)` вмещает ±99 999.99 — больше, чем 100 × число меток.

Альтернатива — `integer` в сотых (вес `0.25` хранится как `25`): быстрее сумма, но каждое чтение и запись делят и
умножают на 100, а выражение балла и фильтры читаются хуже. Пересчёт балла и так идёт только по идеям с изменённой меткой
(индекс GIN), поэтому выигрыш не нужен. Отказ.

Миграция — `ALTER COLUMN … TYPE numeric(…) USING …` для трёх столбцов и замена проверок `−3…3`. Смена типа `ideas.score`
переписывает таблицу и пересоздаёт индексы на ней, включая `ideas_state_score_ix`; на время миграции таблица под
блокировкой (риск 1).

### 2. Проверка веса

Команда `SetLabelWeight` отклоняет вес вне `−100…100` и вес с ненулевыми цифрами дальше сотых: `0.125` — отказ,
`0.10` — то же, что `0.1`. Ошибка при поле `longWeight` или `shortWeight`, как сейчас; текст — «вес от −100 до +100,
не больше двух знаков после точки». API принимает и отдаёт вес числом JSON (`decimal` в C#).

### 3. Балл и «балл от»

Тип балла в домене, ответах и выражении `ListColumns.ScoreOf` — `decimal`; выражение не меняется, кроме приведения
результата к `numeric(7,2)` вместо `::int`. «Балл от» (`minScore` и поле фильтра `score`) — число с не более чем двумя
знаками после точки; иначе отказ, как сейчас. Сравнение `i.score >= @MinScore` без изменений.

### 4. Итоги группами по 0.5

`GET /api/ideas/scores` отдаёт строки по группам: группа идеи — `floor(score * 2) / 2`, строка несёт нижнюю границу
группы (`from`) и верхнюю (`to = from + 0.5`), идёт по `from` по убыванию. Целый балл попадает в группу, которая с него
начинается: `+1` — в «от +1 до +1.5», `−0.5` — в «от −0.5 до 0».

Почему не точный балл: при весах 1 / 0.5 / 0.25 / 0.14 почти у каждой идеи своя сумма, и строк было бы сотни по
несколько идей. Ширина 0.5 — половина веса метки 4h; при прежних целых весах группы совпадают с точными баллами.

### 5. Фронтенд

- «Скоринг»: вес — поле числа (`step 0.01`, ширина под `−100.00`) вместо выбора; сохраняется по Enter и по уходу из
  поля, если число поменялось. Отказ сервера — как сейчас: ошибка в строке, прежний вес на месте.
- «Балл от» — поле числа вместо выбора `−3…+9`; пустое — без порога; помнится в браузере под тем же ключом.
- `scoreText` показывает число со знаком без лишних нулей: `+1.25`, `−0.5`, `0`; итоги — «от +0.5 до +1».
- Подсказка меток не меняется, кроме чисел.

### 6. Веса по таймфрейму — после выкладки, не в коде

Масштаб, выбранный для первой настройки: модуль веса растёт как корень из длины таймфрейма, 4h — 1: 5m `0.14`,
15m `0.25`, 1h `0.5`, 4h `1`, 1d `2.45`. Готового стандарта в индикаторах нет (веса там задаёт автор), а √T — тот же
масштаб, по которому издержки сделки падают с таймфреймом в прошлой проверке. Знак каждой метке остаётся прежний; метки
с весом 0 остаются 0. Ставится на проде через `PUT /api/scoring/weights` после выкладки.

## Risks / Trade-offs

1. **Блокировка `ideas` на миграции.** Смена типа переписывает таблицу; на проде вставки идей сканера ждут её конца.
   Задача 1.2 замеряет миграцию на копии размера прода; если дольше минуты — записать в «Открыто после применения».
2. **Сохранённые фильтры с баллом.** Условия «балл ≥ 2» остаются верными: целое — частный случай дробного.
3. **Номер в `localStorage`.** Прежнее целое «Балл от» читается как то же число.

## Migration Plan

Миграция `202611280002_decimal_label_weights`: три `ALTER COLUMN TYPE`, замена проверок. Отката значений не нужно:
целые веса переходят без изменений. `Down` возвращает `smallint` с округлением и проверку `−3…3` после зажима весов в
этот диапазон.
