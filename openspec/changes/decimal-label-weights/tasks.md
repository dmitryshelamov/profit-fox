# Tasks

Тесты бэкенда запускаются из `backend/`: `dotnet test ProfitFox.slnx`; фронтенда — из `frontend/`: `npm test`, `npm run
typecheck`, `npm run lint`, `npm run format:check`, `npm run build`. Каждая задача начинается с теста, который без неё
падает, и каждая группа заканчивается зелёным прогоном всех тестов своей части.

Ожидания не правятся, кроме тех, что прямо говорят о целом весе или целом балле: сценарии «Дробный вес», «Вес вне
диапазона», «Не число» и тесты выбора веса `−3…+3` на «Скоринге». Движок, узлы, `EngineVersion` не меняются. Если
задача требует иного — остановиться и записать это в раздел «Открыто после применения» в конце этого файла.

Слои и папки — по README, «Слои». Решения — `design.md`, номера в скобках.

## Замеры

Миграция `202611280002_decimal_label_weights` (задача 2.1) на dev-стенде: `docker compose up bench-db` (Postgres 17,
настройки по умолчанию, `fsync` включён) в облачном контейнере, 4 ядра. `ideas` заполнена до 500 000 строк (10 000
открытых, 5 052 исключённых, остальные закрытые; 397 МБ с индексами), 4 метки с весами.

| Шаг | Время |
| --- | --- |
| `ALTER TABLE label_weights …` (типы и проверки) | 4–5 мс |
| `ALTER TABLE ideas ALTER COLUMN score TYPE numeric(7,2)` с пересозданием 8 индексов | 4,6–4,9 с (два прогона в `BEGIN … ROLLBACK`) |

Это меньше минуты из риска 1: на проде (~246 000 строк) ожидается около 2–3 секунд блокировки `ideas`, если диск прода
не намного медленнее.

Та же миграция стартом API (`FluentMigrator`, тот же стенд, 500 000 строк): `label_weights` 0,008 с, `ideas.score`
4,50 с, вся миграция 4,88 с.

Попутно на том же стенде (задача 5.2), не часть миграции: смена веса пересчитывает балл всех идей с меткой в одной
транзакции под блокировкой весов (решение 2 add-idea-score, без изменений). Метка на 125 000 идей, из них 62 500 с
изменённым баллом — `PUT /api/scoring/weights` 7,2 с; «⚡ всплеск» на 250 000 идей — 15,6 с. Сканер на это время ждёт
блокировку весов.

## Открыто после применения

- Задачи 1.2 и 5.2 сделаны в облачном контейнере, а не на dev-стенде Мака: Postgres 17 из `docker-compose.yml`
  (`bench-db`), API и Vite из ветки. Данные синтетические (500 000 идей, 4 метки). Сервис рыночных данных
  (`192.168.8.213`) из облака недоступен, поэтому метку сигнала `price-down-15m` → «цена ↓ 15m» записали прямо в
  `signal_labels` (`PUT /api/signals/{name}/label` проверяет инструменты через этот сервис и отвечает 500); вес, балл,
  «Балл от» и итоги проверены через страницу. Повторить 5.2 на настоящем dev-стенде — за основной сессией.
- В синтетике все идеи с «цена ↓ 15m» — лонги, поэтому для снимка «⚡ всплеск» дан вес лонга `1` и шорта `−0.5`:
  итоги «от +1 до +1.5», «от 0 до +0.5», «от −0.5 до 0».
- Минус в `scoreText` остался дефисом `-`, как был (`-0.5`, `-1`): в тестах прежние ожидания `-1`, `Балл от: -3` и
  `↓ BTC 1h-1` с дефисом; `−` в `design.md` и спеке — типографский.
- Сверх списка в начале файла поменялись ожидания, которые следуют из самой задачи: перечень версий миграций в
  `MigrationTests` (+`202611280002`), типы `int` → `decimal` в кортежах тестов балла, строки итогов `Score` → `From`/`To`
  (задача 3.1), тест «Балл от» поля фильтра «1.5 — отказ» (теперь `0.125`), тесты «Балл от» −3…+9 и строки итогов
  `Балл +2` на фронтенде (теперь поле числа и «от +2 до +2.5»). Инвариантный тест `ideas.score = ScoreOf` берёт случайные
  веса в сотых вместо целых — по задаче 2.4.
- `Down` миграции, кроме описанного в «Migration Plan», пересчитывает `ideas.score` из округлённых весов (округлённая
  сумма не была бы суммой весов). В `ALTER COLUMN … USING` подзапрос запрещён, поэтому это отдельный `UPDATE`.
- Пересчёт балла при смене веса на большом числе идей занимает секунды (см. «Замеры»): это поведение add-idea-score,
  здесь не менялось. Если на проде метка будет на десятках тысяч идей — сканер будет ждать столько же.

## Ревью главной сессии

2026-11-28, главная сессия: тесты бэкенда (Unit 940, Integration 505) и фронтенда повторены на Маке — зелёные.
Исправлено по ревью:

- Вес, введённый во второе поле строки, пока сохраняется первое, уходил с прежним весом первого поля, и второе
  сохранение возвращало старый вес. Строка помнит последние отправленные веса и шлёт второй вместе с первым.
- Поля веса и «Балл от» — текст с `inputmode="decimal"` вместо `type="number"`: запятая («0,25») читается как точка,
  типографский минус — как дефис. Поле `type="number"` в Safari отдаёт пустое значение на «1,5».

Фронтенд после правок: 489 тестов в 39 файлах; typecheck, lint, format:check, build зелёные.
