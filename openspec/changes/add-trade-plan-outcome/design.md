# Design

## Context

`ProfitFox.Engine.Simulation` пуст (заготовка `Class1.cs`) и по `Directory.Build.targets` может ссылаться только на
`ProfitFox.Engine.Strategy`. Engine без часов, файлов и сети. Решения владельца — ADR 0012: исход плана считает симулятор
заявок; рыночная заявка исполняется по open первой минуты со сделками не раньше момента заявки; в 1.2 только то, что
нужно H0001.

Эталон — `src/profit_fox_bench/outcome.py` Python-стенда. Что из него берётся без изменений: вход в момент закрытия
свечи события, а если в первой минуте нет сделок — в первой следующей минуте со сделками внутри срока; проскальзывание
против стороны на каждой рыночной сделке; комиссия тейкера со стоимости каждой стороны; фандинг за выплаты
`вход < t ≤ выход` по close минуты перед выплатой (с переносом вперёд через минуты без сделок); разложение итога
(`gross`, `slippage`, `fees`, `funding`, `net`); исключения «покрытие», «нет сделок», «фандинг» в этом порядке. Что
меняется (ADR 0012): выход по сроку — по open минуты T, а не по close минуты перед T.

Сервис данных хранит минутные свечи и без сделок — с объёмом `0` (`candle-loading`); поэтому «минута со сделками» —
свеча с `volume > 0`, а не просто наличие свечи.

## Goals / Non-Goals

**Goals:**

- Минутный путь, симулятор рыночной заявки и расчёт исходов плана, которые стенд 1.3 вызывает напрямую.
- Совпадение с `outcome.py` на синтетике по всем полям итога.

**Non-Goals:**

- Лимитная и стоп-заявка, стоп и цель плана, R и признак «стоп и цель в одной минуте».
- Счёт, позиции, шаг объёма, минимальная заявка, комиссия мейкера, спот: придут с бэктестом бота.
- Выключатель фандинга в издержках: H0001 его не выключает.

## Decisions

### Типы

```text
MinuteCandle(OpenTime, Open, High, Low, Close, Volume)                 // decimal, время UTC
TimeRange(Start, End)                                                  // [Start, End)
MinutePath(InstrumentId, candles, candleCoverage, payments, fundingCoverage)
ExchangeSimulator(path, Costs(TakerFee, Slippage))
  .Execute(MarketOrder(PlacedAt, Side, Amount | Quantity)) → Fill(Time, Price, Quantity, Fee) | NoFill(coverage)
  .Funding(positionSide, quantity, from, to) → decimal | unknown
TradePlan(Side, Horizon)
TradePlanOutcomes.Compute(path, plan, costs, entryMoments) → [TradeOutcome]
TradeOutcome: Status (Ok | ExcludedCoverage | ExcludedNoTrade | ExcludedFunding), EntryTime, EntryPrice, ExitTime,
              ExitPrice, Gross, Slippage, Fees, Funding, Net
```

Рабочие имена; выплата — `FundingPayment` из `ProfitFox.Engine.Strategy.Execution`, чтобы у стенда был один тип выплаты
для сигнала и для исхода. Сторона — у плана, как в гипотезе: события и их случайные входы идут в одну сторону, поэтому
входы — только моменты.

### Числа — `decimal`

Engine уже считает граф в `decimal`, а сервис данных отдаёт цены десятичным текстом. Объём расчёта мал: у рыночных заявок
нет прохода по минутам срока, кроме проверки покрытия, а она — по отрезкам покрытия, а не по минутам. Сверка с `Float64`
Python идёт с точностью `1e-12`.

Альтернатива — `double` ради скорости: отвергнута, пока объём не стал проблемой; переход затронул бы и граф.

### Минутный путь хранит минуты по индексу

Путь при построении раскладывает свечи по индексу минуты от начала покрытия, считает префиксные суммы покрытых минут и
перенесённый вперёд close минут со сделками. Тогда первая минута со сделками не раньше T, проверка «вся ли минута
отрезка покрыта» и цена перед выплатой ищутся без прохода по свечам. Фандинг — двоичный поиск по выплатам.

### Вход и выход — две рыночные заявки симулятора

`TradePlanOutcomes` для каждого входа ставит заявку на сумму `1` в E и заявку на весь объём в T = E + срок, затем
спрашивает у симулятора фандинг позиции между исполнениями. Вход, исполнившийся не раньше T, — «нет сделок»: так делает
Python, который ищет минуту входа только внутри срока. «Покрытие» проверяется на отрезке от E до минуты исполнения
выхода; «фандинг» — по покрытию выплат на отрезке от E до исполнения выхода, как в Python, где оно судится от E, а не от
фактического входа.

### Сверка с Python — на синтетике `synthetic.py`

Скрипт в `profit-fox-bench` (`uv run`) пишет фикстуру в тесты:

- `SyntheticMarket` с малым числом пар и дней; на части путей минуты выбиты в NaN (вход по следующей минуте), на части —
  пробел покрытия и конец покрытия выплат раньше конца пути (исключения). Минута T каждого входа остаётся со сделками:
  там правила Python и ADR 0012 дают одну цену, потому что open минуты равен close предыдущей;
- входы — закрытия свечей 4 ч, планы — шорт и лонг со сроком `4h`;
- итоги `simulate` (`status`, `entry_ms`, `exit_ms`, `entry_price`, `exit_price`, `gross`, `slippage`, `fees`,
  `funding`, `net`) с `repr` чисел.

Тест строит пути из фикстуры, считает итоги и сравнивает поля. Ни на каких рыночных данных исходы не считаются ни в
скрипте, ни в тестах.

## Risks / Trade-offs

- [На реальных данных итог отличается от Python на `open(T) − close(T − 1 мин)`] → решение ADR 0012; Python-стенд не
  выносил вердиктов, сохранять нечего.
- [Минута T без сделок сдвигает выход позже конца срока, и сделка держится дольше плана] → так исполнилась бы заявка на
  бирже; фандинг считается по фактическому выходу.
- [`decimal` медленнее `double`] → объём мал; мерить, когда стенд 1.3 прогонит H0001 со случайными входами.
- [Тип выплаты из Strategy в Simulation связывает части Engine] → разрешённая ссылка; отдельный общий тип — когда
  появится второй потребитель.
