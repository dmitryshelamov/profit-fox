# Design

## Context

Мотивация — в proposal.md. Что есть в коде на `release/0.1.0` (`8965d14`) и на что опирается решение:

- **Движок.** `NodeCatalog` знает 14 видов узлов; у вида есть признак `AllowedInSignal` (ложен у `enter`, `stop-loss`,
  `take-profit`, `close-after`). Пины вида — функции графа (`NodeKind.Inputs(graph)`): так узлы `parameters` и `outputs`
  берут пины из графа. Настройка узла — строка из перечня (`SettingDeclaration.Values`). `GraphValidator.ValidateStrategy`
  проверяет граф стратегии, `StrategyGraph.ReadStrategy` отдаёт `TradingStrategy`, `StrategyExecutor` считает шаги,
  `PairPosition` и `Cycle` ведут позицию пары, `TradeSimulator` считает сделку по минутной истории.
- **Сигналы.** Таблицы `signals` (строка с `id uuid`, именем, расположением, номером версии) и `signal_versions` (граф
  версии, только добавляются). Сущность `SignalDocument`, `ISignalRepository`, команды и запросы темы `Signals`. API знает
  сигнал по имени, `id` наружу не отдаётся.
- **Предпросмотр сигнала.** `PreviewSignalQueryHandler` читает свечи таймфрейма и фандинг за всю разведку (в памяти —
  `PreviewHistoryCache` на 5 пар) и считает события `PairEvents.Of`. Минутную историю не читает.
- **Прогон.** `ExecuteRunCommandHandler` считает `PairSteps.Of(strategy…)`, читает минутные свечи недельными блоками с
  событиями (`RunDesign.Span`) и ведёт `PairPosition`.
- **Фронтенд.** Редактор графа (`modules/graph-editor`) общий и принимает `DocumentRules`; сейчас правила одни —
  `signalRules`, а комментарий к ним прямо ждёт правил стратегии. Проверка графа — `useGraphCheck` на
  `POST /api/signals/validate`; пины узла — `pinsOf` из каталога или из графа (`pinsFromGraph`).

Устройство кода — по `match-market-data-structure`: команды в `Commands/<Тема>/<Имя>/`, запросы в `Queries/<Тема>/`,
контракты `<Имя>Internal`, репозитории `<Имя>Repository` с `Contracts`, `Converters`, `Queries`.

## Goals / Non-Goals

**Goals:**

- Стратегию можно собрать на холсте, сохранить с версиями и посмотреть на паре.
- Сигнал входит в стратегию ссылкой на версию, а исполнитель и симулятор не меняются: они получают плоский граф.
- Сохранённая версия стратегии никогда не меняется сама: ни от правки сигнала, ни от его переименования.

**Non-Goals:**

- Составные узлы вообще: узел `signal` — единственный вид со ссылкой, вложенных сигналов нет.
- Автоматический переход стратегии на новую версию сигнала.
- Прогон стенда из стратегии, заморозка стратегии в гипотезе, идеи и бот.
- Свои издержки стратегии: предпросмотр считает с издержками по умолчанию.
- Удаление отдельных версий стратегии или сигнала.

## Decisions

### 1. Ссылка узла сигнала — идентификатор сигнала и номер версии в `settings`

Узел: `{ "id": "s", "kind": "signal", "settings": { "signal": "<uuid>", "version": "2" }, "inputs": { … } }`. Формат
графа и `formatVersion` = 1 не меняются: `settings` уже строки. Идентификатор — `signals.id`, который есть в базе с
`add-bench-service`.

Почему идентификатор, а не имя. Владелец принял «удаление запрещено, переименование обновляет ссылки». Со ссылкой по
имени переименование сигнала должно переписать граф во всех версиях всех стратегий — а версии не меняются (spec
`strategy-constructor` «Версии стратегии»). Со ссылкой по идентификатору обновлять нечего: имя — подпись, которую API
подставляет при чтении.

Альтернативы: имя + запрет переименования используемого сигнала (проще, но владелец выбрал разрешить); имя + перезапись
версий (ломает неизменность версий). Цена выбора: в карточке JSON виден `uuid`, а не имя — имя видно на узле.

Чтобы настройка могла быть не из перечня, `SettingDeclaration` получает признак «свободное значение»: проверка такого
значения — дело вида узла (идентификатор читается как `Guid`, версия — как целое от 1). В каталоге API у такой настройки
пустой список значений.

### 2. Проверка стратегии получает набор сигналов

Пины узла `signal` зависят от самого узла и от библиотеки, а `Domain` в базу не ходит. Поэтому:

- В `Domain` — значение «набор сигналов» (`SignalSet`): по ссылке (идентификатор, версия) отдаёт проверенный `Signal`,
  имя и номер последней версии, либо причину, почему ссылки нет (нет сигнала, нет версии, граф версии не читается).
- Функции пинов вида получают узел и набор: `Inputs(node, graph, signals)`. У прежних видов они узел и набор не читают.
- `StrategyGraph.ReadStrategy(element, signals)` — новая перегрузка; прежняя `ReadStrategy(element)` равна вызову с пустым
  набором, так что гипотезы и `TradingStrategy.FromSignal` работают как раньше.
- Application перед проверкой читает из `ISignalRepository` версии, на которые ссылается граф (одним запросом по списку
  ссылок), и собирает набор. Чтобы узнать ссылки, граф сначала читается по форме (`GraphJson`), без проверки смысла.

У вида `signal` признак `AllowedInSignal` ложен: проверка сигнала отклоняет его тем же правилом, что узлы позиции, с
отдельным кодом ошибки. Новые коды `GraphErrorCode`: `UnknownSignal` (нет сигнала или версии), `UnreadableSignal`,
`SignalInSignal`, `ExpandedIdTaken`; значение вне границ параметра — прежний `ParameterOutOfBounds` с узлом и пином.

Альтернатива — раскрыть граф и проверять только плоский — отброшена: ошибки тогда называли бы узлы `s/high`, которых на
холсте нет, а ошибка «у узла `s` нет входа `limit`» потерялась бы.

### 3. Раскрытие — отдельный шаг между проверкой и исполнением

`TradingStrategy` хранит два графа: `Source` — как записан, и `Graph` — раскрытый; исполнитель по-прежнему компилирует
`Graph`. Раскрытие выполняется только для графа без ошибок проверки и детерминировано:

- **Узлы.** На месте узла сигнала `s` — узлы графа версии в их порядке, кроме `parameters` и `outputs`, с
  идентификаторами `s/<id>`; настройки и записанные значения входов копируются.
- **Параметр.** Провод сигнала `parameters.X -> n.pin` заменяется тем, что подано на вход `X` узла `s`: проводом
  стратегии `src -> s/n.pin`, записанным значением входа `pin` узла `s/n` или, если на входе ничего нет, значением
  параметра `X` версии сигнала.
- **Событие.** Каждый провод стратегии `s.event -> t.pin` становится `src -> t.pin`, где `src` — выход, который в графе
  сигнала подан на узел `outputs`.
- **Порядок проводов.** Сначала провода стратегии в их порядке (провода на входы узла сигнала выпадают, провода от
  `event` переписаны), затем по узлам сигнала в порядке графа — внутренние провода каждого в порядке его графа.
- **Проверка результата.** Раскрытый граф проходит `ValidateStrategy`; ошибка здесь — дефект раскрытия, а не графа
  пользователя, и бросается исключением, как в `TradingStrategy.FromSignal`.

Идентификаторы с `/` допустимы уже сейчас (запрещена только точка). Нового правила идентификаторов нет: совпадение
`s/rate` с узлом, который пользователь так назвал сам, ловит проверка (`ExpandedIdTaken`) до раскрытия.

Номер движка не меняется: исполнитель получает граф из тех же видов узлов, что и раньше. Равенство счёта закрепляет тест
на истории `H0001ParityTests` (spec `strategy-graph` «Раскрытая стратегия считает так же»). Граф не равен тексту
`FromSignal` — там остаётся узел `parameters`, здесь значение параметра вписано во вход, — поэтому сравниваются шаги, а
не графы.

### 4. Хранение: три таблицы, запрет удаления сигнала — внешним ключом

Миграция `202611210001_create_strategy_tables`:

- `strategies (id uuid PK, name UNIQUE, description, layout jsonb, version)` и
  `strategy_versions (strategy_id, version, graph jsonb, created_at, PK (strategy_id, version), FK … ON DELETE CASCADE)` —
  как `signals` и `signal_versions`.
- `strategy_signals (strategy_id, version, node, signal_id, signal_version)`: по строке на узел сигнала версии стратегии.
  `PK (strategy_id, version, node)`, `FK (strategy_id, version) → strategy_versions ON DELETE CASCADE`,
  `FK (signal_id, signal_version) → signal_versions (signal_id, version) ON DELETE RESTRICT`.

Строки `strategy_signals` пишутся в той же транзакции, что версия стратегии. Удаление сигнала каскадом идёт в
`signal_versions` и упирается в `RESTRICT` — база сама не даст удалить используемый сигнал, даже когда удаление и
сохранение стратегии пришли одновременно. `DeleteSignalCommandHandler` до удаления спрашивает имена стратегий, чтобы
ответить ими; нарушение ключа при гонке `SignalRepository` переводит в тот же отказ.

В `Domain`: сущность `Entities/Strategies/StrategyDocument` (`Create`, `Restore`, `Rename` — зеркало `SignalDocument`),
`Repositories/IStrategyRepository` с теми же глаголами, что у `ISignalRepository`, и `UsingSignalAsync(signalId)` —
имена стратегий, чья любая версия ссылается на сигнал. `SignalDocument` получает `Id`; `ISignalRepository` —
`ReadVersionsAsync(ссылки)`. Правило имён и отбор `layout` по узлам графа общие для сигналов и стратегий: код выносится,
а не копируется.

Альтернатива — искать ссылки в `jsonb` версий при удалении — отброшена: гонку не закрывает и читает все версии.

### 5. Application и API

Команды темы `Strategies`: `CreateStrategyCommand`, `ReplaceStrategyCommand`, `RenameStrategyCommand` → `StrategyInternal`;
`DeleteStrategyCommand`. Запросы: `GetStrategiesQuery`, `GetStrategyQuery(Name)`, `CheckStrategyGraphQuery(Graph)` →
`StrategyCheckInternal` (ошибки и `SignalUseInternal` на каждый узел сигнала), `Preview/PreviewStrategyQuery`.

`StrategiesController`, маршруты зеркалят сигналы:

| Запрос | Что делает |
| --- | --- |
| `GET /api/strategies` | список: имя, описание, версия, ошибка чтения |
| `GET /api/strategies/{name}` | стратегия с графом, расположением и сведениями об узлах сигнала |
| `POST /api/strategies`, `PUT /api/strategies/{name}` | создание и сохранение; `400` с ошибками графа |
| `POST /api/strategies/{name}/rename`, `DELETE /api/strategies/{name}` | как у сигналов |
| `POST /api/strategies/validate` | ошибки и сведения об узлах сигнала |
| `GET /api/nodes/strategy` | каталог узлов стратегии |
| `POST /api/preview/strategy` | предпросмотр стратегии |

Сведения об узле сигнала: узел, идентификатор и имя сигнала, версия узла, последняя версия, параметры версии. Их
отдают и проверка, и чтение стратегии — редактору не нужен отдельный запрос «версия сигнала по номеру».

У сигнала в `SignalListItem` и `SignalResponse` появляется `id`. `DELETE /api/signals/{name}` получает ответ `409` с
ошибкой `SignalInUse` и именами стратегий. Прежние маршруты и поля не меняются; `GET /api/nodes` отдаёт то же, что
раньше.

### 6. Предпросмотр стратегии

`PreviewStrategyQueryHandler` проверяет запрос целиком, как предпросмотр сигнала, затем:

1. Берёт свечи таймфрейма и фандинг из `PreviewHistoryCache` (общая с предпросмотром сигнала запись по паре и
   таймфрейму) и считает `PairSteps.Of(strategy…)` — все заявки за разведку.
2. Делит заявки по неделям (UTC, с понедельника — как блок `week` стенда). Берёт не больше 26 последних недель с
   заявками; заявки более ранних недель получают исход «не посчитана».
3. Для каждой взятой недели читает минутные свечи от начала недели до её конца плюс самый длинный срок заявок недели, не
   дальше конца разведки, строит `MinutePaths.Build` и проводит заявки через один `PairPosition` на всю посчитанную
   часть — позиция, открытая в одной неделе, держит пару и в следующей.
4. Заявку, у которой момент плюс срок позже конца разведки, не симулирует: исход `period`.

Исходы: `opened` (сделка `TradeOutcome`), `skipped` (`PairPosition.Enter` вернул null), `excluded` с причиной —
`TradeStatus` симулятора (`plan`, `coverage`, `no-trade`, `funding`) или `period`, `not-computed`. Издержки —
`TradeCosts.Default`. Чтения идут через `MarketHistory` с границей «конец разведки», как у предпросмотра сигнала.

Предел 26 недель — константа рядом с ёмкостью кэша. Он нужен, потому что стратегия с заявкой на каждой свече заставила
бы читать минутные свечи пары за всю разведку (около 1,8 млн). Минутная история в памяти не держится: она зависит от
графа.

Альтернатива — показывать только заявки без сделок — отброшена: без выходов не видно, какие заявки пропущены, а это
главное отличие стратегии от сигнала.

### 7. Фронтенд

- **Правила документа.** `DocumentRules.kind` — `'signal' | 'strategy'`. `strategyRules`: старт — узлы `enter` и
  `close-after`, палитра — каталог стратегии, удалить можно любой узел (нехватку назовёт проверка). В правила уходит и
  то, чем документы различаются в редакторе: адрес проверки и ключ черновика. Ключи черновиков сигналов остаются
  прежними, у стратегий — свой префикс.
- **Узел сигнала.** `pinsOf` для вида с `pinsFromGraph: 'signal'` берёт пины из сведений об узлах сигнала, которые
  пришли с последней проверкой или с чтением стратегии. При добавлении сигнала из палитры и при обновлении версии
  проверка уходит сразу, без задержки 0,4 с; до ответа узел показывает имя и «загрузка». Карточка узла: имя, версия,
  «Обновить до версии N», ссылка на редактор сигнала; у входа без значения — значение параметра серым.
- **Палитра.** Группа «Сигналы» — из `GET /api/signals`; сигнал, который не читается, в неё не попадает.
- **Страницы.** `pages/strategies`: список и редактор — по образцу `pages/signals`; общее между ними (вопрос о черновике,
  сохранение, имя) выносится в общий код страницы документа, а не копируется. Маршруты `/strategies`,
  `/strategies/new/$draftId`, `/strategies/$name`. `SectionNav` получает пункт «Стратегии».
- **Стратегия из сигнала.** Кнопка в редакторе сохранённого сигнала и в строке списка: пишет черновик новой стратегии
  (узел сигнала последней версии, `enter`, провод, `close-after`) и открывает `/strategies/new/<id>`.
- **Панель предпросмотра.** `PreviewPanel` получает вид предпросмотра: для стратегии — метки входа и выхода на графике
  и список заявок с исходом вместо списка событий; выбор пары, таймфрейма, высота панели и пометка «граф изменился» —
  общие.

## Risks / Trade-offs

- [Стратегии отстают от сигнала: правка сигнала их не меняет] → так задумано; узел показывает, что есть новая версия, и
  обновляется одним нажатием. Массового «обновить все стратегии» нет.
- [Сигнал нельзя удалить, пока жива хоть одна версия стратегии со ссылкой на него, даже старая] → отказ называет
  стратегии; удаление стратегии снимает запрет. Удаления отдельных версий нет.
- [В карточке JSON ссылка — `uuid`] → имя видно на узле и в сведениях об узлах сигнала; граф, вставленный в карточку из
  другой базы, даст ошибку `UnknownSignal`, а не молчаливую подмену.
- [Предпросмотр частой стратегии показывает сделки только за последние 26 недель с заявками] → ответ называет момент, с
  которого сделки посчитаны, панель пишет это над списком.
- [Меняется сигнатура функций пинов вида и проверки — задето ядро графа] → прежние тесты `GraphValidationTests`,
  `ExecutionTests`, `H0001ParityTests` и эталон `EngineVersions.json` проходят без правки ожиданий; это условие задач.
- [Идентификаторы `s/rate` в раскрытом графе попадут в текст гипотезы на шаге 2] → формат их допускает; решение о виде
  идентификаторов в замороженном тексте принимается в изменении шага 2, здесь раскрытый граф никуда не пишется.
- [Параметр сигнала с границами, на который подан провод, границами не проверяется] → записано в spec `strategy-graph`
  «Границы параметра на входе узла сигнала»; так же сегодня не проверяется ни один вход, пришедший по проводу.

## Migration Plan

- Ветка `feat/add-strategy-constructor` от `release/0.1.0`, один PR в `release/0.1.0`.
- Одна новая миграция, только новые таблицы; откат — `Down` удаляет три таблицы, прежние данные не задеты.
- API меняется добавлениями; `schema.d.ts` пересобирается из документа OpenAPI.
- Данных для переноса нет: стратегий в базе ещё не было.
