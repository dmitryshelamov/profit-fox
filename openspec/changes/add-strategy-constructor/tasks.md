## Открыто после применения

Сюда записывается всё, что при применении разошлось с design.md.

- 2.1. Прежние `NodeKind.Inputs(graph)` и `Outputs(graph)` оставлены перегрузками: это вид узла вне графа и без
  сигналов (узел `null`, пустой набор), по ним строится каталог API. Новые функции пинов —
  `Inputs(node, graph, signals)`, как в решении 2.
- 2.1. Слова вида `signal` в `NodeTitles` («Сигнал», группа «Сигналы») добавлены уже в группе 2, а не в 4.4: тест
  `NodesTests` требует слов у каждого вида каталога, без них группа 2 не зелёная.
- 2.1. Форма ссылки: `signal` — `Guid` в виде `D`, `version` — целое от 1, записанное без знака и ведущих нулей («2», не
  «02»), чтобы одна версия имела один текст. Неверная форма — `InvalidSetting` по настройке.
- 2.2. Узел сигнала, ссылка которого не найдена или не читается, получает одну ошибку (`UnknownSignal` или
  `UnreadableSignal` с настройкой `signal` либо `version`), а его входы дальше не проверяются: провода и значения на них
  не дают ошибок `UnknownInput`, чтобы ошибка ссылки не размножалась. Выход `event` у такого узла есть, провода от него
  проверяются как обычно.
- 2.2. Проверка сигнала (`ValidateSignal`) узлы `signal` не ищет в наборе: такой узел даёт только `SignalInSignal`.
- 2.3. `ExpandedIdTaken` — по ошибке на каждый занятый идентификатор, у узла сигнала.
- 2.3. Порядок проводов — по решению 3: провода стратегии первыми, затем внутренние. В сценарии spec «Раскрытие
  стратегии H0001» провода перечислены в другом порядке; сценарий порядка не называет, тест проверяет порядок design.md.
  Провод, заменивший провод параметра, стоит среди внутренних на месте этого провода.
- 3.1. В миграцию добавлен индекс `strategy_signals_signal_ix (signal_id, signal_version)`, которого нет в решении 4: по
  нему база проверяет `RESTRICT` при удалении версий сигнала и отвечает `UsingSignalAsync`.
- 3.2. Идентификатор сигнала теперь задаёт сущность: `SignalDocument.Create` берёт новый `Guid`, `Restore` получает `id`
  первым параметром, `SignalRepository.CreateAsync` пишет `signal.Id` (раньше идентификатор придумывал репозиторий).
- 3.2. Отказы библиотеки стратегий — своё исключение `StrategyLibraryException` с `StrategyProblem` (`Invalid`,
  `NotFound`, `NameTaken`, `Unreadable`), по образцу `SignalLibraryException`; в design.md оно не названо.
- 3.2. `StrategyRepository` читает граф версии только по форме (`StrategyGraph.ReadForm`): смысл графа стратегии зависит
  от сохранённых сигналов, его проверяет Application. Ошибка формы или `layout` даёт `StrategyRead` с ошибками.
- 3.2. Общий код с сигналами: отбор `layout` по узлам графа — `Domain/Services/Graph/GraphLayout`, JSON `layout` —
  `Infrastructure/.../Dapper/Converters/LayoutJson` (из `SignalJson` вынесен, не скопирован).
- 3.3. Имена стратегий в отказе удаления сигнала (`SignalProblem.InUse`, свойство `Strategies`) `SignalRepository`
  читает сам, после нарушения внешнего ключа, — так в отказ попадает и стратегия, сохранённая мгновением раньше.
- 3.3. Сохранение стратегии, у которой сигнал удалили между проверкой и записью, `StrategyRepository` отклоняет
  `StrategyLibraryException(Invalid)` только с текстом, без ошибки по узлу: узел в нарушении ключа не назван. Обычный
  случай «Ссылка на удалённый сигнал» ловит проверка графа до записи — ошибкой `UnknownSignal` по узлу (группа 4).
- 4.1. Правило имён — общий `Commands/Base/DocumentNames` для сигналов и стратегий; текст ошибки называет вид документа
  («not a strategy name»), у сигналов текст прежний.
- 4.1. Список стратегий (`GetStrategiesQuery`) помечает ошибкой только стратегию, чья версия не читается по форме или чей
  `layout` не читается; смысл графа со ссылками на сигналы в списке не перепроверяется (версии сигналов неизменны,
  используемый сигнал не удаляется).
- 4.2. «Порт истории не вызван» в unit-тестах проверен устройством обработчика: у `CheckStrategyGraphQueryHandler` нет
  порта рынка в конструкторе; в интеграционном `StrategiesTests` поддельный сервис данных не получил запросов.
- 4.3. `SignalEntryInternal.Id` и `SignalListItem.Id` — `Guid?`: у сигнала, который не читается, идентификатора в списке
  нет. В трёх тестах (`GetSignalsQueryHandlerTests`, `SignalInternalConverterTests`, `SignalRepositoryTests`) записи с
  ожидаемыми полями получили идентификатор: сравнение записей включает новое поле, прочие ожидания не менялись. Тесты
  команд сигналов прошли без правки ожиданий; в `SignalRequests` обработчик удаления получил репозиторий стратегий.
- 4.4. Ответ `409` удаления сигнала — новая схема `SignalInUseResponse` (`errors` с кодом `SignalInUse` и `strategies`):
  поле имён стратегий в прежнюю `RequestError` не добавлено, чтобы схемы базы не менялись (условие 4.5).
- 4.4. `POST /api/strategies/validate` принимает прежний `ValidateGraphRequest` и отвечает `StrategyValidationResponse`
  (`errors`, `signals`). Отказ сохранения при гонке с удалением сигнала (3.3) — `400` с ошибкой `UnknownSignal` без узла.
- 4.5. Для документа OpenAPI dev API перезапущен из этой сессии (прежний процесс `dotnet run` остановлен, новый — по
  `bench-api` из `.claude/launch.json`); при старте миграция `202611210001` применилась к dev-базе. Сравнение с базой:
  добавлены 5 путей и 9 схем, у `SignalListItem` и `SignalResponse` — поле `id`, у `DELETE /api/signals/{name}` — ответ
  `409`; прочие пути и схемы не изменились. `schema.d.ts` — только добавления (473 строки).
- 5.2. Фандинг предпросмотр стратегии читает так же, как предпросмотр сигнала и прогон разведки, — по конец разведки
  включительно (`FundingThrough`, окно до конца плюс 1 секунда): выплата ровно в конец относится к сделкам, что там
  кончаются. Минутные свечи — не дальше конца разведки. Чтение истории разведки вынесено в `PreviewHistory.ReadAsync`,
  общее у двух предпросмотров.
- 5.1. Заявка, срок которой кончается после конца разведки, получает `period` раньше правила одной позиции: её сделка не
  считается, даже если позиция пары в этот момент открыта.
- 5.4. Заявку на каждой свече из нынешних узлов не собрать; замер — на заявке на каждой смене направления свечи (см.
  «Замеры»).
- 6.1. Правила документа получили ещё и адрес проверки и ключ черновика (`checkPath`, `draftKey`), как в решении 7.

## Замеры

Задача 5.4, 2026-11-21, dev-запуск: `bench-api` из `.claude/launch.json` (Debug, сразу после старта, кэш предпросмотра
пуст), `bench-db`, сервис данных из настроек разработки. Время — `curl` `time_total` запроса `POST /api/preview/strategy`,
таймфрейм `1h`, предел 26 недель.

Стратегию «заявка на каждой свече» из нынешних узлов не собрать: `first-time` даёт событие только на смене «ложь →
истина». Замер — на самой частой стратегии, какую можно собрать: два `enter` шорт на `first-time` от `close > previous(close)`
и от его отрицания, `close-after` 1h. Это заявка на каждой смене направления свечи — на BTCUSDT 15 568 заявок на 29 544
свечах `1h`; заявки есть в каждой неделе, так что минутные свечи читаются за все 26 недель, как и при заявке на каждой свече.
Ответ: 2 228 сделок за 26 недель с 2025-11-17, 13 340 заявок «не посчитана».
