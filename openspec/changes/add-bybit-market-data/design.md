# Design

## Context

Мотивация — см. `proposal.md`, требования — `specs/market-data-import` и `specs/market-data-query`.

Текущее состояние: решение `backend/ProfitFox.sln` содержит только скаффолд — слои `Domain` → `Application` → `Infrastructure` → `Presentation` (ASP.NET Core Web API с контроллерами) и проекты `Tests.Unit` / `Tests.Integration` (NUnit). Внешних зависимостей, БД и предметного кода нет. Термины — в `CONTEXT.md`.

Ограничения проекта, влияющие на решение: деньги, цены и объёмы — только `decimal`; время — только UTC `DateTimeOffset`, без `DateTime.Now`; тесты и локальные запуски не отправляют реальных ордеров; новые внешние зависимости вводятся только через этот дизайн; секреты — только через переменные окружения / user secrets.

## Goals / Non-Goals

**Goals:**
- Ввести первое хранилище и первый внешний интеграционный адаптер так, чтобы последующие фичи (бэктест, автоактуализация, live) переиспользовали их без переделки.
- Сделать правила сохранения (закрытые свечи, границы периода, идемпотентность) проверяемыми unit-тестами без сети и БД.

**Non-Goals:**
- Параллельное выполнение нескольких задач загрузки и горизонтальное масштабирование сервиса.
- Отмена задачи пользователем и автоматическое возобновление прерванных задач.
- Пропуск уже загруженных диапазонов при повторной загрузке (см. решение 6).
- Обнаружение и отчёт о «дырах» в данных Bybit.

## Decisions

### 1. Источник: публичный REST API Bybit v5, mainnet, без ключа
Свечи — `GET /v5/market/kline` (`category`, `symbol`, `interval`, `start`, `end` в миллисекундах, `limit` до 1000; `result.list` отсортирован по убыванию `startTime`, элементы — строки `[startTime, open, high, low, close, volume, turnover]`). Проверка символа — `GET /v5/market/instruments-info?category=&symbol=`. Базовый адрес — из конфигурации, по умолчанию `https://api.bybit.com`.
- Рыночные данные публичные: API-ключ не нужен, ордера не отправляются, поэтому mainnet безопасен и правило «никаких реальных ордеров» не затрагивается.
- Testnet отклонён: его история неполная и не совпадает с реальной.
- Готовые SDK (например, `Bybit.Net`) отклонены: ради двух публичных эндпоинтов они тянут большую зависимость, а парсинг строк в `decimal` всё равно хотим контролировать сами.

### 2. Постраничная выгрузка от конца периода к началу
Адаптер запрашивает страницы по 1000 свечей, двигая `end` назад (`end` = open time самой ранней полученной свечи − 1 мс), пока не дойдёт до `from` или Bybit не вернёт пустую страницу. Каждая страница сразу сохраняется — так прогресс задачи растёт, а при ошибке сохранённое остаётся (требование «Ошибка биржи»). Так работает пагинация Bybit (ответ по убыванию), отдельного запроса «найти начало истории» не нужно; это же покрывает «Период до листинга».

### 3. Правило закрытой свечи — чистая доменная функция с инжектируемым временем
`Interval` в `Domain` знает конец свечи по её open time: фиксированная длительность для минутных интервалов и `D`, 7 суток для `W`, начало следующего календарного месяца UTC для `M`. Свеча закрыта, если её конец ≤ «сейчас». «Сейчас» берётся из `TimeProvider` (.NET), в тестах — `FakeTimeProvider`. Конец периода по умолчанию (`to` не указан) — тоже из `TimeProvider` в момент создания задачи. Фильтрация закрытых свечей и границ `[from, to)` делается в `Application` до сохранения, поэтому проверяется unit-тестами на эталонных наборах.

### 4. Хранилище: PostgreSQL + TimescaleDB, доступ через EF Core (Npgsql)
- Таблица `candles`: `category`, `symbol`, `interval`, `open_time timestamptz`, `open`, `high`, `low`, `close`, `volume`, `turnover` — `numeric` без фиксированной точности (значение хранится ровно как пришло). Первичный ключ `(category, symbol, interval, open_time)`. Hypertable по `open_time`.
- Таблица `candle_import_jobs`: идентификатор (`uuid`), параметры, статус, число сохранённых свечей, причина ошибки, `created_at` / `started_at` / `finished_at`.
- Схема — миграции EF Core; `CREATE EXTENSION timescaledb` и `create_hypertable` — raw SQL внутри миграции. Миграции применяются при старте сервиса (на этом этапе один экземпляр, без отдельного шага деплоя).
- Upsert свечей — один SQL-запрос на страницу: `INSERT ... SELECT FROM unnest(...) ON CONFLICT (pk) DO UPDATE`. EF Core change tracking для пакетов по 1000 строк медленный и не умеет upsert.
- Альтернативы: Dapper + DbUp/FluentMigrator — меньше магии, но миграции и маппинг пишутся вручную, а для будущих сущностей (стратегии, ордера) EF Core удобнее; чистый PostgreSQL без TimescaleDB — выбран владельцем вариант с TimescaleDB ради сжатия и быстрых диапазонных запросов на больших объёмах минутных свечей.

### 5. Фоновое выполнение: in-process очередь и один воркер
`POST` сохраняет задачу (`Pending`) и кладёт её идентификатор в `Channel<Guid>`; `BackgroundService` берёт задачи по одной и выполняет последовательно. Состояние задачи живёт в БД, очередь — только сигнал. При старте, до приёма запросов, все задачи `Pending`/`Running` переводятся в `Failed` («прервана перезапуском сервиса»).
- Последовательное выполнение держит нагрузку далеко под лимитом Bybit (600 запросов / 5 с на IP) без отдельного rate limiter.
- Альтернативы: Hangfire/Quartz — избыточная зависимость ради одной очереди; возобновление прерванных задач — лишнее поведение, раз повторный запуск идемпотентен и дешёв.

### 6. Идемпотентность через upsert, без пропуска загруженных диапазонов
Повторная задача всегда заново выгружает весь запрошенный период и делает upsert. Результат совпадает с «дозагрузкой только недостающего», а логики вычисления пропусков нет. Цена — лишние запросы к Bybit при повторной загрузке длинного периода (год минутных свечей ≈ 526 запросов, единицы минут). Оптимизация — отдельной фичей, если станет заметной.

### 7. Повторы при ошибках Bybit
Повтор с экспоненциальной паузой (1, 2, 4, 8, 16 с; не более 5 повторов) на HTTP 429, 5xx, таймаут и `retCode` = `10006` (rate limit). Остальные ненулевые `retCode` — сразу `Failed` с текстом `retMsg`. Пауза — через `TimeProvider`, поэтому тесты повторов не ждут реального времени. Реализация — собственный цикл в адаптере, без Polly: поведение маленькое и полностью покрыто тестами.

### 8. Проверка символа синхронно в `POST`
Символ проверяется до создания задачи через `instruments-info`: пустой `result.list` → 400 по полю `symbol`; Bybit недоступен → 503. Пользователь сразу видит ошибку в символе, а не узнаёт о ней из упавшей задачи.

### 9. HTTP API
- `POST /api/market-data/candle-imports` — тело `{ category, symbol, interval, from, to? }` → `202 Accepted`, `Location` на задачу, тело — задача.
- `GET /api/market-data/candle-imports/{id}` → `200` с задачей или `404`.
- `GET /api/market-data/candles?category=&symbol=&interval=&from=&to=&limit=` → `200` со списком свечей; `from` и `to` обязательны.
- Ошибки валидации — `400` в формате `ProblemDetails` (`errors` по полям); недоступность Bybit — `503`.
- `category` — строки `spot` / `linear`; `interval` — коды Bybit (`1` … `720`, `D`, `W`, `M`), как в `CONTEXT.md`; символ приводится к верхнему регистру. Время — ISO 8601, любой offset приводится к UTC.
- `decimal` в JSON — строками (`"0.000123"`): JSON-числа в JavaScript-клиентах теряют точность. Включается конвертером System.Text.Json только для свечей.

### 10. Раскладка по слоям
- `Domain`: `MarketCategory`, `Instrument` (категория + символ), `Interval` (коды Bybit и конец свечи), `Candle`.
- `Application`: сценарии «создать задачу», «выполнить задачу», «прочитать свечи», «пометить прерванные»; порты `IBybitMarketDataClient`, `ICandleStore`, `ICandleImportJobStore`.
- `Infrastructure`: HTTP-адаптер Bybit (typed `HttpClient`), EF Core `DbContext`, миграции, реализации хранилищ.
- `Presentation`: контроллеры, `BackgroundService`, регистрация зависимостей, применение миграций при старте.

### 11. Тесты
- Unit (`Tests.Unit`): конец свечи для каждого вида интервала, фильтр закрытых свечей и границ периода, парсинг ответов Bybit на эталонных JSON-фикстурах, пагинация и повторы адаптера на подменённом `HttpMessageHandler`, валидация запросов.
- Integration (`Tests.Integration`): `WebApplicationFactory` + TimescaleDB в Testcontainers (образ `timescale/timescaledb` с фиксированной версией тега) + подменённый HTTP Bybit. Покрывают upsert/идемпотентность, hypertable-миграцию, сценарии API целиком, перевод прерванных задач в `Failed`.
- Ни один тест не ходит в реальный Bybit.

### 12. Локальная разработка
`docker-compose.yml` в корне репозитория с сервисом TimescaleDB (тот же тег образа, что в тестах). Пароль — из `.env` (в `.gitignore`), в git — `.env.example`. Строка подключения сервиса — `ConnectionStrings__MarketData` через переменную окружения или user secrets.

## Risks / Trade-offs

- [Bybit меняет формат ответа или лимиты] → парсинг изолирован в адаптере и покрыт фикстурами; лимиты — повторы с backoff.
- [`instruments-info` не возвращает делистнутые символы] → историю делистнутых инструментов загрузить нельзя; приемлемо для первой версии, при необходимости — отдельное изменение.
- [Миграции при старте и несколько экземпляров сервиса] → сейчас экземпляр один; при масштабировании миграции выносятся в отдельный шаг.
- [Последовательный воркер — долгие задачи блокируют очередь] → для ручной загрузки истории приемлемо; параллелизм — при появлении автоактуализации.
- [Интеграционные тесты требуют Docker] → Docker уже нужен для dev compose; без Docker запускаются только unit-тесты.
- [Повторная загрузка длинного периода тратит запросы] → см. решение 6.

## Migration Plan

Первое хранилище, данных для переноса нет. При старте сервис применяет миграции к пустой БД. Откат — удалить БД / volume dev compose. Production не затрагивается.
