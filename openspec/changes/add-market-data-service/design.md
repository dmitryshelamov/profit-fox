# Design

## Context

Мотивация и объём — в `proposal.md`, поведение — в спеках `market-data-service`, `market-data-parity`,
`production-deploy`, `service-metrics` и `monitoring`. Ниже только то, что определяет подход.

Решения владельца на грилинге 2026-11-11:
- цель — один источник для всех машин;
- транспорт — gRPC: история по запросу, подписка с курсора с догонкой из базы, формирующаяся свеча отдельным методом;
- по сделкам хранятся только минутные суммы;
- сначала сервис работает отдельно, переезд — потом;
- в первом изменении все данные сканера и сделки;
- история 90 дней настройкой, старше — догрузка по запросу;
- машина — отдельный мини-ПК N150;
- проверка — сверка со сканером и метрики, переезд после 7 дней без необъяснённых расхождений;
- `collect-trade-flow` сначала мержится как есть;
- свой потолок REST;
- отдельный деплой.

Что уже есть в коде:
- **Процесс сканера** `ProfitFox.Scanner` — generic host без HTTP с арендой потока в `scanner_state`.
  - `BybitMarketStreams` подписывает kline 1m и ликвидации пачками по 10 тем, по 100 тем на соединение. Обработчик
    kline сейчас пропускает только закрытые свечи. `Breaks` пишет один разрыв на поток в `stream_breaks`.
  - `ScannerBackfill` догружает минуты, открытый интерес и фандинг через `IMarketDataFeed` (`BybitPublicDataClient`).
    Минута, которой биржа не дала внутри загруженного диапазона, не хранится: в ней не было сделок.
  - `ScannerMinuteCycle` берёт точку открытого интереса из тикеров в первую минуту 5-минутного шага, иначе оставляет
    шаг истории.
  - `ScannerUniverse.Select` и `Merge` — чистые функции списка пар.
- **`ScannerRestGate`** — token bucket `Scanner:RestRequestsPerSecond` (на проде 20) с паузами на 403, 429 и `10006`.
  Конец паузы хранится в `scanner_state.rest_paused_until`. Лимит Bybit по IP — 600 запросов за 5 секунд.
- **`collect-trade-flow`** (мержится до этого изменения) даёт:
  - `IMarketStreams.SubscribeTradesAsync` и `TradeEvent`;
  - сведение сделок в минуты `TradeFlowMinutes`;
  - разбор суточного архива и пересборку дня;
  - таблицы `trade_flow_minutes` (гипертаблица со сжатием через 7 дней) и `trade_flow_days`.
- **gRPC в проекте** только клиентский: T-Invest на `Grpc.Net.Client`. Тесты поднимают его сервер в процессе
  (`MockTInvestApi`).
- **Миграции** FluentMigrator лежат в одной сборке Infrastructure, их применяет API.
- **Метрики** уходят по OTLP через `MetricsRegistrar.Configure(configuration, services, serviceName)`.
- **Деплой**: `deploy.yml` собирает образы на `ubuntu-latest`, runner soyo-03 выкатывает по SSH с принудительной командой
  `deploy/deploy.sh`. Удалённый Worker запускается отдельным compose-проектом `docker-compose.worker.yml`.

## Goals / Non-Goals

**Goals:**
- Сервис, у которого подписчик закрытых данных не может пропустить изменение. Ни перезапуск сервиса, ни обрыв сети, ни
  медленное чтение к пропуску не ведут.
- Схема базы сервиса скрыта за контрактом gRPC, а контракт растёт только расширением.
- Ни одного нового запроса к Bybit сверх потолка сервиса.
- Ни одного изменения в поведении сканера, API и Worker'а.

**Non-Goals:**
- Перевод сканера, графиков, Worker'ов и replay на сервис.
- Тикеры как отдельный вид данных.
- Moex.
- Хранение сырых сделок.
- Общий лимитер на Redis.
- Авторизация и TLS в gRPC.
- Бэкапы базы сервиса.
- Свечи интервалов кроме 1m в живом сборе: они есть только через догрузку по запросу.

## Decisions

### 1. Три новых проекта, слои те же

- `ProfitFox.MarketData` — хост ASP.NET Core с Kestrel: gRPC на порту `5100` (HTTP/2 без TLS) и `/health` на
  `127.0.0.1:5101` (HTTP/1.1) для скрипта деплоя. Внутри `Program.Configure` и `InfrastructureRegistrar.ConfigureMarketData`.
- `ProfitFox.MarketData.Contracts` — `Protos/market_data.proto` и код, который `Grpc.Tools` генерирует для сервера и
  клиента. Проект не зависит от Domain: его подключают сервис, сверка, а потом и потребители.
- `ProfitFox.MarketData.Parity` — generic host сверки, `InfrastructureRegistrar.ConfigureMarketDataParity`.

Логика живёт в Application:
- `MarketDataService` — сбор, покрытие, журнал изменений, история, подписки;
- `MarketDataParity` — сверка.

Адаптеры — в Infrastructure: Bybit, база сервиса, gRPC-сервер и gRPC-клиент сверки. Domain переиспользуется как есть:
`Candle`, `Instrument`, `OpenInterestPoint`, `FundingRatePoint`, `LiquidationEvent`, `TradeEvent`, минуты сделок.

Отвергнуто:
- **Отдельное решение или репозиторий.** Пришлось бы дублировать домен и Bybit-адаптеры.
- **REST/JSON вместо gRPC.** Нет потоков с обратным давлением, владелец выбрал gRPC.
- **Прямое чтение базы сервиса потребителями.** Схема становится контрактом, владелец выбрал gRPC.

### 2. Своя база, свои миграции, миграции применяет сам сервис

TimescaleDB в контейнере на N150, строка `ConnectionStrings:MarketStore`. Миграции сервиса лежат в отдельном пространстве
имён `Persistence/Postgres/FluentMigrator/MarketStore`. Раннер сервиса берёт только его, раннер API его исключает (фильтр
по пространству имён). Это проверяет тест: миграция одного набора не попадает в другой. Сервис применяет миграции на
старте до взятия аренды. Отвергнуто: миграции силами API — API живёт на другой машине и к этой базе не ходит.

Таблицы базы сервиса:
- `candles` — та же схема, что в прод-базе: свечи 1m из сбора и свечи других интервалов из догрузки;
- `open_interest`, `funding_rates`, `liquidations`, `trade_flow_minutes`, `trade_flow_days`, `stream_breaks` — та же
  схема, что в прод-базе;
- `pairs` — список пар со сроками торгов;
- `coverage` — решение 8;
- `changes` — решение 7;
- `collector_state` — одна строка: аренда и `rest_paused_until`.

Схемы прод-таблиц повторяются намеренно: так в сервисе переиспользуются те же репозитории Dapper, только с другой строкой
подключения.

### 3. Аренда и один писатель

Аренда в `collector_state` устроена как у сканера: `LeaseKeeper` и `WorkerIdentity`. Внутри держателя все записи в таблицы
данных, `coverage` и `changes` идут через одну полосу записи `ChangeWriter`, по одной транзакции за раз. Очередей две:
- живые минуты (пачка всех пар за минуту по каждому виду);
- всё остальное: догрузки, история, пересборка дней.

Живая очередь всегда идёт первой. Так порядок курсоров в `changes` совпадает с порядком коммитов (решение 7), а загрузка
истории не задерживает живые минуты. Объём укладывается в один писатель: живые данные — около 3 транзакций в минуту плюс
OI раз в 5 минут, история — страница за транзакцию.

### 4. Пары

Своя таблица `pairs`. Список перечитывается раз в 10 минут: `ListInstrumentsAsync` по `spot` и `linear`, затем
`ScannerUniverse.Select` и `Merge` — те же правила, что у сканера, чтобы сверка сравнивала одинаковые множества.
Подписки обновляются сразу после перечитывания. Настройка `MarketData:Symbols` сужает список в тестах, как у сканера.

### 5. Один набор сокетов на вход

Новый порт `IMarketDataStreams` реализуется в `BybitMarketDataStreams` на тех же правилах: пачки по 10 тем, 100 тем на
соединение, `Breaks` на каждый поток. Темы:
- `kline.1` всех пар;
- `publicTrade` всех пар;
- `allLiquidation` пар `linear`.

Всего около 3 250 тем, это около 33 соединений. Обновление kline с `confirm = false` идёт в доску формирующихся значений
(решение 12), с `confirm = true` — в живую очередь записи. Сделки идут и в минуты потока (`TradeFlowMinutes` из
`collect-trade-flow`), и в текущую минуту доски. Отвергнуто: расширять `BybitMarketStreams` сканера — он завязан на
`ScannerSettings`, а сканер в этом изменении не меняется.

Точка открытого интереса берётся по тому же правилу, что у сканера: тикеры `linear` одним запросом в первую минуту
5-минутного шага, иначе шаг из истории. Фандинг — `TopUpFunding` по тем же правилам раз в 10 минут. Иначе сверка видела
бы расхождения, порождённые только разным источником.

### 6. Минуты в базу через 5 секунд после конца минуты

Закрытая свеча копится в живой очереди до `конец минуты + 5 с`, затем все свечи минуты уходят одной транзакцией. Свеча,
закрытая позже, уходит следующей пачкой. Минуты сделок закрываются так же, через `TradeFlowMinutes`. Ликвидации пишутся
пачкой раз в 5 секунд. Запас 5 с покрывает задержку `confirm` у Bybit. Спека требует 15 с, оставшиеся 10 с — запас на
запись.

### 7. Журнал изменений: одна строка на транзакцию и вид данных, курсор — её номер

```
changes (seq bigint PRIMARY KEY, kind text, "interval" text NULL,
         "from" timestamptz, "to" timestamptz, instruments text[], written_at timestamptz)
```

Строку пишет `ChangeWriter` в той же транзакции, что данные и покрытие. В ней сказано, что у этих пар серия `kind`
(и `interval`) за `[from, to)` заменена целиком. `seq` выдаёт писатель, а раз писатель один, порядок `seq` равен порядку
коммитов. Поэтому подписчик, дочитавший до `seq`, никогда не увидит позже строку с меньшим номером.

Примеры:
- пачка минутных свечей всех пар за 12:04 — одна строка с ~1 200 парами;
- страница истории одной пары — одна строка;
- пересборка дня сделок пары — одна строка на день.

Подписка отдаёт строку журнала как изменение. Содержимое серий она читает из таблиц данных в момент отправки вместе с
текущим покрытием периода. Если период позже заменили ещё раз, подписчик сразу получит новое содержимое, а потом это же
изменение ещё раз. Состояние после применения всех изменений верное, применение идемпотентно: это замена периода.
Промежуточное состояние подписчик может не увидеть, и ни одному потребителю оно не нужно.

`changes` — гипертаблица по `written_at`. Политика удаляет куски старше `MarketData:ChangeRetentionDays` (7).
`GetCursor` отдаёт наибольший `seq`. Курсор меньше наименьшего хранимого `seq − 1` получает `FAILED_PRECONDITION` с
причиной `cursor_expired`.

Отвергнуто:
- **`seq` в каждой таблице данных.** Удаление минуты при пересборке дня требует надгробий, а подписке пришлось бы сливать
  пять таблиц по порядку.
- **Журнал с полным содержимым.** Данные хранились бы дважды, а живая минута всех пар — это 150 КБ на строку.
- **`LISTEN/NOTIFY` как источник изменений.** Уведомления теряются, пока клиент не подключён; он используется только
  как сигнал «есть новое».
- **Логическая репликация или Debezium.** Новая инфраструктура ради одного потребителя.
- **Курсор по времени минуты.** Не выражает поздние догрузки и пересборки прошлых дней.

### 8. Покрытие — непересекающиеся диапазоны по серии

```
coverage (category, symbol, kind, "interval", "from", "to")
```

Здесь `kind` — один из `candles`, `open_interest`, `funding`, `liquidations`, `trade_flow`. Смежные диапазоны сливаются
при записи в той же транзакции. Чистая функция слияния и вычитания диапазонов живёт в Domain и проверяется юнит-тестами
на эталонных наборах.

Как растёт покрытие:
- **Живая минута** продлевает диапазон пары, если поток с последней записанной минуты не прерывался.
- **Разрыв** обрывает диапазоны всех пар этого потока на минуте потери связи. По `Breaks` нельзя понять, каких пар он
  коснулся, поэтому считаем, что всех.
- **Догрузка по REST** добавляет загруженный период целиком: пустые минуты внутри — минуты без сделок, как у сканера.
- **Пересборка дня из архива** покрывает день `trade_flow`.
- **Ликвидации** покрываются только живым сбором.

Историю запроса за пределами торгов пары тоже покрывает ответ биржи: пустая страница до листинга запоминается, и запрос
не повторяется.

### 9. История: одна очередь загрузки с приоритетами

`HistoryLoader` в Application держит задачи «серия, диапазон» с приоритетами:
1. пропуски после разрыва и перезапуска;
2. догрузка по запросу клиента — ждущие вызовы `GetHistory`;
3. окно `MarketData:HistoryDays` (90) от свежих дней к старым.

REST-задачи идут по одной через гейт (решение 10). Дни архива идут по одному файлу за раз в своей полосе: это статический
хостинг, а не API, поэтому в потолок REST не входит. Одинаковые задачи на одну серию и пересекающиеся диапазоны сливаются,
и два клиента с одним запросом ждут одну загрузку.

`GetHistory` вычитает покрытие из запрошенного периода, ставит недостающее в очередь с приоритетом 2 и ждёт. Затем
постранично отдаёт данные и покрытие. Если гейт на паузе или биржа ответила ошибкой, вызов не ждёт конца паузы: он отдаёт
то, что есть, с `exchange_unavailable = true`. Так ведёт себя и read-through графиков сейчас. Свечи других интервалов
хранятся, только когда закрыты, по правилу `ChartCandles`.

### 10. Общий REST-гейт без изменения поведения сканера

Логика `ScannerRestGate` выносится в `RestGate`:
- token bucket по `RestGateSettings` (`RequestsPerSecond`, `Pause`, `LimitPause`, читается через `IOptionsMonitor`);
- паузы;
- порт `IRestPauseStore` для конца паузы.

`ScannerRestGate` остаётся регистрацией `RestGate` с настройками `Scanner` и хранилищем на `scanner_state`. Его тесты не
меняются и должны остаться зелёными: это доказательство, что поведение сканера то же. У сервиса — `MarketData:Rest`
(по умолчанию 10 запросов в секунду, это 50 из 600 за 5 с) и хранилище на `collector_state`. `BybitPublicDataClient`
берёт гейт через абстракцию, а не конкретный класс.

Счётчики Bybit REST и заголовки лимита (`BybitLimitHeadroom`) работают в сервисе как есть, с `service.name =
market-data`. Так его нагрузка сразу видна на дашборде «Bybit REST».

### 11. Контракт gRPC

```proto
service MarketData {
  rpc GetHistory(HistoryRequest) returns (stream HistoryPage);
  rpc GetCursor(CursorRequest) returns (Cursor);
  rpc SubscribeClosed(ClosedRequest) returns (stream Change);
  rpc WatchForming(FormingRequest) returns (stream FormingUpdate);
}
```

Как кодируются поля:
- **Числа** — строкой десятичной записи (invariant), в коде `decimal`. Отвергнуто: `double` (запрещён правилами домена)
  и пара `units`/`nanos` (9 знаков мало для цен вроде `0.0000001234`).
- **Время** — `google.protobuf.Timestamp`, всегда UTC.
- **Вид данных** — `enum Kind` с `KIND_UNSPECIFIED = 0`.
- **Изменение** — `Change { seq, kind, interval, from, to, repeated SeriesContent series }`, где
  `SeriesContent { instrument, oneof rows, repeated Range coverage }`.
- **Страница истории** — `HistoryPage { rows, coverage, exchange_unavailable }`, не больше 1 000 строк.

Ошибки:
- `NOT_FOUND` — пары нет;
- `INVALID_ARGUMENT` — неверный период или интервал, больше 20 пар у `WatchForming`;
- `FAILED_PRECONDITION` с `cursor_expired`.

Совместимость проверяет тест. Копия `.proto` первой версии заморожена в `Tests.Integration/MarketData/Contract/v1`, из неё
генерируется клиент, и он проходит основные сценарии против текущего сервера. Номера полей не переиспользуются, поля не
удаляются — это правило записывается в `docs/conventions.md`.

### 12. Подписки: курсор читается из базы, память на подписчика ограничена

`SubscribeClosed` — цикл на подписчика:
1. прочитать `changes WHERE seq > cursor ORDER BY seq LIMIT 100`;
2. для каждой строки, проходящей фильтр видов и пар, прочитать содержимое и отправить;
3. когда журнал дочитан, ждать сигнала `ChangeNotifier` после коммита писателя или 1 с.

Буферов рассылки нет. Медленный клиент тормозит только `WriteAsync` своего цикла, обратное давление HTTP/2 доходит до
него, а в памяти лежит одна страница. Сбор и другие подписчики этого не замечают.

`WatchForming` читает доску формирующихся значений: в памяти последнее значение свечи и текущей минуты сделок по каждой
паре. Раз в секунду цикл подписчика отправляет пары, у которых значение сменилось с прошлой отправки. Закрытие минуты
отправляется сразу. Если клиент не читает, цикл стоит на `WriteAsync`, а доска продолжает перезаписываться, так что после
паузы он получит последнее значение.

### 13. Сверка

`ProfitFox.MarketData.Parity` — generic host. Он читает прод-базу существующими репозиториями (`ICandleRepository`,
`IOpenInterestRepository`, `IFundingRateRepository`, репозитории ликвидаций, `trade_flow_*` и `stream_breaks`) со строкой
read-only роли. В сервис ходит клиентом из Contracts.

- **Живая полоса**: подписка на все виды с курсора из файла `/data/parity-cursor` (том compose). Каждое изменение
  выжидает `Parity:Margin` (3 мин) после `written_at`. Потом сравнение с прод-строками тех же пар за тот же период внутри
  покрытия прода: `scanner_pairs.history_from…covered_until`, у OI и фандинга — их границы, у ликвидаций и сделок —
  время сбора минус разрывы.
- **Ночная полоса** в 00:30 UTC: `GetHistory` прошедшего дня по каждой паре и виду. Всё внутри покрытия сервиса, поэтому
  к бирже не обращается. Минуты сделок сверяются на день позже и только по дням, которые прод отметил `rebuilt`.
- **Объяснение**: расхождение или дыра объяснены, если их время в разрыве из `stream_breaks` прода или сервиса (сервис
  отдаёт разрывы в покрытии как его границы).
- **Вывод**: счётчики метра `ProfitFox.MarketData.Parity` и итог дня в журнал с первыми 20 необъяснёнными.

На soyo-01 сверка запускается отдельным compose-проектом `docker-compose.market-data-parity.yml` (как
`docker-compose.worker.yml`) с `cpus: 0.5` и 512 МБ. `docker-compose.prod.yml` не меняется.

### 14. Деплой

- **`deploy.yml`**: job `build` собирает ещё образы `market-data` и `market-data-parity`, job `images` проверяет все
  шесть. Выкатка прода по-прежнему трогает только свои четыре сервиса.
- **Новый `deploy-market-data.yml`**: только `workflow_dispatch` с номером версии. Job на `[self-hosted, soyo-03]` в
  Environment `market-data` с обязательным подтверждением владельца и только для `main`. Адрес N150 — переменная
  репозитория `MARKET_DATA_HOST`, это не секрет.
- **Новый `deploy/market-data-deploy.sh`** — принудительная команда ключа на N150 (`deploy <N> <protocol>`). Те же
  проверки, что у `deploy.sh`: тег `v<N>`, коммит в `main`, метка ревизии образа. Скрипт скачивает
  `docker-compose.market-data.yml` этого коммита, поднимает `db` и `market-data` и ждёт `/health`. Общие функции двух
  скриптов не выносятся: копия из 40 строк проще, чем библиотека shell для двух машин.
- **`docker-compose.market-data.yml`**: `db` (TimescaleDB того же образа, что прод, порт не публикуется) и `market-data`
  (порт `5100` на LAN-интерфейсе). Пароль базы — в `~/profit-fox-market-data/.env.market-data` (права `600`).
- **`deploy.test.sh`** дополняется тестами разбора команды и отказов второго скрипта.

Отвергнуто:
- **Выкатка сервиса с каждой версией прода.** Каждый релиз рвал бы сокеты, сделки за рестарт возвращались бы только
  архивом на следующий день, а догрузки свечей тратили бы общий лимит.
- **Выкатка по изменению путей.** Сервис зависит от общих Domain, Application и Infrastructure, которые меняются почти в
  каждом PR, так что сервис перезапускался бы почти каждый раз.

### 15. Тесты

Юнит-тесты:
- слияние и вычитание покрытий;
- правила изменения и их идемпотентность;
- доска формирующихся значений и прореживание раз в секунду;
- `RestGate` (существующие тесты сканера плюс хранилище сервиса);
- сравнение и объяснение в сверке на маленьких эталонных наборах.

Интеграционные тесты с Testcontainers TimescaleDB. Сервис поднимается в процессе (`WebApplicationFactory`, клиент
`Grpc.Net.Client` через обработчик тестового сервера), Bybit — `FakeBybitSocketServer` и `FakeBybitHandler`, архив —
HTTP-заглушка. Сценарии:
- догонка и живой поток без пропусков и повторов через перезапуск сервиса;
- медленный и быстрый подписчики;
- устаревший курсор;
- догрузка при чтении и отсутствие повторного запроса;
- пауза 403, пережившая перезапуск;
- два процесса и одна аренда;
- замороженный клиент v1;
- сверка против прод-базы-заглушки с расхождением и с разрывом.

Ни один тест и ни один локальный запуск не обращаются к настоящему Bybit.

## Risks / Trade-offs

- **Характеристики N150 не проверены** (оценка: SSD от 500 ГБ, память от 16 ГБ). → До первой выкатки владелец сообщает
  диск и память. Таблицы сжимаются через 7 дней. На 90 дней это около 160 млн минутных свечей и 150 млн минут сделок, по
  оценке — десятки ГБ.
- **Гео-блок CloudFront.** Точка раздачи Bybit уже отвечала 403 «block access from your country» soyo-01. → До выкатки
  проверить с N150 доступ к `api.bybit.com`, `stream.bybit.com` и `public.bybit.com` (задача с одобрением владельца).
  При 403 потоки или архив не идут, и это видно по метрикам.
- **Первая загрузка долгая.** Около 265 тыс. REST-запросов при потолке 10 в секунду — около 7,5 часа. Архив сделок за
  90 дней — около 130 ГБ скачивания. → Свежие дни идут первыми, прогресс виден на дашборде, сверка до конца загрузки
  сверяет только покрытое.
- **Сверка может показать расхождения, которые порождает разный путь записи, а не ошибка.** Например, точка OI из тикера у
  одной стороны и из истории у другой. → Правила записи OI и фандинга взяты у сканера (решение 5). Каждое такое
  расхождение разбирается и записывается в этот документ до переезда.
- **Содержимое изменения читается в момент отправки, а не в момент записи** (решение 7). → Для замены периода это верно.
  Если потребителю понадобится история промежуточных состояний, это отдельное решение.
- **Догрузка по запросу большой глубины** (например, сделки BTC за год — около 29 ГБ архива) держит вызов часами. → Вызов
  получает страницы по мере загрузки дней. Ограничение глубины одного запроса — отдельным решением, если понадобится.
- **Один писатель** — потолок пропускной способности записи. → Живая очередь первой, история страницами. При заметном
  отставании живых минут оно видно на метрике задержки, и тогда историю можно писать пачками крупнее.

## Migration Plan

1. Шаги владельца на N150: Docker, пользователь в группе `docker`, каталог `~/profit-fox-market-data`,
   `.env.market-data`, ключ выкатки с `from=<soyo-03>` и принудительной командой `market-data-deploy.sh`, `known_hosts`
   на soyo-03. В GitHub: Environment `market-data` и переменная `MARKET_DATA_HOST`.
2. Проверка доступа к Bybit с N150 (задача с одобрения владельца).
3. Мерж и выкатка сервиса на N150 вручную на номер версии. Сервис сам создаёт свою базу и начинает сбор и загрузку
   истории.
4. Шаг владельца на soyo-01: read-only роль в прод-базе и `parity.env`. Запуск `docker-compose.market-data-parity.yml` на
   тот же номер.
5. 7 дней наблюдения по дашборду «Сервис рыночных данных». Каждое необъяснённое расхождение разбирается.
6. Переезд потребителей — следующее изменение.

Откат: выкатка сервиса на предыдущий номер, данные в его базе сохраняются. Сверка останавливается `docker compose down`.
Прод ни от того, ни от другого не зависит.
