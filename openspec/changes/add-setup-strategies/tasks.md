# Tasks

Тесты бэкенда запускаются из `backend/`: `dotnet test ProfitFox.slnx`; фронтенда — из `frontend/`: `npm test`, `npm run
typecheck`, `npm run lint`, `npm run format:check`, `npm run build`. Каждая задача начинается с теста, который без неё
падает, и каждая группа заканчивается зелёным прогоном всех тестов своей части.

прежние тесты узлов. `EngineVersion.Number` остаётся `4`. Если задача требует иного — остановиться и записать это в
раздел «Открыто после применения» в конце этого файла.

## Открыто после применения

- **`atr` с длиной 1.** Spec «Длина окна» разрешает `length` от 1, а `AtrList` пакета отказывает при длине 1
  (`ArgumentOutOfRangeException`: «Lookback periods must be greater than 1 for Average True Range»). Своей формулы для
  этого случая нет (решение владельца — считает пакет), поэтому узел `atr` с длиной 1 отдаёт отсутствующее значение, а
  проверка графа литерал `1` пропускает, как велит spec. Нужно решение: сузить в spec длину `atr` до 2–1000 (и тогда
  проверка графа отклонит литерал `1`) или оставить как есть. `rsi` с длиной 1 пакет считает.
  **Закрыто (8.2):** длина `atr` — от 2 до 1000, литерал `1` — ошибка проверки графа, `1` с провода — пусто.
- **Перечни каталога в прежних тестах.** Новые виды нельзя добавить, не дополнив тесты, которые перечисляют весь каталог:
  `NodeCatalogTests` (порядок видов и строка пинов каждого вида), в `NodesTests` число видов каталога сигнала (14 → 25),
  перечень видов и состав группы «Числа», во фронтенде — перечень групп палитры в `editorLook.test.tsx` (добавлены «Окна»
  и «Индикаторы») и перечень токенов темы в `theme.test.ts` (33 → 35). Строки прежних видов не менялись, добавлены только новые — так же, как делало
  изменение add-ideas-and-market с `pair-candle`. Тесты того, что считают прежние узлы (`NodeTests`), не трогались.
  Ревьюеру — подтвердить, что это не «правка ожиданий прежних тестов узлов».
- **Строки тестов этого изменения, записавшие прежнее поведение (группа 8).** Три утверждения тестов группы 2 и 4 описывали
  то, что владелец решил изменить, и без правки противоречат spec: в `NumberNodeTests` общий тест длины для `atr` проверял,
  что литерал `1` проходит, — теперь там `2` (для пяти остальных видов — по-прежнему `1`); тест
  `IndicatorNodeTests.Atr_with_a_length_of_one_has_no_value` подавал `1` литералом, а теперь подаёт параметром (сценарий
  «ATR с длиной один из параметра», ожидание «пусто на каждой свече» то же); в `SetupSignalTests.A_close_below_the_zone_is_a_breakout_down`
  убрана строка «`breakout-up` неизвестно» — то же утверждение с ответом «ложно» стало тестом «Зоны над открытием нет».
  Ожидания сценариев spec не менялись. Ревьюеру — подтвердить, что это не «правка ожиданий прежних тестов узлов».
- **OpenSpec CLI 2.x.** `openspec validate add-setup-strategies --strict` проходит в 1.15.0 (версия навыков проекта) и
  1.17.0, а в 2.1.1 падает на предупреждении «Requirement text is very long (>500 characters)» для изменённого
  требования «Итог идеи» (`specs/strategy-ideas`). Spec не правился.
- **`breakout`: сторону стопа выбирает направление свечи, а не состояние лонга (отступление от решения 5 design.md).**
  Состояние `breakout-up` на свече пробоя вниз бывает неизвестным, а не ложным: когда над `open` нет ни одной зоны,
  выход `above` узла `zones` отсутствует. Так в самом сценарии spec «Пробой вниз» (зона 100.0–100.3, `open` 100.4) —
  `select(when = breakout-up)` дал бы отсутствующий стоп и отказ `plan`, а spec требует стоп от `high`. В каталоге нет
  узла, превращающего неизвестное логическое в ложь. Поэтому у `breakout` `when` = `close > open`: свеча пробоя вверх
  закрывается выше открытия (`close ≥ above + запас`, `above ≥ open`), пробоя вниз — ниже. Нужно подтверждение владельца
  или правка design.md.
  **Закрыто (8.3):** условие с зоной ложно без зоны (`is-true`), `when` узла `select` снова читает `breakout-up`.
- **`false-breakout`: шорт без зоны снизу.** Здесь `select` берёт состояние `false-breakout-long`, как в решении 5:
  простого признака стороны по свече нет. Это состояние неизвестно, когда ни у одной зоны нижний край не ниже
  меньшего из `open` и `close`; шортовое событие на такой свече получит отказ `plan`. Лонговое событие не страдает
  (его состояние истинно).
  **Закрыто (8.3):** лонг без зоны снизу ложен, шорт получает свой стоп — сценарий «Шорт без зоны снизу».
- **Неизвестное вместо ложного.** Условия с зонами (`breakout-*`, `false-breakout-*`) неизвестны, когда нужной зоны
  нет, условие `quiet-volume` — когда за `wait` свечей не было тихой свечи. Заявки тогда нет, как велит «Событие
  сетапа», но и следующая свеча с истинным условием не даст события: `first-time` ждёт известной лжи. Сценарий spec
  «Закрытие под зоной» ложен в тестах потому, что ниже есть зона 98.6; без неё условие было бы неизвестным, а сценарий
  «Срок ожидания вышел» проверен как «заявки нет».
  **Закрыто (8.3) для условий с зонами;** `quiet-volume` решение 11 не трогает и остаётся как было («Срок ожидания вышел» — заявки нет).
