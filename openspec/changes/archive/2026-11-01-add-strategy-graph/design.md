# Design

## Context

Мотивация — см. `proposal.md`, требования — `specs/strategy-graph`, `specs/strategy-library`,
`specs/strategy-execution`. Термины — в `CONTEXT.md` («Стратегия», «Параметр стратегии», «Узел», «Простой узел»,
«Составной узел», «Библиотека узлов», «Бот»).

Текущее состояние: в `backend/src` есть только область `MarketData` — слои `Domain` → `Application` →
`Infrastructure` → `Presentation`, CQRS на MediatR, PostgreSQL через Dapper и FluentMigrator. Репозитории открывают
своё соединение на вызов, транзакций и unit of work нет. Пользователей и авторизации нет.

Ограничения проекта: деньги, цены и объёмы — только `decimal`; время — UTC `DateTimeOffset`; исполнение
детерминировано и без заглядывания вперёд; новая логика — строго TDD, без кода, которого не требует тест; новые
внешние зависимости — только через дизайн (здесь их нет).

## Goals / Non-Goals

**Goals:**

- Один формат графа для стратегии и составного узла, который бэктест (фича 2) и бот (фичи 4–5) исполняют без
  изменений.
- Интерпретатор — чистая доменная логика без I/O: проверяется unit-тестами на эталонных последовательностях событий.
- Инвариант «всё сохранённое валидно» держит одна доменная модель, а не проверки в контроллерах.

**Non-Goals:**

- Симуляция исполнения ордеров, комиссии, PnL, округление до шага цены и лота — фича 2.
- Отправка команд на биржу, сверка с биржей, отказ биржи в ордере — фича 5.
- HTTP-эндпоинт для запуска исполнения: в этой фиче исполнение вызывают только тесты.
- Масштабирование библиотеки на много пользователей (см. решение 6).

## Decisions

### 1. Решения из обсуждения с владельцем

Зафиксированы в интервью перед этим изменением:

- Бот исполняет стратегию из дизайнера, а не встроенный тип бота. Стратегия не привязана к инструменту и интервалу:
  это поля бота и бэктеста. Стратегии на нескольких инструментах не входят в первую версию.
- Стратегия задаётся визуальным графом. Формат проектируется с нуля; ProfitGraph — только справочник. Отклонены: код
  на C# (не дизайнер), конфиг из правил, перенос формата ProfitGraph (блоки с проводами событий и lowering в граф
  примитивов).
- Внешний вид — как в Unreal Blueprints, но без exec-проводов. Варианты «блоки с проводами событий» и «чистый поток
  данных без составных узлов» владелец счёл сложными для понимания: петли «докупка → отмена → продажа» и плотные схемы.
- Сложность прячется в составные узлы: библиотека содержит простые, встроенные составные и пользовательские составные
  узлы. Пользовательские узлы используются по ссылке, правятся всегда, правка доходит до всех мест использования,
  включая будущих работающих ботов. Отклонены копия при вставке и неизменяемость используемого узла.
- Правка пользовательского узла, ломающая хотя бы одно место использования, не сохраняется. Отклонены «сохранить и
  пометить стратегию сломанной» (у сломанной стратегии без версий нечего исполнять, бот только остановился бы) и
  «последний исправный снимок» (фактически версии).
- Встроенные составные узлы не правятся пользователем, их можно клонировать. Стратегию с ошибками сохранить нельзя.
- Версии стратегий отложены до бэктеста (фича 2): там они, если понадобятся, станут историей снимков раскрытого графа,
  на которую ссылаются бэктесты и ордера, а боты по-прежнему следуют последней правке.
- Эталонные стратегии: EMA, EMA Short, DCA (по времени, без выхода), Ladder (как в `profit-fox-old`). Без плеча,
  funding и ликвидаций.

### 2. Направление стратегии вместо объявления категорий

Стратегия объявляет направление `long` или `short`; поддерживаемые категории выводятся из него: `long` — `spot` и
`linear`, `short` — только `linear`. Направление же ограничивает ордера: у лонга продажа только уменьшает позицию, у
шорта — покупка (спек `strategy-execution`, «Направление ограничивает ордера»).

- Почему: из графа нельзя надёжно вывести, откроет ли продажа шорт — это зависит от позиции во время исполнения.
  Направление делает это статическим свойством, которое проверяется при создании бота или бэктеста.
- Отклонено: список категорий, объявляемый вручную, — он мог бы противоречить логике графа; разворот позиции в одной
  стратегии — ни одной эталонной стратегии не нужен.
- Уточнено при ревью: владелец принял направление вместо списка категорий; термин «Стратегия» в `CONTEXT.md`
  обновлён.

### 3. Модель графа: только провода данных, пересчёт на каждом событии

Граф — направленный ациклический граф узлов с типизированными пинами (`number` — `decimal`, `boolean`, `duration` —
`TimeSpan`). Провод несёт одно значение от выхода ко входу. На каждом событии интерпретатор вычисляет все узлы в
топологическом порядке; при равенстве порядок задаёт путь узла (ординальное сравнение строк), поэтому он стабилен.

Значение может отсутствовать (`Absent`): до первой свечи, пока EMA не набрала истории, без позиции, при делении на
ноль. Арифметика с `Absent` даёт `Absent`, сравнение — `false`, логика получает только `boolean`. Так ни один узел не
бросает исключений на неполных данных, а «индикатор не готов» не нужно проверять в каждой стратегии.

Узлы с историей (EMA, пересечение) обновляют состояние только на закрытии бара; на событиях ордеров они выдают
последнее значение, а пересечение — `false` (сигнал живёт ровно одно событие закрытия бара). Это и есть правило no
look-ahead: на баре N узел видел только свечи до N.

Отклонено: exec-провода и узлы-события, как в UE и в ProfitGraph, — из них получались петли.

### 4. Узлы ордеров декларативные, позицию ведёт интерпретатор

Узлы ордеров не «делают действие», а описывают, какие ордера должны стоять:

- `market-order` (сторона, размер — объём или сумма): выдаёт рыночный ордер, когда `when` истинно и у узла нет
  незавершённого ордера.
- `close-position`: рыночный ордер в сторону выхода на весь объём позиции.
- `hold-limit` (сторона, цена, размер — объём или сумма): пока `when` истинно, у узла стоит ровно один лимитный ордер с
  этой ценой и неисполненным остатком, равным размеру. Несовпадение — отмена, а новый ордер ставится на событии
  подтверждения отмены. Ордер в статусе «отменяется» ещё может исполниться, и это исполнение учитывается.

Почему ставить новый ордер только после подтверждения отмены: на споте старый ордер держит баланс, и одновременная
постановка нового может упасть на нехватке средств. Цена — короткий промежуток без ордера в стакане.

Позицию (объём, вложенная сумма, средняя цена входа, цена и время последнего входа) ведёт интерпретатор по событиям
исполнения. Граф только читает её через узел `position`. Поэтому подмена графа на лету (правка узла у работающего бота
в фиче 5) не теряет состояние позиции.

Размер «суммой» у лимитки переводится в объём делением `amount / price` в `decimal` без округления; рыночный ордер на
сумму уходит командой с суммой. Округление до шага цены и лота — фича 2.

Уточнено после код-ревью: исполнение выхода сверх объёма позиции не уменьшает позицию ниже нуля, лишнее не учитывается.
Так бывает, когда два ордера выхода исполнились оба, потому что один из них ещё «отменялся» (стоп по рынку и лимитный
тейк). Цена или размер ордера, равные нулю или отрицательные, считаются отсутствующим значением: ордер не ставится, а
стоящий отменяется. Иначе Ladder с `priceDropForBuy` = 1 делил бы на нулевую цену докупки.

Событие исполнения несёт объём, цену, время и признак «ордер исполнен полностью»: завершение ордера определяет
источник событий (бэктест или биржа), а не сложение дробных объёмов. Отмена завершает и частично исполненный ордер.

### 5. Идентификаторы ордеров и порядок команд

Идентификатор ордера — `o-<n>`, где `n` — счётчик в состоянии исполнения. Команды одного события идут в порядке
вычисления узлов. Ни `Guid.NewGuid`, ни текущее время в исполнении не используются: требование детерминизма.

### 6. Библиотека — один агрегат с инвариантом «всё валидно»

`StrategyLibrary` — корень агрегата: пользовательские составные узлы и стратегии вместе с номером ревизии. Каждая
операция (создать, изменить, удалить стратегию; создать, изменить, удалить, клонировать узел) раскрывает и проверяет
затронутые графы: для правки узла — его самого и всех, кто ссылается на него напрямую или через другие узлы. Ошибка
бросает доменное исключение со списком ошибок или мест использования, и агрегат не меняется. Встроенные узлы приходят в
агрегат из кода и не правятся.

- Почему агрегат целиком: инвариант связывает разные графы (правка узла ломает чужую стратегию), и держать его в одном
  месте проще и проверяемо unit-тестами.
- Цена: на каждое сохранение загружается вся библиотека. Для одного владельца с десятками графов это миллисекунды;
  с появлением пользователей агрегат станет библиотекой одного пользователя.
- Отклонено: обратный индекс ссылок в БД и проверка в SQL — логика уходит из домена.

Конкурирующие сохранения (спек «Сохранённое всегда валидно») — оптимистично по ревизии: репозиторий в одной транзакции
выполняет `UPDATE strategy_library SET revision = revision + 1 WHERE revision = @expected` и записывает изменённый граф;
ноль обновлённых строк — конфликт, ничего не записано, ответ 409. Отклонены `SERIALIZABLE` (повторы на ложных
конфликтах) и advisory lock с перечитыванием внутри репозитория (проверка уехала бы в Infrastructure). Транзакция живёт
внутри одного метода репозитория, поэтому общий unit of work не нужен.

Доменных событий у агрегата нет: ни одному обработчику они пока не нужны. Поэтому unit of work и outbox в это
изменение не входят и уходят в первую фичу с событием и обработчиком (правило из памяти проекта).

### 7. Встроенные узлы в коде, в доменных объектах

Простые узлы — классы с описанием пинов и вычислением, собранные в каталог. Встроенные составные узлы («Пересечение
EMA» `ema-cross`, `ladder`, `dca`) — графы, построенные в коде из тех же доменных объектов, что и пользовательские.
Домен не знает JSON (правило `docs/conventions.md` о кодах на границах), поэтому определения не лежат JSON-ресурсами.
Тест проверяет, что каждый встроенный граф валиден.

Совместимая правка встроенного узла в деплое доходит до всех мест использования, как правка пользовательского.
Несовместимая выходит новым узлом с новым идентификатором, а старый остаётся (риск ниже).

Каталог простых узлов первой версии — ровно то, что нужно четырём эталонным стратегиям и их составным узлам:
`parameters`, `inputs`, `outputs`, `candle`, `position`, `ema`, `cross`, `add`, `subtract`, `multiply`, `divide`,
`compare` (операция `gt`, `ge`, `lt`, `le`; тип `number` или `duration`), `and`, `or`, `not`, `market-order`,
`close-position`, `hold-limit`. Новый узел добавляется вместе с тестом, которому он нужен.

### 8. Формат JSON

Один формат для API и для `jsonb` в БД. Уточнено при реализации: вместо отдельных DTO на каждой границе — один кодек
`Application/Strategies/StrategyJson`, который разбирает определение из `JsonElement` в домен с ошибками по путям и
пишет обратно; его используют и контроллеры (тело запроса — `JsonElement`), и репозиторий. Два набора DTO одного и того
же документа только дублировали бы друг друга. Коды видов узлов, типов, сторон и направлений — в
`Application/Strategies/StrategyCodes`, как `MarketDataCodes`. Пример — стратегия EMA:

```json
{
  "formatVersion": 1,
  "direction": "long",
  "parameters": [
    { "name": "fast", "type": "number", "default": 12, "min": 2, "max": 200, "integer": true },
    { "name": "slow", "type": "number", "default": 26, "min": 2, "max": 400, "integer": true },
    { "name": "amount", "type": "number", "default": 100, "min": 0 }
  ],
  "nodes": [
    { "id": "params", "kind": "parameters" },
    { "id": "candle", "kind": "candle" },
    { "id": "position", "kind": "position" },
    { "id": "cross", "kind": "composite", "ref": "ema-cross" },
    { "id": "flat", "kind": "not" },
    { "id": "entry", "kind": "and" },
    { "id": "buy", "kind": "market-order", "settings": { "side": "buy", "size": "amount" } },
    { "id": "exit", "kind": "close-position" }
  ],
  "wires": [
    { "from": "candle.close", "to": "cross.source" },
    { "from": "params.fast", "to": "cross.fast" },
    { "from": "params.slow", "to": "cross.slow" },
    { "from": "position.hasPosition", "to": "flat.value" },
    { "from": "cross.up", "to": "entry.a" },
    { "from": "flat.result", "to": "entry.b" },
    { "from": "entry.result", "to": "buy.when" },
    { "from": "params.amount", "to": "buy.size" },
    { "from": "cross.down", "to": "exit.when" }
  ],
  "layout": { "params": { "x": 0, "y": 0 } }
}
```

Значение неподключённого входа — `"inputs": { "period": 20 }` у узла. Составной узел добавляет `"inputs"` и
`"outputs"` — объявления пинов с типами. Ссылка на пользовательский узел — его `Guid` в `ref`, на встроенный —
строковый идентификатор. Путь ошибки — идентификаторы узлов через `/`, например `ladder1/mul2`, плюс пин или параметр.

### 9. HTTP API

| Метод и путь | Ответ |
|---|---|
| `GET /api/strategies` | 200, список: `id`, `name`, `direction` |
| `GET /api/strategies/{id}` | 200 с определением и `supportedCategories`; 404 |
| `POST /api/strategies` | 201 с `id`; 400 с ошибками проверки |
| `PUT /api/strategies/{id}` | 204; 400; 404; 409 при конфликте ревизии |
| `DELETE /api/strategies/{id}` | 204; 404 |
| `GET /api/strategy-nodes` | 200, каталог: `id`, `title`, `group` (`simple`, `builtIn`, `custom`), входы, выходы |
| `GET /api/strategy-nodes/{id}` | 200 с определением составного узла или описанием простого; 404 |
| `POST /api/strategy-nodes` | 201 с `id`; 400 |
| `PUT /api/strategy-nodes/{id}` | 204; 400; 404; 409 для встроенного узла, ломающей правки или конфликта ревизии |
| `DELETE /api/strategy-nodes/{id}` | 204; 404; 409 для встроенного или используемого узла |
| `POST /api/strategy-nodes/{id}/clone` | 201 с `id` клона; 404 |

Ошибки проверки — `ValidationProblemDetails`, ключ — путь ошибки (`graph.ladder1/mul2.b`). Конфликты — новый
`StateConflictException` в `Application/Exceptions` и `ProblemDetails` 409 с расширением `usages`: список мест
использования с их ошибками. Контроллеры ловят исключения так же, как `CandleImportsController`. Названия узлов в
каталоге — на русском: их покажет редактор.

### 10. Хранилище

Миграция `202611010002`: таблицы `strategy_library` (одна строка, `revision bigint`), `strategies` (`id uuid`, `name`,
`definition jsonb`, `created_at`, `updated_at`; направление — внутри `definition`) и `strategy_composite_nodes` (`id uuid`, `name`,
`definition jsonb`, `created_at`, `updated_at`). Время — из `TimeProvider`. Репозиторий `IStrategyLibraryRepository`
загружает библиотеку целиком и сохраняет одно изменение с проверкой ревизии; чтение одной стратегии или узла для `GET`
идёт отдельными запросами, без загрузки агрегата.

### 11. Раскладка по слоям

- `Domain/Entities/Strategies`: `StrategyLibrary`, `Strategy`, `CompositeNode`; `Enums`: `PinType`,
  `StrategyDirection`, `OrderSide`, `OrderSizeMode`.
- `Domain/ValueObjects/Strategies`: определение графа, узла, провода, параметра, пина, путь узла, значения узлов,
  события исполнения и команды.
- `Domain/Repositories/IStrategyLibraryRepository`.
- Новая папка `Domain/Services/Strategies` для логики без сущности: `Nodes` (каталог простых узлов), `BuiltIns`
  (встроенные составные узлы), `Validation` (раскрытие и проверка), `Execution` (`StrategyRun` — состояние и
  обработка событий). В `docs/conventions.md` такой папки нет; при реализации она добавляется туда с правилом: в
  `Services` — только логика без своего состояния в БД. Уточнено при ревью: владелец принял эту папку; отдельный
  проект движка (`ProfitFox.Engine`) пересмотреть в фиче 2, когда движок начнёт использовать бэктест. Отклонены
  раскладка по существующим папкам (движок смешался бы с данными графа) и папка фичи (ломает раскладку по типам).
- `Application/Strategies/Commands/...` и `Queries/...` на каждый эндпоинт, `StrategyCodes`, `StateConflictException`.
- `Infrastructure/Persistence/Postgres/Dapper/Repositories/Strategies` с `Contracts`, `Converters`, `Queries`.
- `Presentation/Controllers/StrategiesController`, `StrategyNodesController`, `Contracts/Strategies`.

### 12. Тесты

- Unit: каждый простой узел на эталонных значениях (EMA — на заранее посчитанном ряду), каждое правило проверки графа,
  раскрытие и рекурсия, операции `StrategyLibrary` и его инвариант, разбор кодов, `StrategyRun` на событиях.
- Эталонные стратегии — JSON-фикстуры в `Tests.Shared`. Unit-тесты разбирают их и прогоняют по эталонным
  последовательностям событий с заранее посчитанными командами; интеграционный тест сохраняет каждую через API.
- Integration: репозиторий в Testcontainers (сохранение и чтение без потери точности `decimal`, конфликт ревизии),
  эндпоинты через `ProfitFoxFactory`.

## Risks / Trade-offs

- [Изменение большое: формат, библиотека, API и интерпретатор] → задачи сгруппированы так, что «формат, проверка,
  библиотека, API» и «исполнение» можно выпустить двумя PR, если первый станет слишком большим для ревью.
- [Правка узла доходит до всех мест использования сразу] → в этой фиче ботов нет; подтверждение влияния на работающих
  ботов и момент подхвата правки решаются в фиче 5.
- [Несовместимая правка встроенного узла в деплое сломала бы сохранённые стратегии] → правило для разработчиков:
  встроенный узел меняется только совместимо, иначе выходит новым узлом; тест проверяет валидность встроенных графов,
  но не сохранённые стратегии в production.
- [Ограничение выхода объёмом позиции не учитывает другие незавершённые ордера выхода] → в эталонных стратегиях один
  узел выхода на позицию; биржевые ограничения (reduce-only) — фича 5.
- [Деление `amount / price` даёт до 28 значащих цифр] → округление до шага лота — фича 2; в этой фиче команды не
  уходят на биржу.
- [Вся библиотека загружается на каждое сохранение] → приемлемо для одного владельца; пересмотреть с пользователями.
- [Промежуток без ордера между отменой и новой постановкой] → осознанная цена безопасности баланса (решение 4).

## Open Questions

- Событие по ордеру, которого исполнение не знает (повторное исполнение после полного, исполнение после подтверждённой
  отмены), сейчас бросает исключение. Игнорировать такое событие или сообщать о нём, решается в фиче 5, где события
  приходят с биржи.
- После частичного исполнения у `hold-limit` неисполненный остаток меньше размера, поэтому ордер отменяется и ставится
  заново на полный размер (так требует спек). Для докупки Ladder это значит покупку больше `limitPerOrder` за шаг, пока
  её не ограничит `limitDeposit`. Подтвердить с владельцем до фичи 2.
- Известные неточности сообщений, на поведение не влияют: ошибка параметра и ошибка узла с тем же именем получают один
  ключ `graph.<имя>`; цепочка рекурсии записана идентификаторами узлов, а не их именами; в перечень узлов цикла могут
  попасть узлы между двумя циклами.

## Migration Plan

Миграция только добавляет таблицы и строку `strategy_library` с ревизией `0`; существующие данные не меняются. Откат —
предыдущая версия сервиса, которая новые таблицы не читает. Production-сервер это изменение не затрагивает до отдельного
деплоя.
