# Design

## Context

Сейчас (v8, e405faa):

- `GetIdeasQueryHandler` читает все идеи окна (`IIdeaRepository.GetRecentAsync`), фильтрует их по сетапу, ТФ, типу, стороне
  и категории, строит `IdeaView` с корзинами и долями и отдаёт весь список, упорядоченный `ByExpectancy`.
- `GetMarketQueryHandler` отдаёт весь снимок (`IMarketSnapshotRepository.GetAllAsync`) с сетапами пар.
- Сохранённые фильтры, сортировки, числа категорий и чипов, а также счётчик редактора считает браузер:
  - `saved-filters/model/apply.ts`: `matchesIdea`, `matchesMarketRow`;
  - `ideas/model/sort.ts`, `market/model/sorting.ts`;
  - `market/model/rows.ts`, `market/model/setups.ts`.
- Сервер знает каталог полей фильтров (`SavedFilterFields`) и разбирает условия при сохранении (`SavedFilterRules.Parse`),
  но сами фильтры не применяет. Комментарий `SavedFilter` так и говорит: «the browser applies it».
- Ожидание и вероятность идеи не хранятся: их даёт корзина при чтении (`IdeaView.Of`).

Почему меняем — см. proposal.md.

## Goals / Non-Goals

**Goals:**

- Ни один запрос экранов «Идеи» и «Рынок» не возвращает полный список идей или полный снимок.
- Сохранённые фильтры и сортировки работают как сейчас; правила живут в одном месте, на сервере.
- Порядок строк детерминирован: одинаковые данные дают одинаковые страницы.

**Non-Goals:**

- Хранить ожидание и вероятность в базе и фильтровать в SQL.
- Кешировать прочитанное между запросами.
- Курсорное листание и бесконечная прокрутка.

## Decisions

### 1. Фильтр, сортировка и страница — в памяти обработчика, не в SQL

Обработчик читает то же, что сейчас:
- идеи окна, корзины версии движка;
- снимок рынка — для «Рынка» всегда, для «Идей» только при сохранённом фильтре с условием на метрику рынка.

Затем он фильтрует, сортирует и режет страницу в памяти.

Альтернатива — SQL с `LIMIT/OFFSET`. Ожидание, вероятность и «выше базовой» считаются из корзин при чтении, поэтому SQL
пришлось бы либо дублировать их расчёт, либо хранить их в идее и обновлять при каждом пересчёте корзин. Сейчас уже
читается всё окно, так что объём чтения из базы не растёт. Уходит только передача и разбор JSON в браузере, а это и
была проблема.

Порог для пересмотра: время обработчика `GET /api/ideas` на проде больше 300 мс на p95. Тогда отдельным изменением идём
в SQL или в кеш.

### 2. Проверка сохранённого фильтра — чистая функция в Application

`Application/SavedFilters/SavedFilterMatch` с двумя функциями:

- `Pair(conditions, row, setups)` — для «Рынка», пропускает условия на поля идеи;
- `Idea(conditions, view, row)` — для «Идей», `row` равен `null`, если пары нет в снимке.

Правила перенесены из `apply.ts` один к одному:
- метрика с `null` не проходит;
- сетап рынка — на любом ТФ;
- поле выбора — `=` своего кода;
- вероятность — только при достаточной корзине;
- «выше базовой» — нижняя граница интервала больше базовой линии.

Функции работают в Application, а не в Domain, потому что им нужен `IdeaView` (корзина, доли, базовая линия), а он
живёт в Application. Тесты переносят примеры из `apply.test.ts` в NUnit с теми же входами.

### 3. Порядок строк — чистые функции рядом с запросами

`Application/Ideas/IdeaOrder` и `Application/Market/MarketOrder`: колонка и направление дают упорядоченную
последовательность. Пустое значение всегда в конце, при равенстве действует общий хвост порядка:

- идеи: ожидание по убыванию, затем `FiredAt` от новых к старым, затем `Id`;
- рынок: категория, затем символ.

Хвост делает порядок полным, поэтому страница не зависит от порядка строк из базы.

Сетап, тип и сторона идеи сортируются по порядку перечисления, совпадающему со списками экрана, а не по русским
названиям. Сервер не знает названий, а алфавит «Импульс / Падение / Ранний…» владельцу ничего не даёт. Это изменение
требования «Сортировка списка идей» записано в дельте спеки. Символ сравнивается ординально, как сейчас `<` в TS.

Коды колонок — те же, что сейчас в `ideaSortColumns` и `sortColumns` фронта. Они становятся строками API и разбираются в
Application, как остальные коды.

### 4. Общий тип страницы

`Application/Paging/PageRequest` (номер, размер) и `Page<T>` (строки, номер, размер, всего). Есть и проверка запроса:
размер только 50, 100 или 200, номер от 1. Номер за концом даёт последнюю страницу, при пустом результате — первую. Так
экран после обновления, когда идей стало меньше, получает непустую страницу без второго запроса, а номер в ответе
говорит ему, куда перейти.

Ответы `IdeasPageResponse` и `MarketResponse` содержат `items`, `page`, `pageSize` и `total`. `MarketResponse` содержит
также `pairs` (весь снимок), `categories` и `setups` (числа чипов и «Все»).

### 5. Сохранённый фильтр в запросе — по id

Экран передаёт `savedFilter=<id>`, обработчик читает фильтр из `ISavedFilterRepository`. Фильтра нет — ошибка валидации
по `savedFilter`. Браузер и так снимает запомненный фильтр, которого нет в списке, поэтому ошибку увидит только тот,
кто удалил фильтр в другой вкладке. Передавать условия в каждом запросе опроса не нужно.

### 6. Счётчик редактора — `POST /api/saved-filters/fit`

Тело — `{ conditions }` в той же форме, что у сохранения. Условия разбирает `SavedFilterRules`: из `Parse` выносится
разбор условий, чтобы `fit` проверял их тем же кодом, без требования имени, места и хотя бы одного условия. Ответ —
`{ pairs, ideas }`.

Это `POST`, потому что условия — структура, а в адресе ей не место. Запрос только читает. Браузер шлёт только готовые
условия (`readyConditions`, как сейчас) и не чаще одного раза за паузу в 300 мс.

### 7. Фронт

`ideasQuery` и `marketQuery` получают объект запроса: фильтры, сохранённый фильтр, сортировку, страницу и размер. Ключ
запроса содержит его целиком, `placeholderData: keepPreviousData` оставляет старую страницу на время загрузки новой.

Общий компонент `shared/ui/Pager`: «‹ ›», «N из M», «1–50 из N» и выбор размера.

Номер страницы хранится в `?page=` маршрутов `/ideas` и `/market` (`validateSearch`, число от 1, иначе 1). Смена
выбора делает `navigate({ search: { page: undefined } })`. Если номер в ответе отличается от адреса, адрес заменяется
(`replace: true`).

Размер страницы добавляется в `ideas/model/choice.ts` и `market/model/choice.ts`. Поиск «Рынка» уходит в запрос через
задержку 300 мс.

Из `model` уходят `apply.ts` (проверки), `sort.ts` и `sorting.ts` (сортировки), `categoryOptions`, `filterRows`,
`setupOptions` и `filterBySetup`. Остаются коды колонок и тексты.

## Risks / Trade-offs

- [Разбор 16 500 идей и корзин на каждый запрос раз в 15 секунд] → так уже есть сейчас. Порог пересмотра указан в
  решении 1, проверяем после выкатки по логам запросов.
- [Правила фильтра на сервере расходятся со старыми из TS] → перед удалением TS-тестов их примеры переносятся в NUnit.
  Плюс e2e, где один фильтр с условием рынка и условием идеи проверяется на обоих экранах.
- [Строки на странице меняются между опросами] → принято владельцем. Полный порядок (решение 3) убирает хотя бы
  перестановки при равных значениях.
- [Изменение формы `/api/ideas` и `/api/market`] → web и API выкатываются одной версией. Окно, когда старый web
  обращается к новому API, длится секунды перезапуска, и на ошибку экран отвечает своим текстом.

## Migration Plan

Миграций базы нет. Выкатка — обычный `deploy N`. Откат — `deploy` прошлой версии: формат базы не меняется.
