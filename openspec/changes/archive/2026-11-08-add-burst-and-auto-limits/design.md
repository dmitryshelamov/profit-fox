# Design

## Context

Мотивация — в proposal.md. Как устроено сейчас (`main` 06cfd7e):

- `LiveIdeas.Minute` собирает идеи минуты всех пар в `created` и отдаёт их `LiveAutos.RunAsync(end, born, births, …)`.
  `LiveAutos.TakeAsync` идёт по автоматам по месту в списке, внутри — по идеям в порядке рождения: условия
  (`AutoConditions.Match`), затем `AutoBudget.IsFull` (полный автомат молча пропускает), для «С деньгами» — заявка
  `IdeaAutoEntry` с номером идеи `fired`, для «Без денег» — `PaperEntry.Check` и `PaperFill.Open`; отказы —
  `IdeaAutoRefusal` по одному на идею и автомат (уникальный индекс `idea_id, auto_id`), с причинами и
  `RefusalDetail(Actual, Limit, Holder)`.
- Обещание: `IdeaView.Of(born, buckets, fees)` даёт корзину и `Shares.NetRiskReward`; `IdeaOrder.ByExpectancy` уже
  сортирует представления по матожиданию корзины (идеи без корзины последними). Матожидание корзины — в R после
  комиссий (`CaseResult.R`).
- Признаки: `IdeaFeatures(DayDrop, BtcDrop, HighFunding)` считаются из чисел сигнала и идеи при чтении
  (`IdeaFeatures.Of`), уровень корзины в `CalibrationCalculator` — struct целиком; калибровка строит строки по
  `Enum.GetValues<IdeaFeature>()`. `IdeaOutcomes.WalkAsync` получает поток сигналов по ключу и берёт `signal.Features`.
- `IdeaAutoConditions` с тремя `FeatureCondition`; `idea_autos` хранит их текстом; форма — `autoForm.ts`, подписи —
  `labels.ts`, подробности отказов — `refusal.ts`.
- Замеры прода 2026-11-08 (`ideas` за 7 дней): разных пар стороны на ТФ в минуту, p50 / p90: 5m 27/64, 15m 11/28, 1h 3/8,
  4h 1/3; `paper-test` открывал до 22 лонгов за минуту.

## Goals / Non-Goals

**Goals:**

- Всплеск считается одинаково у живой идеи и у кейса прогона из одних данных — сигналов минуты, без заглядывания вперёд
  и без новой версии правил.
- Один порядок идей минуты для учебных и денежных автоматов; лимиты — чистые функции над сделками автомата.
- Отказы по лимитам видны в журнале, но не раздувают его.

**Non-Goals:**

- Квоты по сетапу и ТФ, разнесение бюджета во времени (отложены до итогов журнала).
- Значки корзин по часовым кластерам (отдельное изменение модели).
- Перенос признаков в числа идей и значки (прежнее правило решения 4 `add-idea-features`).

## Decisions

### 1. Всплеск — число разных пар стороны на ТФ в минуту, порог по ТФ

`IdeaFeatures(bool DayDrop, bool BtcDrop, bool HighFunding, bool Burst)`; `IdeaFeatures.Of(pairChange, btcChange,
funding, int? burstPairs, Interval interval)`: `Burst` — `burstPairs ≥ BurstThreshold(interval)`, `null` → нет.
`IdeaFeatures.BurstThreshold`: 5m 60, 15m 25, 1h 8, 4h 4 (около p90 прода; константы в домене с тестом на каждый ТФ).
Считаются разные пары, у которых в минуту есть хотя бы один сигнал той же стороны на том же ТФ, своя пара включена; типы
одной пары не умножают счёт. `IdeaFeature.Burst` с кодом `burst`; уровень — 16 сочетаний, машинерия подкорзин не
меняется.

Отвергнуто: сырое число идей минуты (структурное: 99,9 % идей в минутах с ≥ 5); один порог на все ТФ (распределения
различаются на порядок); доля от числа пар списка (список меняется, а порог должен быть воспроизводим на истории).

### 2. Живая идея хранит число пар, кейс прогона считает его при чтении

- `Idea.BurstPairs` (`int?`): `LiveIdeas.Minute` после обхода всех пар считает по `created` число разных инструментов на
  каждую пару (сторона, ТФ) и кладёт в идеи минуты до `autos.RunAsync` и `ideas.SaveAsync`; колонка `ideas.burst_pairs
  integer NULL`, у идей до выкатки — `NULL` → нет. Идеи, созданные при прогреве пары, считают только идеи своей минуты из
  `created`, как все остальные.
- `IdeaSignal.BurstPairs` не хранится: `IIdeaSignalRepository.CountPairsByMinuteAsync(version, from)` даёт
  `(fired_at, side, interval) → count(distinct symbol)` одним запросом группировки (`idea_cases`, те же 180 дней, что
  поток статистики); `IdeaStatistics.WalkAsync` читает словарь до прохода и передаёт в `IdeaOutcomes.WalkAsync` функцию
  `burstOf(signal)`, из которой строится `IdeaFeatures` кейса. Пока прогон версии не дошёл до части пар, счёт неполный и
  растёт с каждым пересчётом (сценарий «Прогон пополняет минуту»); после прогона он точен. Уточнено при реализации:
  считаются разные `(category, symbol)`, как у живых идей, где linear и spot одной монеты — две пары; словарь читает только
  полный пересчёт статистики, пересчёт одного тип × ТФ пишет лишь корзины, а их признаки не делят; запрос идёт с таймаутом
  10 минут вместо 30 секунд по умолчанию.

Отвергнуто: колонка `burst_pairs` у `idea_cases` (прогон идёт по парам, число известно только когда все пары минуты
пройдены — пришлось бы дописывать задним числом); новая версия правил (двое суток прогона ради числа, которое целиком
выводится из уже записанных сигналов).

### 3. Порядок идей минуты и лимиты — чистая функция

`Services/IdeaAutos/AutoMinutePlan`: по автомату, списку `(Idea, IdeaView)` подходящих идей, его открытым сделкам (учебным и
реальным) и `AutoLimits(MaxPerMinutePerSide, MaxOpenPerSide)` даёт порядок идей (`IdeaOrder.ByExpectancy`, при равенстве
`NetRiskReward` по убыванию) и для каждой — взять или пропустить с причиной `MinuteLimit` / `SideLimit`. Счётчик минуты
стороны растёт на каждую взятую идею (учебную сделку или заявку); открытые стороны — открытые сделки автомата этой стороны
плюс взятые в этой минуте. `LiveAutos.TakeAsync` идёт по этому порядку вместо `born`; `IdeaAutoEntry.Fired` получает
порядковый номер в плане, чтобы Worker брал заявки в том же порядке. Уточнено при реализации: `AutoMinutePlan` — небольшой
класс с состоянием на автомат и минуту (`Order` статический, `Allows` / `Took` / `Skips`), потому что взята ли идея, решают
проверки входа между вызовами; порядок проверок: условия → полный бюджет (молча) → лимиты → вход; при равном матожидании и
R:R идеи идут в порядке рождения, `IdeaOrder.ByExpectancy` не переиспользован, так как разбивает равенство по времени и id.

`IdeaAuto` получает `MaxPerMinutePerSide` и `MaxOpenPerSide` (`int?`, `null` — без лимита); `IdeaAutoConditions` —
`Burst` (`FeatureCondition`). Лимит открытых считает учебные и реальные сделки автомата, как бюджет (`AutoBudget.Used`).
Проверки автомата: лимит задан и меньше 1 — ошибка поля `maxPerMinutePerSide` / `maxOpenPerSide`.

Отвергнуто: лимиты в общих настройках торговли (владелец хочет сравнивать два автомата рядом); лимит на заявки в Worker'е
(Worker видит заявки по одной, минуту целиком знает только сканер).

### 4. Один отказ на автомат, сторону и минуту

Пропущенные по лимиту идеи дают одну строку `IdeaAutoRefusal`: `idea_id` — первая пропущенная идея (уникальный индекс
`idea_id, auto_id` сохраняется), причина `MinuteLimit` или `SideLimit`, `RefusalDetail.Numbers(пропущено, лимит)`; пара,
сетап, ТФ, тип и сторона — первой идеи. Таблица и API отказов не меняются; фронт в `refusal.ts` показывает «пропущено N
при лимите M». Коды причин `minute_limit`, `side_limit`.

Отвергнуто: отказ на каждую идею (при сотне подходящих идей в минуту — сотни тысяч строк в день, журнал за 7 дней — миллион);
молча, как полный автомат (владелец просил видеть всплески в журнале).

### 5. Хранение и API

Миграция `202611080007`: `ideas.burst_pairs integer NULL`; `idea_autos.burst text NOT NULL DEFAULT 'any'`,
`max_per_minute_per_side integer NULL`, `max_open_per_side integer NULL`. `IdeaAutoBody` / `IdeaAutoResponse`: `burst`
как другие признаки, `maxPerMinutePerSide` и `maxOpenPerSide` целые или null. Ответы идей, сделок и журнала отдают
`burst` в списке признаков через `IdeaCodes.Codes`; у сделки флаг `burst boolean NOT NULL DEFAULT false` в `idea_trades`
и `idea_paper_trades`, копируется при создании, как три других.

### 6. Фронт

`ideaFeatures` получает четвёртый элемент: код `burst`, чип «⚡ всплеск», название «всплеск», подсказка «сработала вместе
с другими парами той же стороны на том же ТФ». Форма автомата: четвёртый переключатель и секция «Лимиты» с двумя числовыми
полями (пусто — без лимита, подсказки «например 2» и «например 5»); строка условий в списке: «с/без ⚡ всплеск»,
«≤ 2/мин на сторону», «≤ 5 на сторону». Пояснение «С признаками» на «Калибровке» называет четыре признака и порог
всплеска по ТФ.

## Risks / Trade-offs

- [Уровней 16 вместо 8, подкорзины тоньше] → подтягивание к корзине уже есть; сравнение моделей покажет, стало ли хуже;
  решение о переносе признаков в числа по-прежнему только по правилу Брайера.
- [Счёт пар прогона неполон, пока прогон идёт] → задокументировано сценарием; калибровка «После изменения правил» на
  живых идеях точна с первой минуты.
- [Запрос группировки по 180 дням сигналов раз в час] → одна группировка по `(fired_at, side, interval)` с
  `count(distinct symbol)`; на проде ~20–60 M строк версии — десятки секунд, в полосе статистики, которая и так идёт
  минуты; при росте — материализация в таблицу отдельным изменением.
- [Ранжирование концентрирует сделки в лучшей корзине] → ожидаемо и проверяемо журналом; квоты по корзине отложены до
  доказательства вреда.
- [Денежный автомат: порядок заявок и лимит на сторону] → заявки одной минуты нумеруются по плану, Worker берёт их по
  очереди; лимит открытых стороны проверяется в сканере по открытым на начало минуты и взятым в ней — сделка, которую
  Worker не смог открыть, в счёт не идёт до следующей минуты, это в безопасную сторону.
- [Агрегированный отказ ссылается на одну идею] → подробность даёт число пропущенных; какие именно идеи пропущены, журнал
  не хранит — принято ради его размера.

## Migration Plan

1. Миграция `202611080007`: колонки с умолчаниями; старые автоматы — `any` и без лимитов, старые идеи и сделки — без
   всплеска.
2. Выкатка образов: сканер считает всплеск у идей со следующей минуты, статистика при следующем пересчёте — у кейсов;
   прогона нет.
3. Откат: прежний образ, колонки остаются и не мешают.
