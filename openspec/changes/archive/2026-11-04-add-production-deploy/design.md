# Design

## Context

- Образы есть у Worker'а (`backend/src/ProfitFox.Worker/Dockerfile`), сканера и веба (`frontend/Dockerfile`, Caddy
  проксирует `/api` на `api:8080`). У API образа нет. API применяет миграции при старте и отвечает на
  `/openapi/v1.json`; так его готовность уже проверяют e2e.
- Нужные на проде настройки задаются переменными окружения: `ConnectionStrings__MarketData`,
  `ExchangeAccounts__MasterKey` (API и торгующий Worker), `Trading__Enabled=true` (Worker), `DOTNET_ENVIRONMENT` /
  `ASPNETCORE_ENVIRONMENT=Production`. Сканеру мастер-ключ не нужен.
- Проверки: `ci.yml` идёт на каждый push в `main`. `frontend.yml` и `e2e.yml` идут только при изменениях в своих путях,
  поэтому у коммита их может не быть.
- Репозиторий публичный (решено оставить так). soyo-01 (`192.168.8.111`) — прод, Docker пуст, у `soyo` есть группа
  `docker`, `sudo` только у владельца. soyo-03 (`192.168.8.142`) — машина выкатки: из неё виден soyo-01 по SSH,
  runner'а нет. Обе машины в одной локальной сети и выходят в интернет через провайдера в РФ.
- Из сетей РФ часть адресов `api.nuget.org` блокируется на TLS: TCP-соединение открывается, а рукопожатие TLS виснет.
  .NET не переключается на другой адрес, если TCP открылся, поэтому `dotnet restore` падает через раз. Тот же риск у
  npm и `mcr.microsoft.com`. Локально это обходится VPN, на машинах в локальной сети VPN нет.
- На сервере Docker ротирует логи (10 МБ × 3) и включён `live-restore`.

## Goals / Non-Goals

**Goals:**

- Выкатка одной кнопкой после мержа: ничего не собирается на проде и нет ручных шагов на сервере.
- Даже если runner на soyo-03 захвачен чужим кодом, он может только выкатить уже существующий коммит `main`.
- Версии нумеруются по порядку (1, 2, 3…): по номеру видно, что новее, и откат — это та же выкатка с другим номером.
- Сборка образов не зависит от блокировок в сети РФ.

**Non-Goals:**

- Нулевой простой. На время выкатки Worker и сканер остановлены, а API перезапускается: это секунды или минуты. Боты
  после выкатки продолжаются по сверке с биржей.
- Бэкапы базы, мониторинг, HTTPS, доступ из интернета, Worker на soyo-03.

## Decisions

### 1. Образ API

`backend/src/ProfitFox.Presentation/Dockerfile` сделан по образцу Worker'а: контекст `backend/`, `dotnet publish` в SDK,
запуск в `aspnet:10.0`. Порт оставлен по умолчанию образа, `8080`, — этого и ждёт Caddyfile веба.

### 2. Номер версии, образы и теги

Версия — целое число `N`, общее для всех четырёх образов одной сборки. Номер хранится в git-теге `v<N>` на коммите
`main`, так что связь «номер → коммит» видна в GitHub и её может проверить сервер. Образы называются
`ghcr.io/dmitryshelamov/profit-fox-{api,worker,scanner,web}:<N>`. SHA коммита записан в метку
`org.opencontainers.image.revision`. Плавающих тегов (`latest`, `main`) нет: прод всегда называет точную версию, и откат
однозначен.

Номер выдаёт джоба `build` (решение 5). Если у коммита уже есть тег `v*`, используется он, поэтому пересборка коммита
номер не меняет. Иначе берётся наибольший `v<N>` в репозитории плюс 1 (первый — `v1`), тег создаётся и пушится до сборки
образов. Альтернатива — `run_number` workflow. Она отвергнута: номера шли бы с пропусками, а связь с коммитом была бы
видна только в Actions.

Пакеты GHCR делаются **публичными**. Код и так открыт, секретов в образах нет. Зато soyo-01 скачивает образы без входа в
реестр, и токен GHCR на сервере не хранится. Альтернатива — приватные пакеты и PAT `read:packages` на soyo-01: это ещё
один секрет без выигрыша.

### 3. `docker-compose.prod.yml`

Один проект `profit-fox`. Версия задаётся переменной `PROFITFOX_VERSION`, секреты подставляются из `--env-file
~/profit-fox/.env.prod`. Каждый сервис получает только свои переменные: мастер-ключ видят `api` и `worker`, но не
`scanner`.

| Сервис | Образ | Важное |
|---|---|---|
| `db` | `timescale/timescaledb:2.30.2-pg17` (как в dev и тестах) | том `profit-fox-db`, healthcheck `pg_isready`, порт не публикуется |
| `api` | `profit-fox-api` | `127.0.0.1:8080:8080` только для проверки готовности с хоста |
| `worker` | `profit-fox-worker` | `Trading__Enabled=true`, `stop_grace_period: 30s`, чтобы отпустить аренды ботов |
| `scanner` | `profit-fox-scanner` | без мастер-ключа |
| `web` | `profit-fox-web` | `80:80` |

У всех сервисов `restart: unless-stopped`. Строка подключения собирается в compose из `PROFITFOX_DB_PASSWORD`: хост
`db`, база и пользователь `profitfox`. Пароль генерируется в hex, чтобы не экранировать символы.

`.env.prod` (права `600`, его заводят один раз, в git его нет):

```text
PROFITFOX_DB_PASSWORD=<64 hex>
PROFITFOX_MASTER_KEY=<32 байта в base64>
```

Порт базы закрыт. Внешний Worker появится отдельным изменением и тогда откроет порт для локальной сети. Раздел README «On
production, Postgres listens on the LAN interface» переписывается.

### 4. Скрипт выкатки на сервере — единственное, что умеет ключ деплоя

`deploy/deploy.sh` из репозитория владелец ставит в `~/profit-fox/deploy.sh`. В `authorized_keys` на soyo-01 ключ
деплоя записан так:

```text
from="192.168.8.142",command="/home/soyo/profit-fox/deploy.sh",no-pty,no-port-forwarding,no-agent-forwarding,no-X11-forwarding,no-user-rc ssh-ed25519 AAAA… profit-fox-deploy
```

Скрипт принимает только `SSH_ORIGINAL_COMMAND` вида `deploy <N> <версия протокола>`, где `N` — положительное целое без
ведущих нулей. Версия протокола — число, записанное в самом скрипте и в `deploy.yml`. Если они расходятся, значит, новый
`deploy.sh` не перенесли на сервер, и скрипт отказывает. Разбор команды вынесен в функцию, у неё есть тест
`deploy/deploy.test.sh`. Этот тест и `shellcheck` запускаются в `ci.yml`. Скрипт делает следующее:

1. Через публичный API GitHub находит коммит тега `v<N>` (`git/ref/tags/v<N>`) и проверяет, что этот коммит есть в
   `main` (`compare/main...<commit>`, статус `behind` или `identical`). Если тега нет или коммит не из `main` —
   отказывает, ничего не меняя на проде. Уточнено при реализации: `compare/<commit>...main` для предка `main` отвечает
   `ahead`, а не `behind`, поэтому база и голова сравнения поменяны местами (проверено на API: предок `main` —
   `behind`, сам `main` — `identical`, голова смерженного squash'ем PR — `diverged`).
2. Скачивает `docker-compose.prod.yml` коммита тега `v<N>` с `raw.githubusercontent.com` в
   `~/profit-fox/releases/<N>/`. Файл берётся по SHA, проверенному на шаге 1, а не по имени тега: тег не может
   сдвинуться между проверкой и скачиванием.
3. Выполняет `pull` всех образов версии `<N>` и проверяет, что метка `org.opencontainers.image.revision` у каждого
   образа равна коммиту тега. Образ, подменённый под существующим номером, так не пройдёт.
4. Делает `stop worker scanner`, затем `up -d db` и ждёт healthcheck.
5. Делает `up -d api` и до 120 с ждёт ответа `http://127.0.0.1:8080/openapi/v1.json`. Если ответа нет — код ошибки,
   Worker и сканер остаются остановленными (спека «Порядок обновления»).
6. Делает `up -d worker scanner web`, записывает номер в `~/profit-fox/current`, удаляет образы старше 7 дней, которыми
   никто не пользуется: их можно скачать заново из GHCR.

Почему так, а не «runner копирует compose и скрипт по scp»: всё, что runner передал бы на сервер, было бы под его
контролем. Тогда захваченный runner получил бы shell на проде. Сейчас вход ограничен коммитами `main`, а `main` защищён
PR и squash-мержем. Цена: изменения самого `deploy.sh` владелец переносит на сервер вручную, это шаг в README. Сам
`docker-compose.prod.yml` обновляется автоматически вместе с версией.

Повторная выкатка того же номера проходит те же шаги: `pull` ничего не скачивает, Worker и сканер коротко перезапускаются,
итоговое состояние то же.

Скрипту на сервере нужны `curl`, `jq` и `docker`: ответы API GitHub разбираются через `jq`. Если `jq` на soyo-01 нет,
его ставит владелец (`sudo apt-get install -y jq`), это шаг в README.

### 5. Workflow `deploy.yml`

Триггеры:

- `workflow_run` workflow `CI`, `types: [completed]`, `branches: [main]`. Внутри проверяется
  `workflow_run.event == 'push'` и `head_repository.full_name == github.repository`. Иначе прогон CI на PR из форка
  тоже запустил бы деплой.
- `workflow_dispatch` со входом `version` (номер) — для отката и для повторной выкатки. Сборки он не делает: номер
  должен уже быть, и образы этого номера должны быть в GHCR.

Джобы:

1. **`checks`** (`ubuntu-latest`, `actions: read`, только для `workflow_run`). Для коммита берёт прогоны CI, Frontend и
   E2E. CI обязан быть `success`. Frontend и E2E, если они есть, ждутся до завершения и тоже обязаны быть `success`.
   Если их нет, значит, они не нужны этому коммиту по путям. Ждать безопасно: прогоны создаются при push, задолго до
   конца CI.
2. **`build`** (`ubuntu-latest`, `contents: write`, `packages: write`, только для `workflow_run`). Делает
   checkout коммита и выдаёт ему номер (решение 2): берёт существующий тег `v*` коммита или создаёт и пушит `v<max+1>`.
   Затем входит в GHCR через `GITHUB_TOKEN`, собирает и публикует 4 образа `:<N>` с меткой `revision`. Образы, которые
   уже есть в GHCR, не пересобираются. Номер передаётся дальше как output джобы.
3. **`images`** (`ubuntu-latest`, `packages: read`). Получает номер из `build` или из входа `version`, входит в GHCR
   через `GITHUB_TOKEN` и проверяет, что все 4 образа `:<N>` опубликованы. Идёт для обоих триггеров и передаёт номер в
   `deploy` как output.
4. **`deploy`** (`[self-hosted, soyo-03]`, `environment: production`). Получает номер из `images` и выполняет только
   `ssh -i ~/.ssh/profit-fox-deploy soyo@192.168.8.111 deploy <N> <протокол>`. Ключ и `known_hosts` лежат в домашней
   папке runner'а на soyo-03, в GitHub их нет. На soyo-03 ничего не собирается и не скачивается: runner'у не нужны ни
   Docker, ни токен GHCR.

Пересмотрено после реализации: сначала `build` шёл на soyo-03, но из сети РФ `dotnet restore` в Dockerfile падает на
заблокированных адресах nuget.org (Context). Поэтому сборка и проверка образов идут на облачном раннере вне РФ, а
soyo-03 нужен только для SSH внутри локальной сети. Отвергнутые альтернативы: закрепить рабочий адрес через
`--add-host` — CDN меняет адреса, и следующий тоже могут заблокировать; прокси или VPN за границей для soyo-03 — ещё
одна машина и ещё один секрет; кеш пакетов — не спасает первую загрузку и новые пакеты. Цена: у облачного раннера нет
кеша слоёв между прогонами, каждая сборка идёт с нуля (минуты). Для публичного репозитория минуты облачных раннеров
бесплатны.

`permissions: contents: read` по умолчанию, права выдаются по джобам. Очереди заданы на джобах, без
`cancel-in-progress`: `build` в группе `deploy-build`, `deploy` в группе `deploy-production`. Одна выкатка не обрывает
другую, и две сборки не выдают номер одновременно. Уточнено при реализации: очередь на весь workflow держала бы
сборку следующего коммита, пока предыдущая выкатка ждёт Approve, поэтому она разделена по джобам. Push тега, который уже
существует, отклоняется. Тогда сборка падает и не выкатывает ничего, чтобы два коммита не получили один номер.

Environment `production`: обязательный reviewer — владелец, ветки развёртывания — только `main`. Настройки репозитория:
Actions → «Require approval for all external contributors» для workflow из форков.

### 6. Runner на soyo-03

Runner уровня репозитория, метка `soyo-03`, работает службой от `soyo` и выполняет только джобу `deploy`. В группу
`docker` `soyo` не добавляется: Docker runner'у не нужен, и root на soyo-03 через него не получить. На машине нет
секретов, кроме ключа деплоя, который умеет только выкатить коммит `main`. Сборка образов и обычный CI (`ci`,
`frontend`, `e2e`) идут на облачных раннерах: проверки PR из форков никогда не попадают на soyo-03.

### 7. Что делает владелец, а что агент

С `sudo` или в настройках GitHub работает владелец по готовым командам из README:

- runner службой на soyo-03;
- Environment `production`;
- одобрение workflow из форков;
- правило защиты тегов `v*`: их нельзя удалять и перезаписывать;
- публичность пакетов GHCR после первой публикации.

Без `sudo` и только с разрешения владельца на эти шаги агент может:

- создать ключ деплоя на soyo-03;
- добавить строку в `authorized_keys` на soyo-01;
- создать `.env.prod`, сгенерировав секреты прямо на сервере (`openssl rand`), не выводя их;
- поставить `deploy.sh`.

## Risks / Trade-offs

- [Захваченный runner на публичном репозитории] → обычный CI на нём не идёт. Деплой запускается только из `main` и
  после Approve. Ключ деплоя умеет только `deploy <N>` с тегом `v<N>` на коммите `main`. Workflow из форков требуют одобрения.
- [Approve на чужом PR по ошибке] → даже тогда до прода доходит только коммит `main`: сервер сам проверяет через GitHub,
  что тег `v<N>` стоит на коммите `main`, а метка образов совпадает с этим коммитом.
- [Тег `v<N>` передвинули на другой коммит] → сервер всё равно примет только коммит из `main`. Двигать теги может лишь
  тот, у кого есть права на запись в репозиторий. Запрет на удаление и перезапись `v*` ставится правилом защиты тегов в
  GitHub (шаг владельца).
- [Номер выдан, а сборка образов упала] → тег `v<N>` остаётся, образов `:<N>` нет. Повторный запуск сборки того же
  коммита возьмёт тот же номер, а выкатка без образов отказывает на проверке в `deploy`.
- [GitHub или GHCR недоступны с soyo-01 во время выкатки, в том числе из-за блокировок в РФ] → выкатка падает до
  остановки Worker'а: проверка, скачивание compose и `pull` образов идут до `stop`.
- [Миграция упала] → API не ответил, Worker и сканер остановлены, боты стоят до исправления. Боты на бирже защищены
  только тем, что выставлено на бирже. Бэкапа нет, это осознанный выбор владельца. → Откат на прошлый номер работает,
  только если миграция не успела частично изменить схему. FluentMigrator применяет каждую миграцию в транзакции.
- [Изменённый `deploy.sh` забыли перенести на сервер] → в нём хранится версия протокола. Workflow передаёт ожидаемую
  версию, и при несовпадении скрипт отказывает с понятной ошибкой.
- [Перезапуск Worker'а посреди сделки] → время выкатки выбирает владелец кнопкой Approve. Аренды отпускаются при
  остановке, и новый Worker сразу подхватывает ботов.
- [Сканер на старте грузит историю ~210 тыс. запросов с IP прода] → у сканера свои лимиты и пауза на 10006 и 403.
  Других процессов, которые ходят в Bybit с soyo-01, кроме profit-fox нет.

## Migration Plan

1. Владелец выполняет шаги на машинах и в GitHub (решение 7). Агент делает свою часть с отдельного разрешения.
2. Мерж PR этого изменения в `main` запускает CI, затем `deploy.yml`. Коммит получает `v1`, на облачном раннере
   собираются образы `:1`, и workflow ждёт Approve.
3. Владелец делает пакеты GHCR публичными и жмёт Approve. Первая выкатка создаёт базу, API применяет все миграции,
   сканер начинает загрузку истории.
4. Проверка: `http://192.168.8.111/market` открывается, `~/profit-fox/current` равен `1`. Повторная выкатка `1` через
   `workflow_dispatch` проходит.
5. Откат: `workflow_dispatch` с предыдущим номером.
