# Proposal

## Why

У profit-fox нет прода: soyo-01 пуст, `docker-compose.prod.yml` и образа API нет, сканер рынка из `add-market-scanner`
ждёт выкатки, чтобы начать копить историю за 90 дней. Нужен повторяемый деплой одной кнопкой: собирать не на сервере
с живой торговлей и не открывать сервер в интернет. Сборка не должна зависеть от блокировок РКН: из сетей РФ часть
адресов nuget.org не отвечает по TLS.

## What Changes

- **Образ API**: новый `backend/src/ProfitFox.Presentation/Dockerfile`, как у Worker'а и сканера.
- **Прод на soyo-01**: `docker-compose.prod.yml` в репозитории — проект `profit-fox` из сервисов `db` (TimescaleDB, порт
  наружу не публикуется), `api`, `worker` (торгует), `scanner` и `web` (Caddy, порт 80 в локальной сети). Образы берутся
  из GHCR по номеру версии. Секретов в файле нет: они в `~/profit-fox/.env.prod` на сервере (права `600`), его заводит
  владелец.
- **Номерные версии**: каждая новая сборка коммита `main` получает следующий номер `N` (1, 2, 3…) — git-тег `v<N>` на
  коммите и образы `profit-fox-*:<N>`. Пересборка того же коммита номер не меняет.
- **Скрипт деплоя на сервере** `deploy/deploy.sh` (`deploy <N>`): скачивает образы версии, останавливает Worker и
  сканер, обновляет API, ждёт, пока он ответит (миграции применены), затем поднимает Worker, сканер и веб той же версии.
  Тот же скрипт откатывает: это деплой предыдущего номера.
- **Сборка и выкатка в GitHub Actions** — новый workflow `deploy.yml`: после зелёных CI, Frontend и E2E коммита в
  `main` облачный runner (`ubuntu-latest`) присваивает ему номер, собирает образы `api`, `worker`, `scanner`, `web` и
  кладёт их в `ghcr.io/dmitryshelamov/profit-fox-*:<N>`. Выкатку на soyo-01 по SSH делает self-hosted runner soyo-03
  (метка `soyo-03`) после Approve в Environment `production`. Можно запустить вручную на выбранный номер — так делается
  откат.
- **Защита публичного репозитория**: deploy-workflow не запускается из `pull_request`; Environment `production` только
  для `main` и с обязательным подтверждением владельца; workflow из форков требуют одобрения владельца; ключ деплоя на
  soyo-01 работает только с адреса soyo-03 и только как `deploy.sh` с номером версии (принудительная команда, без shell
  и проброса портов).
- **Документация**: раздел о проде и деплое в `README.md` и пошаговая настройка машин (runner на soyo-03, ключ деплоя,
  `.env.prod`, вход в GHCR на soyo-01) — шаги с `sudo` выполняет владелец.

## Capabilities

### New Capabilities

- `production-deploy`: как версия profit-fox попадает на прод — номерные сборки образов из `main`, подтверждение
  владельца, порядок обновления сервисов с миграциями, откат по номеру, где лежат секреты и откуда доступен прод.

### Modified Capabilities

Нет: поведение API, Worker'а, сканера и веб-приложения не меняется, меняется только то, как они запускаются на проде.

## Impact

- Новые файлы: `backend/src/ProfitFox.Presentation/Dockerfile`, `docker-compose.prod.yml`, `deploy/deploy.sh`,
  `.github/workflows/deploy.yml`; правки `README.md` (раздел о проде; сейчас там написано, что Postgres прода слушает
  LAN — теперь порт закрыт, пока нет Worker'а на другой машине).
- Машины: на soyo-03 — GitHub Actions runner службой, без Docker; на soyo-01 — ключ деплоя в
  `authorized_keys`, `.env.prod`, вход в GHCR. Требуют `sudo` или доступа к настройкам GitHub — их делает владелец.
- GitHub: Environment `production`, настройка одобрения workflow из форков, пакеты GHCR `profit-fox-*`, теги `v<N>`.
- Вне изменения: бэкапы базы (отдельное изменение), Worker на soyo-03, HTTPS и доступ из интернета (придут с
  авторизацией), мониторинг и алерты.
