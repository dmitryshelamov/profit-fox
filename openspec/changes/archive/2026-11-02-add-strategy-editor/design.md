# Design

## Context

Мотивация — `proposal.md`; требования — `specs/strategy-editor`, `specs/web-application`, `specs/strategy-library`.
Термины — в `CONTEXT.md` («Стратегия», «Узел», «Составной узел», «Библиотека узлов», «Черновик»).

Текущее состояние:

- Фронтенда нет. API — контроллеры на `ProfitFox.Presentation`, OpenAPI-документ на `/openapi/v1.json`, Swagger UI.
  Образа API пока тоже нет: в репозитории есть только `Dockerfile` Worker'а.
- Стратегии и узлы правятся через `POST/PUT /api/strategies` и `/api/strategy-nodes`. Тело — имя и определение
  (`StrategyJson`, один кодек для API и `jsonb`). Ошибки проверки — `ValidationProblemDetails` с ключами-путями
  (`graph.buy.when`). Конфликты — `ProblemDetails` 409 с расширениями `usages` (места использования с ошибками) и
  `bots` (боты с ошибками).
- Конфликт ревизии возникает, только если другое сохранение успело между загрузкой библиотеки и записью внутри одного
  запроса. Клиент ревизию не передаёт.
- Каталог `GET /api/strategy-nodes` отдаёт id, название, группу, входы и выходы, но не настройки узлов (`side`, `size`,
  `operation`, `type`). Пины узлов `parameters`, `inputs` и `outputs` зависят от объявлений стратегии или составного
  узла (`PinContext`), а входы `compare` — от его настройки `type`.
- В ProfitGraph (`~/RiderProjects/ProfitGraph/frontend`) есть рабочий редактор на том же стеке: холст на весь экран и
  плавающие панели (`StrategyEditorPage`), сквозные тесты Playwright против настоящего API.
- Макеты согласованы с владельцем в Penpot (файл «New File 1», страница «Макеты редактора»): списки, редактор и его
  состояния, составной узел, встроенный узел.

## Goals / Non-Goals

**Goals:**

- Правила проверки остаются в одном месте — в домене. Фронтенд их не повторяет и показывает ответы сервера.
- Логика редактора, которую можно ошибиться написать (определение ↔ холст, пины, совместимость типов, разбор путей
  ошибок, черновики), — чистые функции TypeScript, проверенные unit-тестами по TDD. React-компоненты тонкие.
- Определение, открытое и сохранённое без правок, остаётся тем же JSON, кроме раскладки.

**Non-Goals:**

- Повторение проверки графа на TypeScript, офлайн-режим.
- Обнаружение правки той же стратегии в другой вкладке: см. риски.
- Мобильная вёрстка: редактор рассчитан на экран ноутбука и больше.

## Decisions

### 1. Решения из обсуждения с владельцем

Зафиксированы в интервью и при согласовании макетов:

- Скоуп — стратегии и составные узлы. Экраны ботов и бэктестов — отдельное изменение 3.1. Отклонены «только
  стратегии» (узлы правились бы JSON'ом) и «всё сразу» (изменение вдвое больше).
- Стек как в ProfitGraph, папка `frontend/` в корне. Отклонены урезанный стек и Blazor.
- Проверка — эндпоинтом без сохранения (решение 4). Отклонены «только при сохранении» (ошибки видны слишком поздно) и
  копия правил на TypeScript (два источника правил расходятся).
- Черновик в браузере (решение 6). Отклонены черновики на сервере (новая сущность, миграция, API) и «только
  предупреждение при уходе».
- Раздача — образ `web` на Caddy, пока HTTP (решение 8). HTTPS с `tls internal` придёт вместе с авторизацией: сейчас он
  ничего не защищает, а корневой сертификат пришлось бы ставить на каждое устройство. Отклонены раздача из API (сборка
  .NET зависела бы от node) и «только локально».
- Тесты как в ProfitGraph: проверки фронтенда и сквозные тесты Playwright в CI (решение 10).
- Раскладка редактора — холст на весь экран с плавающими панелями, как в ProfitGraph и Miro (решение 3). Первый
  вариант с постоянными колонками каталога и свойств владелец отклонил: мало места для графа.

### 2. Структура `frontend/`

Повторяет ProfitGraph:

- `src/app` — роутер (TanStack Router), провайдеры (TanStack Query).
- `src/pages` — экраны: `strategies` (список), `strategy-editor`, `nodes` (список), `node-editor`.
- `src/modules/graph-editor`:
  - `model` — чистые функции: определение ↔ узлы и провода холста, пины узла из каталога и объявлений, совместимость
    типов, раскладка путей ошибок по узлам и пинам, сравнение черновика с сохранённым;
  - `ui` — холст `@xyflow/react`, узел, провод, палитра, карточки свойств;
  - `drafts` — хранение черновиков.
- `src/shared/api` — клиент `openapi-fetch` и типы из OpenAPI-документа. Типы генерирует `npm run generate:api` из
  запущенного API и коммитятся в `schema.d.ts`: сборка и typecheck не требуют запущенного API.

Версии зависимостей фиксируются точно, как в ProfitGraph (`package-lock.json`, без `^`). Node 24 — версия `engines` и
образа сборки. Правила раскладки и тестов фронтенда добавляются разделом в `docs/conventions.md`.

### 3. Экраны и маршруты

| Путь | Экран |
|---|---|
| `/` | переход на `/strategies` |
| `/strategies` | список стратегий, включая черновики новых стратегий |
| `/strategies/new/$draftId` | редактор новой стратегии (только черновик) |
| `/strategies/$id` | редактор стратегии |
| `/nodes` | список составных узлов |
| `/nodes/$id` | редактор составного узла: пользовательского — на правку, встроенного — на чтение |

Списки — в обычной оболочке с верхней навигацией. Редактор — на весь экран, без навигации приложения. Поверх холста
плавающие панели:

- слева сверху — «‹ Назад», название, направление и статус;
- справа сверху — «Ошибки» со счётчиком, «Параметры» или «Входы и выходы», «Отменить правки», «Сохранить»;
- слева — столбец инструментов: палитра узлов, поиск узла на холсте, «вписать в экран»;
- снизу — легенда типов и зум.

Свойства выбранного узла, параметры и ошибки — плавающие карточки справа, открываются по необходимости.

Отклонено: отдельная страница свойств и модальные окна для правки узла — они прячут граф, а связь «узел ↔ его
настройки» должна быть видна.

### 4. Проверка без сохранения — запрос, а не команда

Новые запросы `ValidateStrategyQuery` и `ValidateNodeQuery` в `Application/Strategies/Queries` выполняют ту же операцию
`StrategyLibrary`, что и сохранение: создание или изменение стратегии, создание или изменение узла. Операция идёт на
загруженном агрегате, но `SaveAsync` не вызывается. Исключения проверки становятся результатом:

```json
{ "errors": { "graph.buy.when": ["..."] }, "usages": [ ... ], "bots": [ ... ] }
```

`usages` и `bots` — в той же форме, что расширения ответа 409.

| Метод и путь | Ответ |
|---|---|
| `POST /api/strategies/validate` | 200 с результатом проверки новой стратегии |
| `POST /api/strategies/{id}/validate` | 200 с результатом проверки правки; 404 |
| `POST /api/strategy-nodes/validate` | 200 с результатом проверки нового узла |
| `POST /api/strategy-nodes/{id}/validate` | 200 с результатом проверки правки; 404; 409 для встроенного узла |

Тело — то же `DefinitionBody`, что у `POST/PUT`. Ошибки разбора определения (неизвестный код, не тот тип JSON) — тоже
`errors` в ответе 200, как ошибки графа. 400 остаётся только для запроса без тела или без обязательных полей, в том
числе с пустым именем — как у `POST/PUT`. Редактор разбирает `errors` ответа 400 так же, как ответа 200.

- Почему запрос с ответом 200: проверка — это чтение. По `docs/conventions.md` запрос может вернуть результат с
  ошибками. Ответ всегда разбирается одним кодом, а консоль браузера не заполняют 400 на каждую паузу в правке.
- Почему та же операция агрегата: проверка обязана совпадать с сохранением, иначе редактор разрешит сохранить то, что
  сервер отклонит. Ломающая правка узла и правка, ломающая бота, видны ещё до нажатия «Сохранить».
- Отклонено: флаг `?dryRun=true` у `POST/PUT` (смешивает запись и чтение в одном эндпоинте) и отдельный сервис
  проверки рядом с агрегатом (второй путь к тем же правилам).

Редактор вызывает проверку через 400 мс после последней правки. Предыдущий запрос отменяется (`AbortController`).
Ответ применяется, только если он относится к последней правке: у каждого запроса есть номер правки. «Сохранить»
недоступно, пока не пришёл ответ на последнюю правку или в нём есть ошибки.

### 5. Настройки узлов в каталоге

Запись каталога получает `settings`: список `{ name, values, default, inputs? }`. `inputs` есть только у настройки,
которая задаёт тип входов (`compare.type` → `a`, `b`). Узлы с настройками:

- `compare`: `operation` (`gt`, `ge`, `lt`, `le`), `type` (`number`, `duration`);
- `market-order` и `hold-limit`: `side` (`buy`, `sell`), `size` (`quantity`, `amount`).

Описание настроек — одна таблица в `Application/Strategies` рядом с `StrategyJson`. Разбор настроек в `StrategyJson` и
каталог читают её, поэтому новая настройка не может появиться в одном месте и забыться в другом. Значение по умолчанию
— то, что редактор ставит новому узлу; для `type` оно совпадает с умолчанием разбора (`number`). Названия значений
для интерфейса («Покупка», «на сумму») живут во фронтенде рядом с остальным русским текстом интерфейса.

Пины узлов `parameters`, `inputs` и `outputs` редактор строит сам: выходы `parameters` — параметры стратегии, выходы
`inputs` и входы `outputs` — объявления составного узла. Это прямое отображение объявлений, а не правило проверки.
Отклонено: запрос пинов у сервера на каждую правку объявлений — задержка в простом действии.

### 6. Черновики

Черновик — запись в `localStorage`:

- ключи: `profit-fox:draft:strategy:<id>`, `profit-fox:draft:strategy-new:<draftId>`, `profit-fox:draft:node:<id>`;
- значение: `{ savedAt, name, definition }`, `savedAt` — UTC ISO-строка.

Черновик пишется после каждой правки (с задержкой 300 мс) и удаляется после успешного сохранения или при «Отбросить».

- При открытии редактор сравнивает черновик с сохранённым определением без учёта `layout`. Если они различаются, он
  предлагает «Восстановить» или «Отбросить» и показывает, сколько узлов и проводов добавлено или удалено. Если не
  различаются, черновик удаляется молча.
- Каждое обращение к `localStorage` обёрнуто в `try/catch`. Без хранилища (приватный режим, запрет) редактор работает
  без черновиков и показывает это в статусе.
- Уход с несохранёнными правками: `beforeunload` для закрытия вкладки и блокировщик роутера для переходов внутри
  приложения.
- Новая стратегия получает `draftId` (`crypto.randomUUID()`) и живёт только черновиком. Первое успешное сохранение
  (`POST`) удаляет черновик и переводит адрес на `/strategies/$id`. Список стратегий показывает черновики новых
  стратегий отдельной пометкой.

Отклонено: `IndexedDB` — граф стратегии занимает килобайты, асинхронный API ничего не даёт.

### 7. Исходы сохранения

Сохранение отправляет `POST` или `PUT` с именем и определением, включая `layout`. Ответ разбирается так:

- 201/204 — успех, черновик удаляется, данные стратегии или каталога перечитываются;
- 400 — ошибки показываются как ошибки проверки. Это возможно, только если библиотека изменилась между проверкой и
  сохранением;
- 409 с непустым `usages` — диалог «Правка не сохранена» со списком мест использования, их ошибками и ссылками
  «Открыть»;
- 409 с непустым `bots` — тот же диалог со списком ботов и их ошибками;
- 409 без `usages` и `bots` — конфликт ревизии: тост «Библиотеку изменили одновременно с сохранением» и повтор
  сохранения;
- остальное — тост с текстом ошибки.

Во всех случаях, кроме успеха, правки остаются в редакторе и в черновике.

### 8. Доставка: образ `web`

`frontend/Dockerfile`: `node:24-alpine` собирает приложение, `caddy:2.11-alpine` отдаёт `dist`. Рядом лежит
`frontend/Caddyfile`, по образцу `docker/Caddyfile` ProfitGraph, но без TLS:

- `:80`;
- `/api` и `/api/*` → `reverse_proxy {$PROFITFOX_API}`, по умолчанию `api:8080`;
- остальное — `try_files {path} /index.html`;
- `Cache-Control: public, max-age=31536000, immutable` для `/assets/*`, `no-cache` для остального.

Файлы лежат в `frontend/`, как `Dockerfile` Worker'а — в его проекте. Production-compose и образ API в изменение не
входят: подключение `web` к production — отдельный деплой владельца (`docker-compose.prod.yml` агент не трогает).

Локально — `npm run dev` (Vite, порт 5173) с прокси `/api` на `http://localhost:5242` (профиль `http` API). Адрес API
переопределяется переменной `PROFITFOX_API`. CORS в API не настраивается.

### 9. Тесты

- **Vitest, строго TDD** — модули `model` и `drafts`:
  - эталонные стратегии EMA, EMA Short, DCA, Ladder из `backend/tests/ProfitFox.Tests.Shared/Fixtures/Strategies`
    (читаются по относительному пути, без копий) проходят «определение → холст → определение» без изменений;
  - пины, совместимость типов, раскладка путей ошибок (`graph.ladder1/mul2.b` → узел `ladder1`), сравнение черновика.
- **Vitest и Testing Library** — компоненты с замоканным `fetch`: исходы сохранения из решения 7, недоступность
  сохранения, диалог черновика, встроенный узел только на чтение.
- **.NET unit и integration** — запросы проверки (каждый сценарий спеки `strategy-library`) и `settings` в каталоге,
  через `ProfitFoxFactory`.
- **Playwright**, по критериям приёмки:
  - сборка EMA с нуля и сохранение;
  - открытие четырёх эталонных стратегий;
  - ошибка на узле и блокировка сохранения;
  - восстановление черновика после перезагрузки;
  - ломающая правка составного узла;
  - клон встроенного узла;
  - обновление страницы редактора по прямой ссылке и запрос `/api` через адрес приложения.

  Тесты идут через образ `web`, а не через Vite. Тест правки, ломающей бота, сквозным не делается: создание бота
  требует правил инструмента с биржи; этот исход покрыт компонентным тестом.

### 10. CI и проверки перед коммитом

- `.github/workflows/frontend.yml` — при изменениях в `frontend/`: `npm ci`, lint, `format:check`, typecheck,
  `npm test`, build.
- `.github/workflows/e2e.yml` — при изменениях в `frontend/` или `backend/`:
  - TimescaleDB как service container, тот же образ, что в `docker-compose.yml`;
  - API через `dotnet run` в среде `Testing` на одноразовой базе со случайным именем, которую создаёт и удаляет
    `e2e/database.ts`;
  - образ `web` собирается и запускается с `--network host` и `PROFITFOX_API=127.0.0.1:<порт API>`;
  - Playwright с одним воркером и без повторов; при падении сохраняются trace и скриншоты.

  Worker не запускается: редактор с ним не работает.
- `.githooks/pre-commit` дополнительно запускает lint, `format:check` и typecheck фронтенда, если коммит трогает
  `frontend/`.
- `CLAUDE.md`: команды фронтенда и определение «задача готова» с проверками фронтенда.

## Risks / Trade-offs

- [Правка той же стратегии в двух вкладках молча перезаписывает: клиент не передаёт ревизию, сохраняется последняя
  запись] → владелец один, черновик у каждой вкладки свой. Передача ожидаемой ревизии (`If-Match`) — вместе с
  авторизацией и несколькими пользователями. Это поведение записано в спеке как «конфликт ревизии только одновременно
  с сохранением». Владелец подтвердил при ревью артефактов: оставить как есть.
- [Запрос проверки на каждую паузу загружает всю библиотеку] → для одного владельца это миллисекунды (design
  изменения 1, решение 6); задержка 400 мс и отмена прошлого запроса ограничивают частоту.
- [`schema.d.ts` отстанет от API] → typecheck и сквозные тесты ловят расхождения в используемых полях; правило
  «изменил контракт API — перегенерируй типы» записывается в `docs/conventions.md`.
- [Черновик живёт в одном браузере] → осознанный выбор владельца; сохранение на сервер остаётся основным путём.
- [Сквозные тесты — самая долгая и хрупкая часть CI] → только критерии приёмки, один воркер, trace при падении,
  запуск только при изменениях `frontend/` и `backend/`.
- [Холст на xyflow с сотнями узлов замедлится] → эталонные графы — десятки узлов; оптимизация отложена до реальных
  больших графов.

## Migration Plan

Миграций нет. Новые эндпоинты и поле `settings` только добавляют данные, существующие клиенты не ломаются. Откат —
предыдущая версия API и удаление образа `web`. Production не затрагивается, пока владелец не подключит образ `web` в
своём деплое.
