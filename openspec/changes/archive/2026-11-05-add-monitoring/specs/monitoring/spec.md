# Spec Delta

## Purpose

Стек мониторинга на soyo-03. Он принимает и хранит метрики сервисов прода и показывает их на дашбордах, чтобы владелец видел
нагрузку на Bybit относительно её лимитов до того, как биржа откажет или забанит IP.

## ADDED Requirements

### Requirement: Приём и хранение метрик на soyo-03

На soyo-03 SHALL работать Prometheus с приёмником OTLP и Grafana, источник данных которой — этот Prometheus. Метрики хранятся
не меньше 15 дней. Конфигурация стека (compose, настройки Prometheus, источник данных и дашборды Grafana) MUST храниться в
репозитории, а секреты стека — только на soyo-03.

#### Scenario: Стек поднимается из репозитория

- **WHEN** на soyo-03 в каталоге `deploy/monitoring/` из репозитория с `.env` сервера выполняется `docker compose up -d`
- **THEN** Prometheus принимает OTLP, а Grafana открывается с готовым источником данных и дашбордом «Bybit REST», без
  ручной настройки в интерфейсе

#### Scenario: Пароль Grafana

- **WHEN** проверяется репозиторий и лог запуска стека
- **THEN** пароля администратора Grafana нет ни в репозитории, ни в выводе запуска

### Requirement: Метрики прода приходят в мониторинг

Сервисы прода api, worker и scanner SHALL отправлять метрики в Prometheus на soyo-03. Порты на soyo-01 для этого MUST NOT
публиковаться.

#### Scenario: Метрики всех сервисов

- **WHEN** прод работает, и каждый сервис хотя бы раз обратился к Bybit REST
- **THEN** в Prometheus есть счётчик запросов к Bybit с именами сервисов `api`, `worker` и `scanner`

### Requirement: Доступ к мониторингу только из локальной сети

Grafana и Prometheus SHALL быть доступны только из локальной сети по адресу soyo-03. Вход в Grafana MUST требовать пароль
администратора; анонимный доступ выключен.

#### Scenario: Вход в Grafana

- **WHEN** владелец открывает Grafana на soyo-03 с машины локальной сети
- **THEN** Grafana просит логин и пароль и только после входа показывает дашборды

### Requirement: Дашборд «Bybit REST»: нагрузка на IP

Дашборд SHALL показывать сумму запросов к Bybit REST всех сервисов за каждые 5 с с линиями 300 (половина лимита) и 600
(лимит Bybit на IP). На этом же дашборде те же запросы показываются по сервисам и по эндпоинтам.

#### Scenario: Всплеск после рестарта Worker

- **WHEN** worker после рестарта восстанавливает ботов и за 5 с отправляет 350 запросов
- **THEN** на графике нагрузки на IP в этом месте точка выше линии 300

#### Scenario: Кто нагружает

- **WHEN** владелец смотрит разбивку запросов
- **THEN** он видит, сколько запросов за 5 с отправил каждый сервис и сколько пришлось на каждый эндпоинт

### Requirement: Дашборд «Bybit REST»: запас по аккаунту и отказы

Дашборд SHALL показывать для каждого эндпоинта с лимитом аккаунта наименьший остаток и его долю от лимита. Отдельно
показываются попытки с исходом `rate_limited` по сервисам и HTTP-кодам.

#### Scenario: Запас по ордерам

- **WHEN** за последние 5 с наименьший остаток `/v5/order/create` был 4 при лимите 10
- **THEN** дашборд показывает для `/v5/order/create` остаток 4, то есть 40% лимита

#### Scenario: Отказ из-за лимита

- **WHEN** Bybit ответил worker'у кодом 403
- **THEN** на панели отказов в этот момент видна попытка `worker` с кодом `403`
