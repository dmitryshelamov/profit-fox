# Design

## Context

Сейчас вся фоновая работа идёт в процессе API (`ProfitFox.Presentation`). Задачи загрузки и бэктесты попадают в
`Channel<Guid>` (`CandleImportQueue`, `BacktestQueue`) через порты `ICandleImportQueue` и `IBacktestQueue`, а
`CandleImportBackgroundService` и `BacktestBackgroundService` выполняют их по одной через `ISender.Send(Run*Command)`.
При запуске `CandleImportInitializationService` и `BacktestInitializationService` снова ставят незавершённое в очередь
и считают «перезапуск без продвижения» (`stalled_restarts`). Отмена бэктеста — один условный `UPDATE` статуса; прогон
видит её при следующем сохранении результатов (`SaveProgressAsync` пишет только в `Running`). Результаты хранятся с
ключом `(backtest_id, combination)`, и прогон пропускает уже посчитанные комбинации. Прогон бэктеста внутри
`RunBacktestCommandHandler` сам ждёт свою задачу загрузки, опрашивая её раз в секунду.

Мотивация — proposal.md, «Why». Справочно: в ProfitGraph (ADR 0011) задачи тоже лежат в базе и берутся через
`FOR UPDATE SKIP LOCKED`, но там допускается ровно один процесс с задачами, а аренды есть только у живых ботов.

## Goals / Non-Goals

**Goals:**

- Один и тот же Worker на одной или шести машинах работает по одним правилам; одна сетка считается всеми сразу.
- Остановка или падение любого Worker'а в любой момент не теряет сохранённое и не создаёт дублей.
- Результат бэктеста не зависит от числа Worker'ов, размера куска и того, какая сборка с той же версией движка считала
  кусок.

**Non-Goals:**

- Heartbeat, проверка здоровья и список Worker'ов, отображение «кто что считает».
- Освобождение аренды при штатной остановке: работа ждёт истечения аренды (до 30 секунд).
- Распределение бэктестов по машинам с учётом их мощности, приоритеты, справедливое деление между бэктестами.
- Общая таблица задач, как `background_jobs` в ProfitGraph: у бэктеста и задачи загрузки свои статусы и свои таблицы.

## Decisions

### 1. Отдельный проект `ProfitFox.Worker` на generic host

`ProfitFox.Worker` — консольный хост (`Host.CreateApplicationBuilder`) с Serilog из конфигурации, как в API.
`Program.Configure` вызывает `InfrastructureRegistrar.ConfigureWorker` (общие сервисы и фоновые сервисы Worker'а), API
вызывает `InfrastructureRegistrar.Configure` (общие сервисы и `StrategyVersionsInitializationService`), поэтому фоновые
сервисы в API не регистрируются, а шаг запуска версий стратегий и миграции остаются в API. MediatR регистрирует
обработчики Worker'а и в API, поэтому то, что они принимают (`WorkerSettings`, `WorkerIdentity`, `BacktestInputCache`),
регистрируется в обоих процессах; тестовые хосты проверяют, что каждый зарегистрированный сервис разрешается
(`ValidateOnBuild`), как это делает Development. Worker сохраняет статический логгер Serilog (`preserveStaticLogger`):
им `Main` пишет ошибку запуска, а Worker в процессе теста не перехватывает логгер API.

Отклонены: роль `worker` внутри бинарника API (на машинах Worker'ов поднимается ASP.NET и HTTP-порт без нужды);
роли по образцу ProfitGraph (`jobs`, `live`) — живого бота пока нет, а загрузки и бэктесты разводятся аренды, а не
роли.

### 2. Очередь — это строки в базе

Создание бэктеста и задачи загрузки только вставляет строку `Pending`. Порты `ICandleImportQueue` и `IBacktestQueue`,
их реализации на `Channel`, команды `RequeueInterruptedImports` и `RequeueInterruptedBacktests` и сервисы их запуска
удаляются. Worker опрашивает базу раз в `Worker:PollInterval`. Ручной повтор задачи загрузки только возвращает её в
`Pending`.

Отклонены: `LISTEN/NOTIFY` вместо опроса (быстрее реакция, но отдельное соединение и обработка разрывов; задержка до
секунды при работе в минуты не важна).

### 3. Аренда: владелец и срок в строке работы

У куска бэктеста и у задачи загрузки есть `lease_owner` (идентификатор процесса Worker'а — `Guid`, созданный при
запуске; в лог пишется вместе с именем машины) и `leased_until`. Захват — короткая транзакция с
`FOR UPDATE SKIP LOCKED`, которая ставит владельца и срок `now + Worker:LeaseDuration`. Продление раз в
`Worker:LeaseRenewal` — `UPDATE … WHERE lease_owner = @me`; если строка не обновилась, аренда потеряна, и Worker
отменяет токен этой работы. Каждая запись результата или прогресса тоже условна по `lease_owner = @me`, поэтому
Worker, потерявший аренду, ничего не сохраняет. Штатная остановка аренду не освобождает.

Время аренды берётся из `TimeProvider`, как всё время в проекте; интеграционные тесты сдвигают `FakeTimeProvider` и
так проверяют истечение. Часы машин синхронизирует NTP (на Ubuntu включён по умолчанию); расхождение в доли секунды
мало рядом с арендой 30 секунд.

Отклонены: часы базы (`now()` в SQL) — независимы от часов машин, но тесты тогда ждут реальное время вместо сдвига
`FakeTimeProvider`; advisory-блокировка на всё время работы — держит соединение минутами и теряется при обрыве
соединения без явного сигнала Worker'у.

### 4. Куски бэктеста

Новая таблица `backtest_chunks`: `backtest_id`, `number`, `first_combination`, `combinations`, `done`,
`lease_owner`, `leased_until`, `lost_leases`, `speed`; ключ `(backtest_id, number)`. Куски создаёт тот Worker, который
переводит бэктест из `LoadingCandles` в `Running`, в одной транзакции с переходом и условно по статусу
`LoadingCandles`: второй Worker, сделавший то же одновременно, ничего не меняет. Размер — `Worker:ChunkSize`
комбинаций (по умолчанию `100`), последний кусок короче.

Захват куска: самый старый `Running` бэктест версии движка Worker'а, его кусок с `done = false` и пустой или истёкшей
арендой, по `backtests.created_at`, затем по `number`. Внутри Worker'а кусок считается на `Backtests:MaxParallelism`
потоках тем же `Parallel.ForEachAsync`, что сейчас; результаты сохраняются пачками раз в секунду.

Сохранение пачки (`SaveProgressAsync`) в одной транзакции: вставляет результаты с `ON CONFLICT DO NOTHING`, прибавляет
к `backtests.calculated_combinations` число действительно вставленных строк, обновляет `speed` куска и
`backtests.speed` как сумму скоростей кусков с действующей арендой, сбрасывает `lost_leases` куска. Пишет только при
`Running` бэктеста и своей аренде куска. После последней пачки Worker отдельным оператором ставит куску `done = true` и снимает аренду, если она ещё его. Отдельным оператором
после фиксации Worker завершает бэктест: `UPDATE … SET status = 'Succeeded' WHERE status = 'Running' AND NOT EXISTS
(несданный кусок)`. Из двух Worker'ов, сдавших последние куски одновременно, хотя бы второй видит оба куска сданными.

Worker держит в памяти свечи и снимок стратегии последнего бэктеста, который считал: следующий кусок того же
бэктеста не читает свечи заново.

Отклонены: кусок под одной арендой со всей сеткой (одна сетка — одна машина); захват отдельных комбинаций без кусков
(запрос к базе на каждую комбинацию); куски, созданные при создании бэктеста в API (размер куска — настройка
Worker'а, а до догрузки свечей кускам нечего делать).

### 5. Догрузка свечей — шаг без аренды

`Pending` и `LoadingCandles` обрабатываются коротким шагом, который ничего не держит: Worker проверяет свечи периода и
обновляет прогресс загрузки; если свечей не хватает и задачи загрузки нет, создаёт её и записывает в бэктест одной
транзакцией и только при пустом `import_job_id`; если задача упала — бэктест `Failed`; если свечей хватает или задача
завершилась — переход в `Running` с кусками (решение 4). Если задача загрузки ещё идёт, Worker переходит к следующей
работе и вернётся к шагу на следующем опросе. Все записи условны по статусу, поэтому два Worker'а, сделавшие шаг
одновременно, дают тот же итог.

Порядок опроса бэктестов: перебор незавершённых бэктестов версии Worker'а от старых к новым до первой найденной работы
— шага загрузки или свободного куска. Поэтому один Worker досчитывает старый бэктест раньше нового, а свободный
Worker начинает новый, пока куски старого заняты.

Отклонены: держать аренду бэктеста, пока идёт загрузка (Worker простаивает, пока ждёт сеть); ждать загрузку внутри
прогона, как сейчас (с одним Worker'ом без отдельной полосы загрузок — взаимная блокировка).

### 6. Загрузки свечей — своя полоса и одна на всех

В каждом Worker'е две независимые полосы опроса: бэктесты и загрузки. Загрузка упирается в сеть, а не в процессор,
поэтому не занимает потоки бэктеста, и бэктест, ждущий свою загрузку, не блокирует её на одном Worker'е.

Захват загрузки — транзакция с `pg_advisory_xact_lock` на постоянный ключ: внутри неё Worker проверяет, что ни у одной
задачи нет действующей аренды, и берёт самую старую задачу `Pending` или `Running` с истёкшей арендой. Блокировка
держится только на время захвата, поэтому два Worker'а не возьмут две задачи одновременно. Машины выходят к Bybit
через один NAT, поэтому лимит у них общий, и «одна загрузка на всех» сохраняет нынешнюю нагрузку на Bybit.

Счётчик `stalled_restarts` задачи переименовывается в `lost_leases`: Worker прибавляет его при захвате истёкшей
аренды, если с прошлого захвата не сохранено ни одной свечи, и на третьем переводит задачу в `Failed`. Ручной повтор
обнуляет его, как сейчас.

Отклонены: роль `imports` только на одной машине (одна машина без неё стоит, если упала); глобальный ограничитель
частоты запросов к Bybit в базе (сложнее, а ускорения загрузок не нужно).

### 7. Счётчик потерянных аренд куска

`backtests.stalled_restarts` удаляется, вместо него `backtest_chunks.lost_leases`. Worker, захватывая кусок с
истёкшей арендой, прибавляет `lost_leases`; сохранённая пачка обнуляет его (решение 4). На третьем подряд Worker
переводит бэктест в `Failed` с причиной `Backtest.InterruptedChunk` («кусок трижды прерван без результата»). Так же,
как сейчас, правило ловит комбинацию, которая роняет процесс: без него каждый Worker падал бы на ней по очереди.

### 8. Версия движка

`EngineVersion.Current` — целая константа в `Domain/Services/Backtests`, начинается с `1`. Бэктест получает её при
создании (`backtests.engine_version`). Обработчики берут версию не из константы напрямую, а из singleton-записи
`EngineVersion` в DI со значением `EngineVersion.Current`: интеграционный тест подменяет её у одного `WorkerHost` и так
запускает Worker'ы двух версий в одном процессе. Worker берёт шаги загрузки и куски только бэктестов с
`engine_version = EngineVersion.Current`. На каждом опросе полосы бэктестов Worker одним оператором переводит
незавершённые бэктесты с `engine_version < EngineVersion.Current` в `Failed` с причиной
`Backtest.EngineVersionChanged`; бэктесты новее своей версии не трогает. API отвечает `409` на детали результата
бэктеста другой версии движка, потому что пересчитал бы их по другим правилам; список результатов отдаёт как есть.

Защита от «забыли поднять версию» — unit-тест на эталонных наборах `Fixtures/Backtests`: он прогоняет эталонные
бэктесты, считает SHA-256 от канонической записи всех их результатов и сверяет с последней записью
`Fixtures/Backtests/engine-versions.json` — списка пар «версия → отпечаток». Тест требует, чтобы версия последней
записи равнялась `EngineVersion.Current`, отпечаток совпадал, версии строго росли, а отпечатки не повторялись. Правка,
меняющая результаты, проходит только с новой записью и поднятой константой.

Отклонены: без проверки (две сборки во время раскатки смешивают результаты одной сетки, правило детерминизма
нарушается); закрепление бэктеста за сборкой (блокирует сетку при любом деплое, даже без изменения расчёта);
автоматический пересчёт бэктеста старой версии с нуля (молча стирает результаты).

### 9. Настройки Worker'а

Секция `Worker` в `appsettings.json` проекта Worker, record `WorkerSettings` в Application:

```json
"Worker": {
  "PollInterval": "00:00:01",
  "LeaseDuration": "00:00:30",
  "LeaseRenewal": "00:00:10",
  "ChunkSize": 100
}
```

Worker проверяет при запуске, что `LeaseRenewal` меньше `LeaseDuration`, иначе завершается с ошибкой уровня `Fatal`.
Число потоков машины — как сейчас, `Backtests:MaxParallelism`, задаётся переменной окружения
`Backtests__MaxParallelism` на каждой машине. Строка подключения — `ConnectionStrings:MarketData`, на машинах
Worker'ов из переменной окружения `ConnectionStrings__MarketData`.

### 10. Миграции и порядок деплоя

Миграцию выполняет только API. Миграция: `backtests.engine_version` (существующим — `1`), удаление
`backtests.stalled_restarts`, таблица `backtest_chunks`, `candle_import_jobs.lease_owner` и `leased_until`,
переименование `candle_import_jobs.stalled_restarts` в `lost_leases`. Бэктесты `Running` переводятся в
`LoadingCandles`: у них ещё нет кусков, и шаг загрузки (решение 5) создаст их, а посчитанные результаты прогон
пропустит. Задачи загрузки `Running` остаются `Running` с пустой арендой — первый Worker их перехватит.

### 11. Тесты

`Tests.Integration` получает `WorkerHost` — хост Worker'а с той же регистрацией, что в `ProfitFox.Worker`, на базе
теста, с `FakeBybitHandler` и общим `FakeTimeProvider` фабрики. `ProfitFoxFactory` по умолчанию запускает рядом один
`WorkerHost`, поэтому нынешние сценарии API не меняют смысла; `RunImports = false` заменяется на «без Worker'а».
Сценарии нескольких Worker'ов запускают два `WorkerHost` с разными идентификаторами процесса. Истечение аренды
проверяется сдвигом `FakeTimeProvider` дальше `LeaseDuration` при остановленном Worker'е. `RestartTests`
переписываются в тесты перехвата аренды.

### 12. Образ и compose

`backend/src/ProfitFox.Worker/Dockerfile` — многоэтапная сборка: образ SDK .NET 10 собирает и публикует, образ
ASP.NET Core runtime .NET 10 запускает: Infrastructure использует общую платформу ASP.NET Core. `docker-compose.worker.yml` в корне — один сервис `worker` с `restart: unless-stopped`,
строкой подключения и `Backtests__MaxParallelism` из `worker.env` рядом с файлом (`*.env` в `.gitignore`); отдельный
файл, а не `.env`, чтобы Worker не получал чужих переменных. На машине Worker'а:
клон репозитория и `docker compose -f docker-compose.worker.yml up -d --build`.

## Risks / Trade-offs

- [Postgres на `soyo-01` виден всей домашней сети] → `pg_hba` пускает только `192.168.8.0/24`, отдельный пароль из
  переменной окружения; это тот же уровень, что у API без авторизации.
- [Часы машин разошлись больше, чем на секунды] → аренда 30 секунд; NTP включён по умолчанию; при подозрении —
  `timedatectl` на машине.
- [Штатная остановка держит кусок до 30 секунд] → приемлемо для работы в минуты; освобождение при остановке можно
  добавить отдельно.
- [Шесть Worker'ов опрашивают базу каждую секунду] → запросы по индексам статуса, это единицы запросов в секунду.
- [API новее Worker'ов по версии движка: новые бэктесты ждут в `Pending`] → API и Worker'ы деплоятся из одного
  коммита, API первым.
- [Старый Worker после миграции не знает новых колонок] → Worker'ы останавливаются до деплоя API и запускаются после.
- [Бэктест, ждущий свою загрузку, пропускается на опросе, и более новый бэктест обгоняет его] → так задумано:
  свободные потоки не простаивают, пока идёт сеть.

## Migration Plan

1. Владелец открывает Postgres на `soyo-01` для `192.168.8.0/24` с паролем из переменной окружения (вне репозитория).
2. Остановить нынешний API и снять дамп базы (`pg_dump`); задеплоить новый API — он мигрирует базу.
3. Запустить Worker на `soyo-01`, затем на остальных машинах через `docker-compose.worker.yml`.
4. Откат: миграции только вперёд, а старый код читает удалённые колонки `stalled_restarts`. Откат — старый API и
   восстановление дампа из шага 2; работа, сделанная после деплоя, теряется.
