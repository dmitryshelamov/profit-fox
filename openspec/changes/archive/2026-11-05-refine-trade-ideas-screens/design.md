# Design

## Context

Экраны из `add-trade-ideas` (архив `2026-11-05-add-trade-ideas`) работают на проде с v6:

- `IdeasTable` показывает идеи в порядке ответа API, то есть по ожиданию.
- `PairIdeasList` показывает в карточке только R.
- Страница пары меняет `?idea=` и `?interval=` через `navigate` роутера TanStack. Роутер при каждой навигации сбрасывает
  прокрутку наверх.
- Цены приходят десятичными строками как есть. Лимит «Отката» округлён по шагу и несёт его знаки (`197.00`). Вход по
  рынку — это open свечи, у которого знаков столько, сколько дала биржа (`184.7`).
- Шаг цены хранится в `ideas.tick` (идея) и `scanner_pairs.tick_size` (пара), но в ответах API его нет.

## Goals / Non-Goals

**Goals:**

- четыре правки из proposal без изменения расчёта идей.

**Non-Goals:**

- сортировка на стороне API и сортировка в адресе страницы;
- деньги в блоке своей идеи;
- смена версии движка идей.

## Decisions

### 1. Сортировка в браузере

Список «Идеи» — это открытые идеи и закрытые за сутки, сотни строк, и все они уже в браузере. Поэтому сортировка идёт по
загруженному списку, функцией модели `sortIdeas(ideas, column, direction)` с unit-тестами. Выбранная колонка хранится в
состоянии страницы. По умолчанию — «Ожидание» по убыванию: это совпадает с порядком API.

- Пустые значения (нет корзины, «мало данных») — внизу при любом направлении. Иначе при сортировке по возрастанию верх
  списка займут идеи без данных.
- Сравнение десятичных строк — через `compareDecimals`, не через `Number`: точность цен и долей сохраняется.
- Сортировка устойчива: равные значения идут в порядке API.

Отклонено:

- **Сортировка в API.** Нужен ещё один параметр запроса и его валидация. При этом список и так целиком у браузера.
- **Колонка в адресе.** Владелец не просил делиться ссылкой на сортировку. Добавить можно потом.

### 2. «Сумма на идею» вместо «Риска на идею»

Владелец привык к ProfitGraph: там задаётся сумма сделки, а прибыль и убыток считаются от неё и от расстояния до цели и
стопа. Первая версия profit-fox задавала риск, то есть убыток на стопе. Поэтому у всех идей с целью 2R прибыль и убыток
выходили одинаковыми (+20 / −10), хотя стопы у них на разном расстоянии. Решение владельца (2026-11-05): поле
«Сумма на идею», по умолчанию 10 USDT.

- **Доли считает API.** У каждой идеи API отдаёт:
  - `profitPerUsdt` — прибыль при цели на 1 USDT суммы после комиссий: (|цель − вход| − комиссии входа и выхода) / вход;
  - `lossPerUsdt` — убыток при стопе на 1 USDT суммы с комиссиями: (|вход − стоп| + комиссии входа и выхода) / вход;
  - `riskPerUsdt` — |вход − стоп| / вход.

  Комиссии — те же, что у итога случая (`CaseResult`) и из того же `DefaultFees` категории: taker на входе по рынку,
  maker на лимитном входе «Отката», taker на выходе. Так правило комиссий живёт в одном месте, в домене, а браузер
  только умножает.
- **Браузер умножает на сумму.** Прибыль = сумма × `profitPerUsdt`, убыток = сумма × `lossPerUsdt`, ожидание в USDT =
  ожидание в R × сумма × `riskPerUsdt`. Ожидание в R уже за вычетом комиссий, поэтому R в деньгах — это риск без
  комиссий. Деньги показываются с двумя знаками после запятой.
- **Хранение.** Сумма хранится в браузере под новым ключом. Прежнее значение риска не переносится: у него другой смысл.
- **Карточка на странице пары** берёт ту же сумму, поля на странице пары нет: сумму меняют на «Идеях».

Отклонено:

- **Ставки комиссий в API, умножение в браузере.** Тогда правило «taker на рынке, maker на лимите» живёт и в домене, и в
  браузере, и копии легко разойдутся.
- **Риск и максимум суммы, как у бота ProfitGraph.** Это нужно для настоящих ордеров, а не для просмотра идей.
- **Своё поле суммы на странице пары.** Тогда два места хранят одно число, и их легко рассинхронизировать.

### 3. Прокрутка остаётся на месте

Навигация выбора идеи, «Снять выбор» и переключения ТФ передаёт роутеру `resetScroll: false`. Переход с «Идей» на
страницу пары — это переход на другую страницу, он по-прежнему открывает её сверху.

### 4. Шаг цены в ответе и формат по нему

- `IdeaResponse` получает `tick` из `ideas.tick`.
- Ответ своей идеи получает `tick` из шага цены пары, который API уже использует для округления.
- Интерфейс форматирует вход, стоп и цель функцией «знаков как у шага». Шаг `0.01` даёт 2 знака, `0.5` — 1, `1` — 0.

Отклонено: **нормализовать знаки в API.** Тогда строка цены перестаёт совпадать с тем, что лежит в базе и уходит в
расчёты. Формат — забота экрана.

## Risks / Trade-offs

- Сортировка по показанному тексту для «Сетапа», «Типа» и «Стороны» зависит от русских подписей. Это ожидаемо:
  владелец видит именно их.
- У идей, созданных до появления шага цены, `tick` может быть пустым. Тогда цена показывается как есть, без
  дополнения знаков.

### 5. Уточнения при реализации

- **Направление первого клика.** Клик по заголовку другой колонки всегда сортирует по убыванию (наибольшее или самое
  позднее наверху), повторный клик — по возрастанию. Так читается сценарий «Сортировка по R:R»; для текстовых колонок
  отдельного правила нет, чтобы не плодить исключения.
- **«Прибыль / убыток» сортируется по `profitPerUsdt`.** Прибыль — это сумма × `profitPerUsdt`, поэтому при любой
  положительной сумме порядок тот же. `sortIdeas` суммы не знает. (Решение 2 заменило прежнюю сортировку по R:R.)
- **Ключи сортировки.** «Вероятность» — доля корзины, если у неё хватает данных (`enoughData`), иначе пусто;
  «Ожидание» — ожидание корзины, пусто без корзины; «ТФ» — как число; «Найдена» — по времени; статус — по ходу идеи.
- **Сумма в карточке пары.** `PairIdeasList` читает сумму из хранилища один раз при показе списка. Страница пары сумму не
  меняет, так что синхронизировать два места не нужно.
- **Ожидание в USDT** показывается со знаком, как прибыль и убыток; знак минус — обычный дефис, как у ожидания в R рядом.
  После решения 2 — два знака после запятой.
- **Пустой `tick`.** У идеи, созданной до появления шага цены, `tick` в ответе `null`, и цена показывается как есть.
  Шаг цены, у которого после точки больше знаков, чем у цены, дополняет цену нулями; цена, у которой знаков больше шага,
  округляется до числа знаков шага (в данных Bybit такого нет).
- **Тест прокрутки в jsdom** считает вызовы `window.scrollTo`: роутер зовёт его при каждой навигации, если не передан
  `resetScroll: false`.
- **Доли идеи в коде.** Расчёт — чистая функция домена `IdeaMoney.PerUsdt(plan, fees)` с результатом `IdeaShares`
  (`ProfitPerUsdt`, `LossPerUsdt`, `RiskPerUsdt`). `IdeaView` несёт доли идеи, а обработчики `GetIdeas`, `GetPairIdeas` и
  `GetIdea` берут комиссии из `BacktestSettings.Policy().DefaultFees` по категории идеи, как `IdeasReplay`. Категория
  без ставок в настройках — ошибка конфигурации (как и в повторе истории), для `spot` и `linear` ставки есть в
  `appsettings.json` API и сканера.
- **Доли не округляются в API.** В ответе точные десятичные строки (`0.038878`); два знака — забота экрана.
- **Невалидная или нулевая сумма** (пусто, не число, ≤ 0) — в колонке «Прибыль / убыток» тире, в карточке пары денег нет.
- **Выбор экранов в браузере.** Ключи `profit-fox.ideas.choice` и `profit-fox.market.choice`, значение — JSON. Читается
  только то, что экран знает: каждое поле проверяется отдельно, и неверное (пустое, битое, устаревшее — например, снятый
  сетап или неизвестная колонка) заменяется значением по умолчанию, остальные поля остаются. Исключение — сортировка:
  направление без своей колонки ничего не значит, поэтому устаревшая колонка возвращает сортировку по умолчанию целиком.
- **Удалённый сохранённый фильтр** отдельно не очищается: пока список фильтров грузится или если такого id в нём нет,
  выбранным считается «ничего», а id в состоянии остаётся до следующего выбора. Так выбор не теряется, пока список ещё не
  пришёл.
- **Страница «Рынок» не запоминает поиск**; «Идеи» не запоминают «Сумму на идею» вместе с выбором: у неё свой ключ из
  решения 2.
- **Тесты.** В `src/test/setup.ts` после каждого теста очищается `localStorage`: экраны теперь пишут в него сами, и без
  очистки тесты влияли бы друг на друга. В e2e после возврата на «Рынок» чип сетапа сначала проверяется, потом
  сбрасывается на «Все»; после перезагрузки выбранный сохранённый фильтр уже применён.
