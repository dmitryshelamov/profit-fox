# Design

## Context

Мотивация — в proposal.md. Что есть сейчас:

- `ProfitFox.Engine.Strategy` читает и проверяет граф, держит каталог из десяти узлов и исполняет сигнал по закрытым
  свечам (`SignalExecutor`, по одному `GraphRun` на пару). Узлов заявок нет, поэтому правило «сигнал читает только
  рынок» ничем не проверяется.
- `ProfitFox.Engine.Simulation` считает исход одной сделки по плану на минутном пути (`TradeSimulator`). Это чистая
  функция «путь, момент, план, издержки → исход»; состояния между сделками нет. Проекты `Engine.Strategy` и
  `Engine.Simulation` друг на друга не ссылаются.
- Стенд (`HypothesisRunner.Pair`) по каждой паре считает события сигнала, разыгрывает на каждое 20 случайных входов и
  считает сделки по блокам-неделям. Каждое событие — отдельная сделка, даже если предыдущая ещё не закрыта.
- Сверочный прогон и прогон с вердиктом «данных мало» исход событий не считают вовсе (`withEventOutcomes: false`).
- Эталонный тест `EngineVersionTests` держит дайджест результатов H0001 на синтетической истории для каждого номера
  версии движка и падает, если две версии имеют один дайджест.
- На реальных данных H0001 даёт «данных мало» (мощность 0,74), поэтому исходы её событий на реальных данных стенд
  никогда не читал.

Решения владельца от 2026-11-21:

- стратегия — полный граф, сигнал — её часть;
- сторона зашита в графе, таймфрейм и пороги — параметры;
- граф с лонговой и шортовой веткой допустим;
- позиция одна на пару у стратегии, а не своя у каждого срабатывания;
- порядок работ из пяти шагов (proposal.md);
- стенд считает через граф уже в шаге 1, шагу 2 остаются формат гипотезы и интерфейс (решение 1);
- сверочные прогоны H0001 на реальных данных до и после правок не делаются («не нужно»);
- три решения, найденные при применении, приняты: случайные входы события с исключённой сделкой (решение 7), значения
  выхода у момента без посчитанной свечи (решение 3), отказ чтения гипотезы с числом, которое граф не передаёт точно
  (решение 8).

Урок 2026-11-18: наполовину построенный симулятор заявок без проверки на реальных данных владелец выбросил вместе с
ветками.

## Goals / Non-Goals

**Goals:**

- Стратегия существует как граф, который движок читает, проверяет и исполняет.
- Всё, что сейчас считает стенд, идёт через этот граф, и результат H0001 на эталонных данных при этом не меняется.
- Ни одного нового правила исполнения сделки: вход, стоп, цель, срок и издержки считает прежний `TradeSimulator`.
- Правило одной позиции и открытие вне графа лежат в движке, чтобы шаги 4 и 5 (идеи, бот) взяли их без переписывания.

**Non-Goals:**

- Реакция графа на свою позицию. Узла «позиция» нет, значения выхода фиксируются на свече заявки и до конца цикла не
  меняются.
- Быстродействие. Прогон H0001 упирается в чтение истории, а не в расчёт; расчёт не ускоряется и не замедляется заметно.
- Перенос старых строк журнала на версию движка 2.

## Decisions

### 1. Шаг включает переключение стенда, а формат гипотезы не меняется

В первом порядке работ шаг 1 был «граф в движке», а «стенд проверяет граф» — шаг 2. Здесь граница сдвинута, и
владелец принял сдвиг 2026-11-21: расчёт стенда переходит на граф уже в шаге 1, а шагу 2 остаётся только формат
(гипотеза с графом стратегии вместо `signal` и `plan`), версии и интерфейс.

Причина: иначе граф стратегии проверялся бы только unit-тестами на синтетике, то есть повторил бы 2026-11-18. Со
сдвигом каждый существующий прогон идёт через новый код: его проверяют эталонный дайджест H0001 и все прежние тесты
стенда, а первый же прогон на реальных данных идёт уже через граф.

Сборка стратегии из `signal` и `plan` не временная: версии гипотез в базе неизменяемы, поэтому гипотезы старого формата
будут исполняться через неё и после шага 2.

Альтернатива — отдельная команда «проверить стратегию на паре» только для сверки. Отвергнута: одноразовый инструмент,
который после шага 2 выбрасывается.

### 2. Узлы выхода — отдельные узлы без проводов к узлу входа

```json
{
  "formatVersion": 1,
  "parameters": [{ "name": "threshold", "type": "number", "value": 0.0005 }],
  "outputs": [],
  "nodes": [
    { "id": "p", "kind": "parameters" },
    { "id": "rate", "kind": "funding-rate" },
    { "id": "high", "kind": "compare", "settings": { "operation": "ge" } },
    { "id": "first", "kind": "first-time" },
    { "id": "enter", "kind": "enter", "settings": { "side": "short" } },
    { "id": "close-after", "kind": "close-after", "inputs": { "after": "4h" } }
  ],
  "wires": [
    { "from": "rate.value", "to": "high.a" },
    { "from": "p.threshold", "to": "high.b" },
    { "from": "high.result", "to": "first.value" },
    { "from": "first.event", "to": "enter.when" }
  ]
}
```

| Вид | Входы | Настройки | Название, группа «Позиция» |
|---|---|---|---|
| `enter` | `when`: событие | `side`: `long`, `short` | Вход |
| `stop-loss` | `distance`: число | — | Стоп |
| `take-profit` | `distance`: число | — | Цель |
| `close-after` | `after`: длительность | — | Закрыть через |

Позиция на паре одна, поэтому стоп, цель и срок принадлежат позиции, а не конкретному входу: связывать их проводом с
узлом входа незачем. Двусторонний граф при этом работает без изменений, потому что расстояния заданы долями и не
зависят от стороны.

Альтернатива — стоп, цель и срок входами узла `enter`. Отвергнута: стоп и цель необязательны, а в формате графа нет
необязательного входа («вход без провода и без значения — ошибка»). Пришлось бы менять общее правило проверки.

`close-after` обязателен и один: `TradeSimulator` не умеет сделку без срока, и покрытие истории проверяется по сроку.

### 3. Значения выхода читаются на свече заявки

Исполнитель стратегии на каждой свече отдаёт шаг: момент закрытия, сторону заявки или её отсутствие, срок, стоп и цель
этой свечи. Значения отдаются и на свечах без события: случайному входу нужны значения его свечи.

Случайный вход выпадает на сетку таймфрейма, а стратегия считается только на свечах со сделками. У момента без
посчитанной свечи — свеча без сделок, дыра в истории — берутся значения последней свечи, закрытой к этому моменту:
граф с тех пор не считался. До первой свечи пары известны только значения, записанные в графе; значение по проводу
отсутствует и даёт отказ `plan`. У стратегии, которую собирает стенд, значения записаны в узлах, поэтому в этом шаге
правило ничего не меняет.

Срок, стоп и цель цикла фиксируются в момент заявки. Трейлинг и перенос стопа — это будущие узлы и будущий симулятор.

Числа в графе десятичные (`decimal`), план сделки считает в `double`. Перевод должен дать то же число, что чтение плана
из текста гипотезы: `0.02` в графе обязано стать тем же `double`, что `"stop": 0.02` в `plan`. Это проверяется тестом
на наборе долей; если прямой перевод расходится, переводить через десятичную запись числа.

### 4. Три слоя, симулятор сделки прежний

```
Engine.Strategy     граф стратегии → шаг на свече: заявка? + срок, стоп, цель
Engine.Simulation   заявка → TradePlan → TradeSimulator (без изменений правил)
                    одна позиция на пару: занята до момента выхода текущего цикла
Bench               события и случайные входы пары через эти два слоя
```

- `Engine.Simulation` получает ссылку на `Engine.Strategy` и функцию «шаг и сторона → план или отказ `plan`».
  Допустимость значений — это проверки конструктора `TradePlan`, вынесенные в форму без исключений.
- Правило одной позиции — маленький объект состояния пары: «занята до момента T». Цикл открывается, если момент заявки
  не раньше T; после расчёта выхода T сдвигается.
- `TradeSimulator` получает способ узнать момент выхода сделки, не считая её результата (см. решение 6). Правила
  входа, стопа, цели, срока и издержек не трогаются, тесты `TradeSimulatorTests` и `OutcomeParityTests` проходят без
  правок ожиданий.
- Тип проверенной стратегии нельзя назвать `Strategy`: имя совпадает с пространством имён `ProfitFox.Engine.Strategy`.
- У `TradeStatus` появляется значение для отказа `plan`.

### 5. Какая заявка занимает пару

- Пару занимает только открытый цикл, до фактического момента выхода: стоп на седьмой минуте освобождает пару сразу.
- Заявка ровно в момент выхода открывает новый цикл: сделка по сроку закрыта по закрытию предыдущей минуты.
- Недопустимая заявка (`plan`) и заявка с исключённой сделкой (`coverage`, `funding`, `no_trade`) пару не занимают.
- В начале периода прогона пара свободна. Цикл, который начался бы до периода, не учитывается: стенд и раньше брал
  только события, чья сделка целиком лежит в периоде.

Альтернатива — занимать пару на весь срок независимо от выхода. Она не требует знать момент выхода, но это не правило
биржевой позиции, и бот в шаге 5 считал бы иначе, чем стенд.

### 6. Момент выхода события считается до вердикта, результат — нет

Какие события открывают цикл, зависит от моментов выхода предыдущих циклов. Поэтому момент выхода цикла события
считается всегда, включая сверочный прогон и прогон «данных мало». Результаты циклов событий по-прежнему не считаются
и не читаются, пока это не разрешено.

Это ослабляет слепоту: число учитываемых событий теперь зависит от того, сработал ли стоп. В оценку мощности идут
только случайные входы, знак результата событий в неё не попадает. У H0001 зависимости нет вовсе.

Требования «Мощность вслепую» и «Сверочный прогон» не переписываются: новое требование «Момент конца цикла до вердикта»
уточняет, что под исходом в них понимается результат.

### 7. Случайные входы разыгрываются по блокам, в прежнем порядке

Сейчас `RandomEntries.Draw` разыгрывает входы всех событий пары одним вызовом, до чтения минут. Теперь случайные входы
не нужны событию, пропущенному при открытой позиции, а это известно после расчёта выходов в блоке. Поэтому розыгрыш
идёт блок за блоком с одним генератором на пару:

1. блок читает минуты и строит путь;
2. события блока по времени проходят правило позиции;
3. для каждого непропущенного события разыгрываются входы;
4. состояние позиции пары переходит в следующий блок.

Событие с исключённой сделкой (`coverage`, `funding`, `no_trade`) или недопустимой заявкой (`plan`) пропущенным не
считается: оно получает случайные входы и остаётся строкой отчёта вне статистики, как в версии движка 1. Если бы
случайные входы получали только события, открывшие цикл, каждое исключённое событие сдвигало бы генератор, и случайные
входы H0001 на реальных данных с дырами разошлись бы с версией 1.

Порядок обращений к генератору для гипотезы без пропущенных событий тот же, что сейчас: блоки по времени, события по
времени, `randomsPerEvent` чисел на событие. Поэтому случайные входы H0001 совпадают с нынешними.

Кандидаты случайного входа — закрытия свечей без события, включая пропущенные события: момент пропущенного события
случайным входом не становится.

Случайный вход — цикл вне графа: с пустого состояния, со значениями выхода своей свечи. Он не зависит ни от циклов
событий, ни от других случайных входов, как и сейчас.

### 8. Сборка стратегии из сигнала и плана

- Узел выходов и объявленный выход сигнала убираются; провод, который шёл в выход, идёт в `enter.when`.
- Добавляются `enter` со стороной плана, `close-after` со сроком, и `stop-loss`, `take-profit`, если они есть в плане.
  Значения записываются в `inputs` узлов.
- Идентификаторы новых узлов — их вид; если такой `id` в сигнале занят, добавляется номер (`enter-1`).
- Собранный граф проходит проверку стратегии; ошибка здесь — ошибка программы, а не гипотезы.
- Числа стопа и цели берутся из текста гипотезы десятичными, без прохода через `double`.
- Заявка собранной стратегии обязана дать ровно план из текста. Число, которое план читает как допустимое, а `decimal`
  из 28 значащих цифр передать точно не может (например, `1e-30`), даёт отказ чтения гипотезы. Это новый отказ; прежние
  не меняются.

Предпросмотр сигнала по-прежнему исполняет сигнал, а не стратегию.

### 9. Версия движка 2 и второй эталон

Результаты гипотез с наложением событий меняются, значит номер версии движка растёт до 2. Но дайджест H0001 остаётся
прежним, а тест запрещает две версии с одним дайджестом. Поэтому:

- эталонных гипотез становится две: H0001 и гипотеза на той же синтетической истории, у которой события приходят при
  открытой позиции (срок длиннее расстояния между событиями);
- запись версии в `EngineVersions.json` несёт дайджест каждой эталонной гипотезы;
- две версии различаются, если различается хотя бы один дайджест;
- отдельный тест требует, чтобы дайджест H0001 версии 2 был равен дайджесту версии 1: это и есть «H0001 даёт прежний
  результат».

Версия 1 второго эталона в файл не пишется: её считал бы код, которого после изменения нет.

### 10. Каталог узлов сигнала фильтруется на сервере

У вида узла в движке появляется признак «допустим в сигнале». `GET /api/nodes` отдаёт только такие виды, поэтому
палитра редактора сигналов не меняется, и фронтенд не трогается. Каталог стратегии понадобится в шаге 3 вместе с
редактором стратегий.

Названия и группа новых узлов всё равно добавляются в `NodeTitles`: тест требует слов для каждого вида каталога.

### 11. Несколько узлов входа

Движок принимает несколько узлов входа любых сторон. Разные стороны на одной свече заявки не дают: что из двух
открывать, граф не сказал. Стенд в этом шаге всегда собирает стратегию с одним узлом входа, поэтому розыгрыш случайных
входов по узлам входа решается в шаге 2, когда гипотеза начнёт нести свой граф.

## Risks / Trade-offs

- [Правится расчёт стенда, сверенный с Python, до его первого деплоя на soyo-02] → дайджест H0001 обязан совпасть с
  версией 1; тесты `H0001ParityTests`, `HypothesisRunTests`, `ParityThroughWorkerTests` и `WorkerTests` проходят без
  правок ожиданий.
- [На реальных данных расчёт через граф до слияния не сверяется: владелец снял прогоны «до и после»] → результат
  сверяют только тесты на синтетике. Расхождение на реальных данных, если оно есть, покажет первый сверочный прогон
  H0001 после деплоя: его строку можно сравнить с прежними строками `parity` версии движка 1.
- [Меньше учитываемых событий у частых сигналов, мощность ниже] → число пропущенных событий в отчёте. Это цена
  решения «одна позиция на пару».
- [Число событий зависит от выходов предыдущих циклов, слепота слабее] → решение 6; результаты событий до вердикта
  по-прежнему не считаются.
- [`decimal` → `double` даёт другое число, чем чтение плана] → тест равенства на наборе долей, запасной путь через
  десятичную запись.

## Migration Plan

1. Правки и тесты.
2. Схема базы не меняется, миграций нет. Откат — возврат коммита; строки журнала с версией движка 2 остаются в базе
   как история.

## Open Questions

- Как разыгрывать случайные входы у стратегии с несколькими узлами входа — по узлу сработавшего входа или по стороне.
  Решается в шаге 2; в этом шаге узел входа у стенда всегда один.
