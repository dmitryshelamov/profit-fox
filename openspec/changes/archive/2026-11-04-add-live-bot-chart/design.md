# Design

## Context

Мотивация и границы — в `proposal.md`, поведение — в спеках этого изменения. Образец — ProfitGraph, ADR 0026 (с
поправкой от 2026-10-30) и ADR 0027, и их модули `frontend/src/modules/market-chart` и `modules/bots`. Здесь то, что
важно для подхода в profit-fox.

- Страница бота (`pages/bot/BotPage.tsx`) опрашивает бота и его позиции раз в 5 секунд, пока бот не остановлен
  (`isFollowed`). Позиции приходят из `GET /api/bots/{id}/positions` целиком: все позиции с ордерами (сторона, тип,
  цена, объём, исполненный объём, статус) и сделками (время, цена, объём).
- Свечи хранятся в `candles` с ключом `(category, symbol, interval, open_time)`. `GetCandlesQuery`
  (`/api/market-data/candles`) только читает. Задача загрузки (`RunNextCandleImportCommandHandler`) берёт сохранённые
  open time, считает `Interval.MissingRanges` и догружает только недостающее; `ICandleRepository.UpsertAsync` пишет
  `ON CONFLICT … DO UPDATE`. Одновременно идёт не больше одной задачи загрузки.
- `IMarketHistoryClient.GetCandlePagesAsync` (`BybitMarketDataClient`) ходит в Bybit страницами по 1000 с повторами
  `ExchangeResilienceExecutor.ExecuteWithRetriesAsync` (1, 2, 4, 8, 16 с); запросы, которых ждёт человек (поиск
  инструментов, правила), делают одну попытку. Bybit.Net сам ограничивает частоту запросов в процессе.
- `BybitStreams` — синглтон процесса над одним публичным `BybitSocketClient`: одна подписка на kline-топик на всех
  слушателей, первый подписывает, последний снимает. Он отбрасывает обновления с `confirm=false` и передаёт дальше
  только закрытые свечи. `IExchangeStreams` зарегистрирован и в API, и в Worker'е, но пользуется им только Worker.
- SignalR в проекте ещё нет. Caddy проксирует в API всё под `/api` (WebSocket-апгрейд `reverse_proxy` проводит сам),
  прокси Vite — только HTTP для `/api`.
- Во frontend `market-chart` уже рисует график деталей бэктеста на `lightweight-charts` 5.2 (`PriceEquityChart`,
  маркеры исполнений `seriesMarkers`); десятичные строки становятся числами только в `market-chart/model`.
- e2e-заглушка Bybit отдаёт `/v5/market/kline` (только закрытые свечи, пилообразная цена, объём `10`) и по
  `/control/candle` шлёт в kline-топик закрытую свечу всем подписанным сокетам. `FakeBybitSocketServer` в
  `Tests.Integration` умеет `Kline(openTime, interval, close, confirm)`, считает подписки (`Subscribes`, `Subscribed`) и
  обрывает соединения (`DropAsync`).

## Goals / Non-Goals

**Goals:**

- Поток Worker'а и торговля не меняются: стратегия по-прежнему получает только закрытые свечи из того же кода
  `BybitStreams`, существующие тесты потоков проходят без правок.
- Догрузка истории в API ограничена: один запрос к Bybit на страницу графика, одна попытка, не больше 1000 свечей.
- В API одна upstream-подписка на серию, сколько бы вкладок её ни смотрело.

**Non-Goals:**

- Несколько экземпляров API с общей подпиской: у каждого экземпляра своя, как в ADR 0027.
- Доставка статуса, позиции и исполнений через хаб: остаётся опрос раз в 5 секунд.
- Запоминание периодов, которых нет у Bybit (аналог `candle_closures` ProfitGraph).
- Новые таблицы, индексы и миграции.

## Decisions

### 1. Один endpoint истории от бота

`GET /api/bots/{id}/candles?from&to&interval` (`Bots/Queries/GetBotCandles`): инструмент берётся из бота, интервал —
из параметра или интервала бота. Ответ `BotCandlesResponse { interval, candles: CandleResponse[], unavailable }`:
свечи — те же десятичные строки, что у `/api/market-data/candles`.

- Проверка входа — как у `GetCandlesQuery`: `from` и `to` через `ApiTimestamps`, `interval` через
  `MarketDataCodes.TryParseInterval`, ошибки по имени параметра (400). Неизвестный бот — 404.
- Период выравнивается и обрезается: `from` опускается к началу своей свечи, `to` обрезается до начала текущей
  свечи — `Interval.CandleOpen(now)`. Если после обрезки свечей в периоде нет, ответ пустой, Bybit не вызывается.
  Больше 1000 свечей (`Interval.CandleCount`) — 400 по `from`.
- `Interval.CandleOpen(at)` — новая чистая функция рядом с `CandleEnd`: сетка от эпохи UTC для минут, часов и суток,
  понедельник 00:00 для `W`, первое число месяца для `M`. Без выравнивания `MissingRanges` видел бы «дыру» между
  невыровненным `from` и первой свечой и звал бы Bybit на каждом чтении.

Альтернатива — расширить `/api/market-data/candles` флагом догрузки: отклонена, тогда любой клиент чтения свечей мог
бы писать в хранилище, а бот и его интервал по умолчанию пришлось бы передавать снаружи.

### 2. Догрузка при чтении (read-through)

`MarketData/CandleReadThrough` в Application: open time периода из `GetOpenTimesAsync` → `MissingRanges`. Если чего-то
нет — один запрос к Bybit на отрезок от начала первой недостающей части до конца последней (страница ≤ 1000 свечей,
значит, один запрос Bybit её покрывает), из ответа берутся только закрытые свечи (`IsClosedAt(interval, now)`),
попавшие в недостающие части, и пишутся `UpsertAsync`. Затем страница читается из хранилища `GetAsync`.

- Догрузка не создаёт `CandleImportJob`, не берёт аренду и не ждёт очереди. С задачей загрузки она не согласуется:
  обе пишут только то, чего не было, по одному ключу, а значения закрытой свечи Bybit одинаковы, поэтому гонка даёт
  ту же строку.
- Пропуски в истории самого Bybit хранятся как есть: свечи, которой Bybit не вернул, в хранилище нет.
- Bybit не ответил или отказал (`ExchangeException`): ответ — сохранённые свечи периода и `unavailable = true`, 200.
  Страница бота от графика не зависит, поэтому статус и позиция видны.

Почему один запрос на страницу, а не на каждую недостающую часть: страница с несколькими пропусками стоила бы
нескольких запросов, а данные одного запроса всё равно покрывают всю страницу.

### 3. Одна попытка к Bybit

`IMarketHistoryClient` получает `GetCandlesOnceAsync(instrument, interval, from, to)` — одна страница Bybit до 1000
свечей через `ExecuteOnceAsync`, как поиск инструментов. Повторы 1…16 с держали бы открытие страницы до 31 секунды,
а человек ждёт ответа сейчас; следующая прокрутка или минутное обновление и есть повтор. Ограничитель частоты
Bybit.Net в API работает как для остальных запросов API. *Решение агента, ждёт ревью владельца.*

### 4. Исполнения и ордера — из опроса позиций

График берёт исполнения и активные ордера из уже опрашиваемого `GET /api/bots/{id}/positions`, а не из endpoint'а
свечей, как в ProfitGraph. Так новое исполнение или ордер появляется на графике с тем же 5-секундным опросом
(критерий 6), а не с минутным обновлением истории, и индекс исполнений по времени не нужен.

- Исполнение ставится на свечу, период которой его содержит, в том числе на текущую свечу: на интервале бота покупка
  в формирующейся свече видна сразу. Исполнение вне нарисованных свечей не показывается.
- Линия ордера — у ордера типа `limit` в статусе `active`; подпись — сторона, цена и остаток
  (`quantity − filledQuantity`), то есть то, что ещё стоит в книге. *Решение агента: остаток, а не исходный объём.*

Альтернатива — исполнения окна в ответе свечей и индекс `live_fills (bot_id, executed_at)`: отложена, пока объём
позиций бота не станет заметным для опроса раз в 5 секунд; тогда это первый шаг.

### 5. Порт текущей свечи в общем `BybitStreams`

`Ports/MarketData/IFormingCandleStreams.SubscribeAsync(instrument, interval, update, lost, restored, ct)` и запись
`FormingCandle` (open time, OHLCV, `IsClosed`, `ObservedAt` — время обновления Bybit). Реализует его тот же
`BybitStreams`: у kline-топика два вида слушателей — закрытых свечей (Worker, как сейчас) и всех обновлений (API).
Обработчик топика отдаёт каждое обновление вторым и только `confirm=true` первым; `ConnectionLost` подписки
сообщается слушателям обновлений.

Почему не отдельный клиент: общий механизм топиков уже даёт «первый подписывает, последний снимает» и одно публичное
соединение на категорию. Цена — правка класса, которым торгует Worker; её страхуют существующие `BybitStreamsTests`.

Переподключение оборванного соединения — по-прежнему встроенное у CryptoExchange.Net с его настройками по
умолчанию, в обоих процессах: менять политику общего клиента значит менять поведение Worker'а. Пауза 1 с с удвоением
до 1 мин из ADR 0027 относится к повторной подписке ленты, если Bybit отказал в подписке или клиент закрыл её
насовсем (`ConnectionClosed`). *Решение агента, уточняет ADR 0027.*

### 6. Ленты текущих свечей в API

`MarketData/FormingCandles/FormingCandleFeeds` (Application) — синглтон, регистрирует его только API. Ключ ленты —
`(category, symbol, interval)`; ключа аккаунта нет, поток публичный.

- Первый зритель открывает подписку через порт, последний (отписка или разрыв соединения) её снимает. Одно
  соединение браузера следует за одним ботом: новая подписка того же соединения сначала покидает прежнюю ленту.
- Состояние ленты: `Connecting` (подписка есть, обновлений ещё нет), `Live`, `NoData` (обрыв, отказ подписки или 90 с
  без обновлений). После `restored` лента остаётся `NoData` до первого обновления.
- `FormingCandleThrottle` — чистая логика с `TimeProvider`: обновление уходит сразу, если прошло ≥ 1 с с прошлого,
  если это закрытие или первая свеча нового интервала; иначе придерживается, и самое новое из придержанных уходит по
  таймеру через секунду после прошлого. Обновление со старшим `(OpenTime, ObservedAt)`, чем уже переданное,
  отбрасывается.
- Публикация — через порт `IFormingCandleBroadcast` (Application), реализованный в Presentation над
  `IHubContext<BotChartHub>`: группа на серию, сообщения `FormingCandle` и `FormingStatus`.

### 7. Первый SignalR-хаб: `/api/hubs/bot-chart`

`BotChartHub` в `ProfitFox.Presentation/Hubs`. `Subscribe(botId)` находит бота (`GetBotQuery`), присоединяет
соединение к ленте его инструмента и интервала и возвращает снимок: состояние ленты и последнюю свечу; неизвестный
бот — `HubException` `bot_not_found`. `Unsubscribe()` и разрыв соединения покидают ленту. Текущая свеча — только на
интервале бота; другие интервалы хаб не предлагает.

- Путь под `/api`: Caddy проводит его без правок, требование «Один адрес для интерфейса и API» сохраняется. Прокси
  Vite для `/api` получает `ws: true`. Альтернатива — `/ws/...`, как в ProfitGraph: отклонена, нужен второй маршрут в
  Caddy и Vite.
- Цены и объём в сообщениях — десятичные строки, время — UTC ISO. Хаба нет в OpenAPI, поэтому типы сообщений
  frontend описывает сам (`modules/bots/model/formingCandle.ts`).
- Зависимости: SignalR — часть ASP.NET Core, на сервере новых пакетов нет. Frontend добавляет `@microsoft/signalr`
  (точная версия в `package.json`), интеграционные тесты — `Microsoft.AspNetCore.SignalR.Client`.

### 8. Frontend: график, страницы истории, переключатель

- `market-chart/model`: `chartPaging` (страница из 500 свечей перед open time, склейка страниц по open time, «слишком
  далеко отстали» — больше 999 свечей с последней), `tradeMarkers` (исполнения на свечах с точной ценой и общей
  подписью «×N»), `liveCandles` (текущая свеча поверх истории, история главнее), `volumeBars`, `orderLines`. Всё —
  чистые функции, тесты первыми.
- `market-chart/ui/BotCandleChart`: `CandlestickSeries` и `HistogramSeries` объёма на своей скрытой шкале в нижних ~20%
  той же панели, полупрозрачные цвета по направлению свечи из токенов темы; маркеры `createSeriesMarkers` с позициями
  `atPriceTop` (покупка, стрелка вверх) и `atPriceBottom` (продажа, стрелка вниз), чтобы остриё стояло на цене;
  ордера — `createPriceLine` с пунктиром. Текущая свеча и её объём — `series.update` полупрозрачным цветом.
- `bots`: `botCandlesQuery` (страницы назад при приближении видимого диапазона к началу; остановка на пустой странице),
  минутное обновление хвоста — запрос от свечи после самой новой до сейчас, при отставании больше 999 свечей —
  заново от сейчас; `followFormingCandle` (SignalR, автопереподключение, после переподключения — снова `Subscribe`),
  `useFormingCandle` с редьюсером, как в ProfitGraph; `chartIntervals` — `1`, `5`, `15`, `60`, `240`, `D` и интервал бота
  с «· бот» (если он уже в списке, отмечается этот пункт).
- Страница: `pages/bot/BotChart.tsx` над `LiveControls`; `?interval=` в `validateSearch` маршрута бота, интервал бота
  в адрес не пишется, неизвестный — интервал бота.
- Над графиком строка последней свечи: время, open/high/low/close, объём и «не закрыта» у текущей; под графиком —
  состояние канала или пометка о минутном обновлении на другом интервале; «История недоступна: Bybit не отвечает» при
  `unavailable`. У графика есть доступное описание с числом показанных исполнений и ордеров. *Решение агента:* строка
  последней свечи и описание делают показанное проверяемым в DOM и для e2e, холст `lightweight-charts` текста не
  даёт.

### 9. Проверка

- Unit: `Interval.CandleOpen` (минуты, часы, `D`, `W`, `M`), `GetBotCandlesQueryHandler` с NSubstitute (выравнивание,
  обрезка, лимит, одна попытка, только недостающее и закрытое, `unavailable`), `FormingCandleThrottle`, состояние
  `FormingCandleFeeds` на фейковом времени и фейковом порте; frontend — чистые функции и редьюсер.
- Integration: догрузка через API на реальном Postgres с `FakeBybitHandler` (пустое хранилище → свечи в `candles`,
  повтор не зовёт Bybit, Bybit не отвечает → `unavailable`); хаб на `FakeBybitSocketServer` (снимок и обновления,
  `confirm=false` не попадает к стратегии и в `candles`, две подписки → один `Subscribes`, закрытие обеих → не
  `Subscribed`, обрыв → `NoData` → восстановление → `Live`). `ProfitFoxFactory` получает `BybitSocketAddress` для API.
- e2e: заглушка получает `/control/forming` (`confirm=false`, цена и объём из параметров). Один сценарий на запущенном
  боте со счётом заглушки: история с объёмом → текущая свеча через `/control/forming` → закрытие через
  `/control/candle` → исполнение через `/control/fill` → переключение интервала.

## Risks / Trade-offs

- [Пропуск в истории Bybit или период до листинга] → такая страница зовёт Bybit при каждом чтении: пустые периоды не
  запоминаются. Это один запрос на страницу, и подгрузка назад останавливается на пустой странице. Если станет
  заметно — таблица закрытых периодов, как `candle_closures` в ProfitGraph.
- [`UpsertAsync` пишет `DO UPDATE`, а спека загрузки требует не менять сохранённые свечи] → догрузка пишет только
  недостающие свечи, так что сохранённые не меняются, кроме гонки с загрузкой, где значения те же. Расхождение кода и
  спеки было и до этого изменения; здесь оно не исправляется.
- [Минутное обновление хвоста каждой открытой вкладки] → один короткий запрос к Bybit в минуту на вкладку; через
  ограничитель Bybit.Net и общий автомат размыкания API. Частые сбои графика могут разомкнуть автомат и на минуту
  отказать поиску инструментов в API — приемлемо, торговля идёт в Worker'е.
- [Правка `BybitStreams`, которым торгует Worker] → путь закрытых свечей не меняется; существующие тесты потоков и
  e2e живой торговли — регрессия.
- [Между присоединением к ленте и входом в группу хаба можно пропустить одно обновление] → снимок несёт последнюю
  свечу, следующее обновление придёт в течение секунды.
- [Много открытых серий] → каждая серия — отдельный топик на общем публичном соединении категории; ограничение на
  пользователя отложено, как в ADR 0027.
- [Позиции бота растут, опрос раз в 5 с отдаёт их целиком] → как и сейчас на странице; при росте — окно исполнений по
  времени с индексом (решение 4).
- [Пересечение с `handle-exchange-intervention`, предложенным в своём worktree] → оно меняет `BybitStreams` (инструмент
  в `ExchangeFill`) и `FakeExchange`; это изменение — тот же `BybitStreams` (kline-топик). Страницу бота и
  `LivePositions` то изменение не трогает, здесь `LivePositions` не меняется, `BotPage` получает график. Кто вливается
  вторым, переносит правки `BybitStreams` поверх; конфликт текстовый, не смысловой.

## Migration Plan

- Миграций БД нет. Выкладка — API и образ `web`; Caddy не меняется.
- API в production впервые открывает WebSocket к публичному потоку Bybit (`stream.bybit.com`): исходящий доступ с
  `soyo-01` к нему уже есть у Worker'а, у контейнера API — проверить при выкладке.
- Откат — выкладка прежних образов; свечи, сохранённые догрузкой, остаются и не мешают.
- Документы обновляются в этом же изменении: `CONTEXT.md` — исключение в «Worker», термины «Текущая свеча» и «График
  бота»; `docs/conventions.md` — хаб, порты, модули.

## Отклонения от плана при реализации

- Параметры запроса истории пишутся как в OpenAPI-схеме: `From`, `To`, `Interval` (ASP.NET Core привязывает их без
  учёта регистра), поэтому в адресе запроса не `from`/`to`/`interval`.
- Минутное обновление хвоста — запрос от конца первой страницы до «сейчас», как в ProfitGraph, но без запроса сразу после
  первой страницы: у хвоста есть начальные данные, свежие на минуту (`initialData` и `staleTime`). Начало заново при
  отставании больше 999 свечей проверяется раз в минуту.
- Роутер TanStack пишет в адрес текстовое значение, похожее на JSON, в кавычках (`?interval=%225%22`) и читает `?interval=5`
  числом. Поэтому `createAppRouter` получил `stringifySearch: stringifySearchWith(JSON.stringify)` (строки пишутся как
  есть), а `validateSearch` маршрута бота принимает и число, и строку. Для остальных маршрутов запись адреса не меняется.
- Месяц в длине интервала (`intervalSeconds`) — 31 день, наибольший: нужен только для размера страницы и для проверки,
  что исполнение внутри свечи.
- Одно исполнение стороны на свече — стрелка без подписи; подпись «×N» только при N больше одного.
- Строка последней свечи показывает время в UTC (`2024-03-10 10:00`) и значения строками API без группировки разрядов.
- Тексты, которых нет в спеках: «Не удалось загрузить свечи.» при ошибке запроса, «Загрузка свечей…» и «Свечей за период
  нет.» для пустой истории без `unavailable`.
- В `src/test/setup.ts` `@microsoft/signalr` заменён тихим соединением: страницы бота в тестах не ходят к хабу.

### Бэкенд (задачи 1–5)

- **Порт получил четвёртый обратный вызов.** `IFormingCandleStreams.SubscribeAsync(instrument, interval, update, lost, restored, closed, ct)`: к `lost` и `restored` из решения 5 добавлен `closed` — подписка закрыта клиентом насовсем (`ConnectionClosed`). Без него лента не узнала бы, что подписку нужно открыть заново (задача 4.4). `ConnectionClosed` не удалось вызвать на `FakeBybitSocketServer`: CryptoExchange.Net поднимает его только при окончательном закрытии подписки, поэтому эта ветка `BybitStreams` покрыта только тестом ленты на уровне порта.
- **Таймер тишины стартует вместе с подпиской.** 90 секунд без обновлений переводят в `NoData` и ленту в `Connecting` (ни одного обновления), а не только `Live`: спека говорит «90 секунд нет обновлений» без оговорки. Успешная повторная подписка после отказа возвращает ленту в `Connecting`; после `restored` лента остаётся `NoData` до обновления (как в решении 6).
- **Регулятор сравнивает с самым новым принятым обновлением** — отправленным или придержанным, а не только с отправленным: обновление старше придержанного не заменяет его. Снимок ленты несёт то же «самое новое принятое» (`FormingCandleThrottle.Latest`).
- **История графика читает бота через `IStrategyLibraryRepository.GetBotAsync`**, а не `GetBotQuery`: аккаунт и состояние бота истории не нужны. Период, где `from >= to`, — ошибка по `from`, как у `GetCandlesQuery`.
- **Хаб входит в группу SignalR до подписки на ленту**, а не после: пропущенное обновление между ними исключено, лишний дубль снимка безвреден. Сообщение `FormingCandle` не несёт `observedAt` (порядок держит сервер), `FormingStatus` — строка `connecting` / `live` / `noData`.
- **`CandleReadThrough` публичен и регистрируется как transient** в `InfrastructureRegistrar.Configure` и `ConfigureWorker` (общая регистрация): обработчик запроса публичный, ему нужен публичный тип в конструкторе. Worker им не пользуется.
- **Новые тесты рядом с существующими:** `IntervalCandleOpenTests` лежит в `Tests.Unit/Domain/Entities/MarketData/Enums` (как соседние тесты `IntervalExtensions`), а не в `Tests.Unit/Domain`.
- **Незащищённая тестом ветка** `FormingCandleThrottle.SendHeld`: проверка `_held is not null` нужна для гонки «таймер уже поставлен в очередь, а закрытие свечи ушло сразу»; воспроизвести её на `FakeTimeProvider` нельзя.

### Ревью, раунд 1 (backend)

- **Гонка подписки и отключения хаба (1).** SignalR выполняет вызовы соединения в фоне, и `OnDisconnectedAsync` может обогнать `Subscribe`. После `JoinAsync` хаб проверяет `Context.ConnectionAborted` (он отменяется раньше `OnDisconnectedAsync`) и сам уводит зрителя из ленты. Тест: `BotChartHubRaceTests`.
- **Брошенная подписка и «закрыта» посреди подписывания (3, 8).** Каждая попытка подписаться получила свой маркер; события (`update`, `lost`, `closed`) старой или уже закрытой попытки ленту не меняют, а подписка, которая закрылась, пока создавалась, освобождается и создаётся заново через 1 с. Проверки `_closed` заменены сравнением маркера, поэтому все ветки закрыты тестами (`FormingCandleFeedsTests`: закрытие и обновление во время подписывания, события старой подписки, события и отказ после ухода последнего зрителя).
- **Live → Connecting (4).** Успешная подписка переводит ленту в `Connecting` только из `NoData`; обновление, пришедшее до возврата `SubscribeAsync`, оставляет `Live`.
- **Огромный период (5).** `Interval.CandleCount` получил предел и перестаёт считать на `limit + 1`; обработчик истории передаёт 1000. Тест с периодом 0001–2100 для минутных свечей (был красным: 12 с).
- **Документация порта (9).** XML-описание параметров `IFormingCandleStreams` исправлено.
- **Подписка, снятая с общего соединения (10): не подтверждено.** Тест `A_subscription_that_was_taken_off_does_not_report_a_drop_to_the_next_one`: первая подписка топика снята, вторая сделана на том же соединении, после обрыва слушатель получает ровно одно `lost`. Старая подписка слушателям нового не вещает, код не менялся.
- **Недозакрытая свеча (11).** Догрузка сохраняет свечу не раньше чем через 5 секунд после её закрытия (`CloseMargin`): Bybit мог отдать её по REST ещё не законченной, а сохранённая свеча уже не перечитывается. Пять секунд — запас на задержку биржи при небольшой задержке графика (свеча появится на следующем минутном обновлении). Тест: `A_candle_that_closed_a_moment_ago_is_not_stored_yet_but_is_after_five_seconds`.
- **Оставлено как защитный код без теста:** хук `ConnectionClosed` в `BybitStreams.Watch` (событие поднимается только при окончательном закрытии подписки, на `FakeBybitSocketServer` не воспроизводится) и проверка `_held is { }` в `FormingCandleThrottle.SendHeld` (гонка таймера с немедленной отправкой).

### Ревью, раунд 1 (frontend)

- **Канал свечи не теряется навсегда (2).** `withAutomaticReconnect` получил свою политику: 0, 2, 10, 30 с и дальше каждые 30 с без конца. Неудавшийся `start()` и отклонённый `Subscribe` повторяются через паузу (2, 10, 30 с и дальше 30 с); `bot_not_found` окончателен и не повторяется. После остановки подписчика повторов нет. Тесты в `followFormingCandle.test.ts`.
- **Поздний снимок не затирает новое состояние (4, клиент).** Подписчик помечает снимок `superseded`, если после вызова `Subscribe` пришло сообщение `FormingCandle` или `FormingStatus`. Редьюсер для такого снимка не меняет состояние канала и свечу, а свечу снимка берёт только если она новее текущей. Тесты в `formingCandle.test.ts` и `followFormingCandle.test.ts`.
- **Недоступные страницы истории перечитываются (6).** Пока среди страниц истории есть `unavailable`, минутный таймер перечитывает их (`refetch`); страница с новыми свечами снова даёт `getNextPageParam`, и листание назад продолжается. Тесты в `candlesApi.test.tsx`.
- **Месячная свеча (7).** Конец свечи считается по календарю UTC (`candleEnd` в `chartPaging.ts`, как `CandleEnd` на backend); `tradeMarkers` принимает функцию конца свечи, `BotCandleChart` получает `interval` вместо `intervalSeconds`. Сделка 1 марта больше не попадает на февральскую свечу. Окно страницы истории (`pageBefore`, `tooFarBehind`) остаётся с запасом по 31 дню: это только размер запроса.
- **Лишние запросы при первом открытии (12).** Библиотека графиков сообщает видимый диапазон синхронно из `setData`, до того как график возвращает вид на прежние свечи; диапазон со `from < 10` вызывал `onReachStart` и подгружал следующую страницу. Пока график принимает данные, смена диапазона не считается действием пользователя (флаг `applying`). Тест в `charts.test.tsx`. Воспроизвести ровно пять запросов QA не удалось, механизм подтверждён чтением кода библиотеки и тестом с имитацией.

### Ревью, раунд 2 (backend)

- **Дыра у последней закрытой свечи (11).** Запас в 5 секунд после закрытия оставлял свечу, закрывшуюся прямо перед открытием страницы, и не в хранилище, и в диапазоне ответа. Теперь обработчик истории обрезает конец периода на тот же запас (`CandleReadThrough.CloseMargin`): ответ не заявляет свечу, которую ещё не сохранил, а минутное обновление хвоста (frontend начинает его с конца самой новой полученной свечи) принесёт её следом. Тест: `To_is_cut_before_a_candle_that_closed_less_than_the_close_margin_ago`.
- **Закрытая лента запускается (3).** `CloseAsync` ставит постоянный признак закрытия, а `ConnectAsync` под замком не начинает подписку закрытой ленты: иначе `LeaveAsync`, обогнавший `Start()`, оставлял подписку на ленте, которой уже нет в `_feeds`. Тест: `A_feed_closed_before_it_starts_makes_no_subscription`.

### Ревью, раунд 2 (frontend)

- **Хвост начинается с конца новейшей полученной свечи.** Раньше минутное дочитывание шло от конца запрошенного периода первой страницы; свеча, которую сервер ещё не успел сохранить (`CloseMargin`, 5 с после закрытия), на первом чтении отсутствовала и позже не запрашивалась. Теперь хвост стартует с закрытия новейшей свечи первой страницы (без свечей на странице — с конца периода); `mergeCandles` убирает повторы.
- **Закрытая свеча видна не позже чем через минуту.** Интервал дочитывания хвоста — не минута, а `min(60 с, время до ближайшего закрытия свечи + 5 с)` (константа `closeMargin`, то же значение, что у `CloseMargin` бэкенда). Лишних запросов нет: дополнительное чтение появляется только когда следующее закрытие + 5 с наступает раньше минутного таймера. Выбрано вместо отдельного таймера на границу: одно место планирования, без дублей запросов на минутных интервалах. Недели и месяцы не выровнены по эпохе и остаются на минуте.
- **Закрытие соединения сервером.** Если SignalR закрыл соединение без переподключения (`onclose`), сбрасывается `started` и планируется повтор, который снова вызывает `start()`; раньше повтор вызывал `invoke` на закрытом соединении.

### Ревью, раунд 3

- **Сброс хвоста считается от начала хвоста.** `tooFarBehind` получает `tailFrom`, а не конец периода первой страницы: при нескольких непришедших свечах в конце страницы (например, остановка торгов) хвост начинается раньше и превышал бы 1000 свечей до сброса, запрос получал бы 400, и хвост замирал.
- **Недели и месяцы читаются раз в минуту.** Ветка для `W` и `M` в `untilNextRead` покрыта тестом: без неё чтение привязывалось бы к границам, выровненным по эпохе, а у недель и месяцев они другие.
- **Принятое ограничение: часы клиента.** `untilNextRead` использует часы браузера, а `CloseMargin` бэкенда — часы сервера. Если часы клиента спешат, чтение у границы может случиться раньше, чем сервер сохранил свечу; она тогда появится следующим чтением, примерно через 60 с плюс расхождение часов, и не теряется. Код не меняем.
