# Design

## Context

Мотивация — `proposal.md`. Требования — `specs/bot-management`, `specs/backtest-runs`, `specs/backtest-simulation`,
`specs/backtest-results` и дельты `specs/strategy-library`, `specs/strategy-execution`. Термины — `CONTEXT.md`
(«Бот», «Баланс бота», «Версия стратегии», «Бэктест», «Режим поиска», «Результат бэктеста»).

Текущее состояние:

- `StrategyLibrary` — один агрегат со стратегиями и пользовательскими составными узлами, оптимистичная ревизия в
  `strategy_library`; каждая запись репозитория — одна транзакция с проверкой ревизии.
- `StrategyRun` (`Domain/Services/Strategies/Execution`) принимает `RunStarted`, `BarClosed`, `OrderFilled`,
  `OrderCancelled` и выдаёт `PlaceOrder`, `CancelOrder`; позицию ведёт `PositionBook` без комиссий; округления нет.
- Загрузка свечей — `CandleImportJob` + `ICandleImportQueue` (`Channel<Guid>`) + `CandleImportBackgroundService`, одна
  задача за раз; `CandleImportInitializationService` при старте ставит незавершённые задачи в очередь; работа идёт через
  `ISender.Send(RunCandleImportCommand)`.
- Bybit — через `Bybit.Net` (`BybitMarketDataClient`): свечи и проверка символа.
- Ни один агрегат не публикует доменных событий; unit of work и outbox по-прежнему не нужны (правило проекта: они
  приходят с первым событием и его обработчиком).

## Goals / Non-Goals

**Goals:**

- Один движок для бэктеста и будущего живого бота: свободные деньги, комиссии, округление и минимум ордера считает
  `StrategyRun`, а не симулятор.
- Детали результата, пересчитанные по запросу, совпадают с сохранёнными метриками по построению: один и тот же код
  прогона с разными наблюдателями.
- Перенос бэктестов в Worker (изменение 2.1) меняет только очередь.

**Non-Goals:**

- Worker, очередь в БД, несколько бэктестов одновременно.
- Прогресс по WebSocket или SSE: прогресс читается опросом `GET /api/backtests/{id}`.
- Удаление отдельного бэктеста и отдельного результата (бэктесты удаляются вместе с ботом).
- Модель маржи и ликвидаций шорта сверх «обеспечение = стоимость входа при плече 1».

## Decisions

### 1. Решения из интервью с владельцем

Зафиксированы в интервью 2026-11-01 перед этим изменением:

- **Бэктест сохраняется и считается в фоне** по образцу загрузки свечей. Отклонены: синхронный POST (таймауты на
  длинных периодах), бэктест без сохранения (нечего сравнивать).
- **Бот входит в эту фичу**: «стратегия → бот → бэктесты бота». Бот — стратегия, значения параметров, инструмент,
  интервал, баланс бота; без ключей и запуска. Отклонены: бэктест у стратегии с созданием бота позже; оба пути сразу.
- **Бэктест — это и оптимизация**, как в ProfitGraph: параметр — значение или диапазон с шагом; у бэктеста режим поиска,
  в этой версии только полный перебор. Случайный поиск, TPE, walk-forward — позже. Отдельной сущности «оптимизация» нет.
- **Защита от огромной сетки** — и лимит комбинаций в `appsettings`, и отмена бэктеста.
- **Хранение**: метрики у каждого результата, детали — пересчётом по запросу. Отклонены: детали у всех результатов
  (объём), финалисты как в ProfitGraph (нужна целевая метрика, а сортируем при чтении).
- **Версии стратегий** (уровень 2 из трёх обсуждённых): версия хранит раскрытый граф, включая встроенные узлы; бот на
  последней версии, бэктест — на своей. Отклонены: только снимок в бэктесте (нет истории и группировки по версии);
  версии и узлов, и стратегий (каскад по узлам, а встроенные узлы в коде пришлось бы версионировать отдельно).
  Закрепление бота на версии — фича 5.
- **Модель исполнения** — от ProfitGraph (ADR 0057, «OHLC Execution Model»): путь O→L→H→C, рынок по Open следующей
  свечи с проскальзыванием, лимитка целиком по своей цене, режим «касание»/«пробой» (по умолчанию «пробой»), отмена
  сразу. Отклонено: исполнение нового ордера на остатке пути той же свечи, как в ProfitGraph, — путь лишь догадка, а
  это завышает число кругов у Ladder и сеток, по которым выбираются параметры.
- **`hold-limit` после частичного исполнения**: в бэктесте частичных исполнений нет, вопрос переносится в фичу 5.
- **Баланс — часть бота**, бэктест может его переопределить. Это баланс бота, не аккаунта.
- **Нехватка денег предотвращается, а не отклоняется**: узел ордера входа без денег ведёт себя как при ложном «когда»,
  проверку делает движок для всех стратегий. Отклонены: событие «ордер отклонён» (зацикливание `hold-limit`, новая
  механика), проверка только явным узлом (забытая проверка — трата сверх баланса живыми деньгами).
- **Комиссии** — настройка бэктеста (уровень аккаунта, не бот), списываются как на Bybit, спот-покупка — в монете.
  Отклонено: всё в USDT (живой бот на споте продавал бы больше, чем у него есть).
- **Округление и минимум — в движке**; правила инструмента запрашиваются у Bybit при создании бэктеста и хранятся в
  нём. Отклонены: правила у бота (устаревают), таблица правил по инструменту (новый шаг загрузки).
- **Правка стратегии, ломающая бота, не сохраняется** — как для составных узлов. Отклонены: автопочинка бота (молча
  другие параметры), пометка «требует правки». Стратегию с ботами удалить нельзя; бот удаляется с бэктестами.
- **Сделка — цикл позиции.** Отклонено: пары FIFO.
- **Метрики** — набор ProfitGraph (`SampleMetrics`, ADR 0057) плюс сделки, доля прибыльных, пропущенные ордера и
  доходность к просадке. Новые метрики добавляются позже как новые поля.
- **Графики** — только данные в API; рисование во фронтенде.
- **Статусы** с `LoadingCandles`, прогресс загрузки и прогона, скорость в свечах в секунду.
- **Недостающие свечи бэктест догружает сам**; если их нет и после загрузки — идёт по тому, что есть, и сообщает об
  этом. Отклонены: отказ при неполных данных, `Failed` после загрузки.
- **Считать в процессе API параллельно**; Worker — следующее изменение 2.1. Отклонены: Worker сейчас (инфраструктура
  проектируется под требования живого бота), один поток (минуты вместо секунд).
- **`ProfitFox.Engine` не выносится**: движок остаётся в `Domain/Services/Strategies`, симулятор и метрики — в
  `Domain/Services/Backtests`. Отклонены: вынос сейчас (доменные типы тянутся следом, изоляции почти нет), вынос в 2.1.

### 2. Боты — часть агрегата библиотеки

`StrategyLibrary` получает ботов. Инвариант «каждый бот валиден против последней версии своей стратегии» связывает
бота и стратегию так же, как правка узла связывает узел и стратегию, поэтому держится в одном агрегате и проверяется
unit-тестами. Конкурирующие сохранения бота и стратегии разрешает та же ревизия `strategy_library`
(спек «Бот всегда валиден»).

- Операции: `AddBot`, `UpdateBot`, `RemoveBot`; `UpdateStrategy` проверяет ботов стратегии и бросает
  `BotsAffectedException` со списком ботов и ошибок; `RemoveStrategy` с ботами бросает её же без ошибок. Проверка бота —
  те же правила, что `StrategyRun.Start` для значений параметров, плюс категория против направления.
- Проверка символа на бирже — в обработчике команды до вызова агрегата, через существующий
  `IMarketHistoryClient.InstrumentExistsAsync`, как в задаче загрузки. Без связи с Bybit бота не создать (503) —
  владелец принял это при ревью артефактов.
- Бот хранит только заданные значения; значение по умолчанию берётся из последней версии в момент использования.
- Отклонено: отдельный агрегат бота с проверкой стратегии в обработчике — между чтением стратегии и сохранением бота
  стратегия может измениться, и инвариант пришлось бы держать в SQL.

### 3. Версия стратегии — снимок исполнения

`StrategySnapshot` (`Domain/ValueObjects/Strategies`) — определение стратегии без раскладки и имени плюс определения
всех составных узлов из её замыкания (пользовательские и встроенные), упорядоченные по идентификатору. У него
структурное равенство; `StrategyRun.Start` принимает снимок как `StrategyDefinition` + `CompositeCatalog`, собранный
только из узлов снимка. Так версия исполняется одинаково после любых правок узлов и деплоев встроенных узлов.

- Агрегат держит номер и снимок последней версии каждой стратегии. Сохранение стратегии и правка узла пересчитывают
  снимки затронутых стратегий; изменившийся снимок даёт версию `n + 1`. Агрегат отдаёт новые версии вместе с
  изменением, и репозиторий пишет их в той же транзакции, что изменение и сдвиг ревизии.
- Репозиторий получает один метод записи изменения библиотеки (`SaveAsync(StrategyLibraryChange, expectedRevision)`:
  записи и удаления стратегий, узлов, ботов и новые версии) вместо отдельных методов на каждую сущность. Это по-прежнему
  одна транзакция внутри одного метода, не общий unit of work.
- В БД снимок — `jsonb` в том же формате `StrategyJson`, что определения (новый документ версии:
  `{ "strategy": …, "composites": [ { "ref": …, "definition": … } ] }`).
- Существующие стратегии получают версию `1` шагом запуска: `IHostedService` до приёма запросов вызывает команду
  `CreateMissingStrategyVersionsCommand`. SQL-миграция не может раскрыть граф, а производственных стратегий может не
  быть — шаг тогда ничего не делает.
- Отклонено: хеш снимка вместо равенства — равенство проще проверить тестом, а хранить хеш незачем.

### 4. Условия торговли в `StrategyRun`

`StrategyRun.Start` получает `TradingConditions`: баланс бота, `InstrumentRules` (`ValueObjects/MarketData`: шаг цены,
шаг объёма, минимальный объём, минимальная сумма) и `FeeSchedule` (ставки лимитки и рынка, правило валюты по категории).
`PositionBook` заменяется на `Account`: свободные деньги, резервы стоящих лимитных входов, позиция.

- `OrderFilled` получает `Fee` и `FeeAsset` (`Quote`, `Base`). Комиссию считает источник событий (симулятор, потом
  биржа), а движок только учитывает.
- Учёт (спек «Учёт позиции», «Свободные деньги»): вход лонга — `cash −= price × qty`, объём `+= qty − baseFee`,
  вложено `+= price × qty + quoteFee`; выход лонга — `cash += price × qty − quoteFee`, вложено `−= avg × qty`. Вход шорта
  — `cash −= price × qty + quoteFee` (обеспечение), вложено `+= price × qty − quoteFee`; выход шорта — обеспечение
  закрытого объёма (`entryNotional × qty / quantity`) плюс `(avgEntry − price) × qty`, минус комиссия. Стоимость
  входа шорта для проверки денег — `price × qty` плюс комиссия.
- Проверка денег до `Place`: стоимость входа с комиссией в валюте котировки не больше свободных денег; рыночный вход
  объёмом оценивается по close последнего бара. Отказ увеличивает счётчик пропущенных ордеров узла.
- Округление в одном месте перед `Place`, и `hold-limit` сравнивает округлённые цену и объём с ордером — иначе ордер
  переставлялся бы из-за десятого знака. Объём выхода — не больше округлённого вниз объёма позиции.
- Остаток позиции меньше минимального объёма после выхода закрывает позицию; в бэктесте он остаётся монетой на счёте
  и входит в капитал по close.
- Выход `free` у `position` — новый пин каталога; совместимое добавление для сохранённых графов.

### 5. Симулятор и прогон комбинации

`Domain/Services/Backtests`:

- `ParameterGrid` — число комбинаций (с проверкой переполнения `long`) и комбинация по номеру: смешанная система
  счисления, параметры по имени ординально, последний меняется быстрее всех.
- `BacktestReplay` — прогон одной комбинации на общем неизменяемом массиве свечей: `StrategyRun`, стоящие ордера с
  моментом активации, очередь событий. На свече: активные ордера по пути цены (спек «Путь цены внутри свечи»), каждое
  исполнение — событие стратегии, её команды обрабатываются сразу (постановка — с активацией со следующей свечи,
  отмена — `OrderCancelled` в очередь), затем закрытие бара. Цикл событий одной свечи заканчивается, когда очередь
  пуста.
- `IReplayObserver` — наблюдатель исполнений и закрытий свечей. `MetricsObserver` копит метрики спека
  `backtest-results`; `DetailsObserver` дополнительно собирает исполнения, сделки и корзины кривой капитала. Результат и
  детали считает один и тот же `BacktestReplay`, поэтому метрики деталей совпадают с сохранёнными, и тест это проверяет.
- Всё в `decimal`, время — время свечей; `TimeProvider` используется только для скорости и времени расчёта.

### 6. Бэктест — отдельный агрегат

`Backtest` (`Domain/Entities/Backtests`): бот, стратегия и номер версии, инструмент, интервал, период, спецификации
параметров (значение или диапазон), `SimulationSettings`, `InstrumentRules`, режим поиска, статус, причина ошибки,
идентификатор задачи загрузки, фактическое начало и пропуски свечей, прогресс (загружено/ожидается, посчитано/всего),
скорость, прерывания без продвижения, время создания, начала и конца. Переходы статусов — методы с unit-тестами.

- Результаты — таблица `backtest_results`: номер комбинации (ключ вместе с бэктестом), значения параметров `jsonb`,
  метрики отдельными `numeric`-колонками (для `ORDER BY` по белому списку кодов метрик), время расчёта. Вставка
  `ON CONFLICT DO NOTHING` — повтор после рестарта ничего не дублирует.
- «Бот изменился» вычисляется при чтении: последняя версия стратегии бота больше версии бэктеста или инструмент или
  интервал бота другие.
- Удаление бота — `ON DELETE CASCADE` на `backtests.bot_id` и `backtest_results.backtest_id`.

### 7. Выполнение бэктеста

`RunBacktestCommand(backtestId)` через `IBacktestQueue` (`Ports/Backtests`) и `BacktestBackgroundService` — как у
загрузки свечей; `BacktestInitializationService` при старте ставит незавершённые бэктесты в очередь.

1. `LoadingCandles`: ожидаемые open time периода — `Interval`; если чего-то нет, создаётся `CandleImportJob` на период
   и ставится в `ICandleImportQueue`, бэктест хранит его идентификатор и опрашивает раз в секунду задачу и число
   сохранённых свечей (прогресс). После рестарта бэктест ждёт ту же задачу.
   - Уточнение к интервью: владельцу было сказано, что бэктест выполнит загрузку в своём прогоне, не дожидаясь чужой
     очереди. При реализации выбрано ожидание задачи в очереди загрузок: иначе после рестарта
     `CandleImportInitializationService` и продолжение бэктеста выполняли бы одну задачу дважды одновременно. Цена —
     бэктест ждёт загрузки, стоящие в очереди перед ним. Владелец принял это при ревью артефактов.
2. `Running`: свечи периода читаются один раз; номера без результата делятся между потоками
   (`Parallel.ForEachAsync`, `Backtests:MaxParallelism`, по умолчанию `Environment.ProcessorCount − 1`, минимум 1).
   Результаты копятся в канале и пишутся пачками не реже раза в секунду вместе с прогрессом и скоростью.
3. При каждой записи пачки обработчик перечитывает статус: `Cancelled` (отмена) или отсутствие бэктеста (удалён бот)
   останавливает потоки. Один механизм для процесса API и будущего Worker, без реестра токенов в памяти.
4. Прерывания без продвижения — как у загрузки: счётчик растёт при постановке `Running` в очередь при старте и
   сбрасывается сохранённым результатом; третье — `Failed`.

Отмена: `Pending` и `LoadingCandles` переходят в `Cancelled` сразу (задача загрузки продолжается сама — свечи
пригодятся); `Running` — по пункту 3.

### 8. Правила инструмента и настройки

- Новый порт `IInstrumentRulesProvider` (`Ports/MarketData`) с реализацией в `BybitMarketDataClient`: спот —
  `priceFilter.tickSize`, `lotSizeFilter.basePrecision`, `minOrderQty`, `minOrderAmt`; `linear` — `tickSize`, `qtyStep`,
  `minOrderQty`, `minNotionalValue`. Через `ExchangeResilienceExecutor`; недоступность — `ExchangeUnavailableException`,
  ответ 503, как у создания загрузки.
- `appsettings.json`, раздел `Backtests`: `MaxCombinations` (10000), `MaxParallelism`, `DefaultFees` — по категориям
  ставки лимитки и рынка (`spot` 0.1 % и 0.1 %, `linear` 0.02 % и 0.055 % — базовые ставки Bybit на 2026-11-01; Bybit
  предупреждает, что в отдельных регионах они другие, поэтому их можно переопределить в бэктесте).

| `GET /api/backtests/{id}/results/{combination}/details` | 200 с исполнениями, сделками, кривой капитала; 404 |
| `POST /api/backtests/{id}/cancel` | 204; 404; 409 для завершённого |

`GET /api/strategies/{id}` получает `version`; `PUT` и `DELETE /api/strategies/{id}` — 409 с расширением `bots`
(список ботов и их ошибок). Числа — десятичные строки, как у свечей; время — с `Z`. Детали считаются синхронно в
запросе: один прогон, секунды на длинном периоде.

### 10. Хранилище

Миграция `202611020001`: `strategy_versions` (`strategy_id` → `strategies` `ON DELETE CASCADE`, `number`,

## Risks / Trade-offs

- [Изменение очень большое: бот, версии, движок, симулятор, метрики, фон] → задачи сгруппированы так, что «боты и
  версии», «движок и симулятор» и «бэктест в фоне и API» можно выпустить тремя PR одной ветки фичи.
- [Перебор нагружает процессор процесса API, API отвечает медленнее] → `MaxParallelism` по умолчанию оставляет ядро;
  Worker — изменение 2.1.
- [Округление меняет команды эталонных тестов `StrategyRun` (например, `100 / 99`)] → эталонные значения
  пересчитываются вместе с задачей округления, с правилами инструмента в фикстуре.
- [Агрегат библиотеки теперь грузит ботов и последние снимки на каждое сохранение] → приемлемо для одного владельца, как
  решено в фиче 1; пересмотреть с пользователями.
- [Свечи периода целиком в памяти: год 1-минуток ≈ 525 тыс. свечей, десятки МБ] → один массив на бэктест, общий для
  потоков; бэктесты идут по одному.
- [Рыночный вход объёмом проверяется по close, исполняется по Open со сдвигом] → перерасход возможен только при гэпе;
  у эталонных стратегий входы заданы суммой.
- [Модель шорта упрощена: плечо 1, без funding и ликвидаций] → так решено в фиче 1 («без плеча, funding и ликвидаций»).
- [Базовые ставки Bybit зависят от региона] → ставки переопределяются в бэктесте и в `appsettings`.
- [Бэктест ждёт загрузки в общей очереди загрузок] → осознанно, чтобы задача не выполнялась дважды после рестарта.

## Migration Plan

Миграция только добавляет таблицы. Шаг запуска создаёт версию `1` для каждой стратегии без версий; повторный запуск
ничего не меняет. Откат — предыдущая версия сервиса: новые таблицы она не читает. Удаление стратегии, на которой есть
боты, в ней упрётся во внешний ключ `bots.strategy_id` и закончится ошибкой 500, а не 409; данные при этом не
портятся. Production это изменение не затрагивает до отдельного деплоя.
