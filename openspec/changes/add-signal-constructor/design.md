# Design

## Context

Шаг 2 (`add-signal-preview`, в архиве) дал:

- API стенда `ProfitFox.Bench.Presentation` на `localhost:5240` с `GET /api/instruments`, `GET /api/hypotheses` и
  `POST /api/preview`;
- страницу `frontend/src/preview` с полем JSON, графиком lightweight-charts и списком ошибок; роутера нет.

Движок `ProfitFox.Engine.Strategy` читает и проверяет граф (`StrategyGraph.ReadSignal` возвращает все ошибки с
местом), пишет его обратно (`StrategyGraph.Write`) и держит каталог из десяти узлов H0001. `NodeCatalog` умеет только
`Find(name)`. Расположения узлов в формате графа нет.

Предпросмотр одной пары идёт около 12 с, и почти всё это время уходит на сервис данных (замер в архивном design.md шага
2). Прогон стенда отклоняется при любых незакоммиченных файлах, кроме журнала и отчётов (`GitRepository.Changed`).

Образец редактора — profit-fox-v2 (`frontend/src/modules/graph-editor`, `pages/strategy-editor`):

- полноэкранный холст `@xyflow/react` с плавающими панелями;
- проверка только на сервере с задержкой, ответы на устаревшие правки отбрасываются;
- черновики в localStorage;
- ступенчатая раскладка по глубине.

Оттуда берутся идеи, а не код целиком. Чего у v2 нет и что здесь новое: предпросмотра в редакторе и хранения файлами.

Решения владельца от 2026-11-19 (опрос перед этим изменением):

- сигналы хранятся файлами на Маке, в шаге 4 переезжают в базу;
- гипотеза держит копию графа сигнала;
- узлы только существующие;
- предпросмотр — нижней панелью;
- запуск по кнопке, история последних 5 пар держится в памяти;
- граница шага такая, как в proposal.md.

## Goals / Non-Goals

**Goals:**

- Граф сигнала собирается и правится на холсте без ручного JSON, и правило проверки одно — то, что в движке.
- Цикл «поменял порог → нажал Показать → посмотрел метки» на уже открытой паре занимает меньше секунды.
- Редактор не знает узлов в коде: новый вид в каталоге появляется в палитре без правок фронтенда.
- Редактор пишется так, чтобы в шаге 5 принять второй вид документа, стратегию, не переписывая холст.

**Non-Goals:**

- Одновременная правка из двух вкладок или с двух машин: последняя запись побеждает, как в v2.
- Отмена и повтор правок (undo/redo), копирование узлов через буфер, выбор нескольких узлов рамкой.
- E2E-тесты в браузере (Playwright): в репозитории их нет, холст проверяется руками на реальных данных.
- Создание и правка гипотез любым путём, кроме уже существующих файлов.

## Decisions

### 1. Файл сигнала: граф и расположение рядом, а не вместе

```json
{
  "name": "funding-high",
  "description": "Фандинг впервые не ниже порога",
  "graph": { "formatVersion": 1, "parameters": [], "outputs": [], "nodes": [], "wires": [] },
  "layout": { "p": { "x": 0, "y": 0 }, "rate": { "x": 0, "y": 120 } }
}
```

`graph` — ровно формат `strategy-graph`, его пишет `StrategyGraph.Write`. Поэтому копия в гипотезу в шаге 4 — это
просто `graph`, а перетаскивание узла не меняет ни байта графа и не меняет хэш будущей гипотезы. Имя файла совпадает с
`name`: так сигнал однозначно адресуется в URL.

Имя — `[a-z0-9]+(-[a-z0-9]+)*`, не длиннее 64. Только строчные буквы, потому что файловая система Мака не различает
регистр, и `Funding.json` с `funding.json` были бы одним файлом.

*Отвергнуто:*

- положение внутри узлов графа, как `layout` в графе v2: в шаге 4 его пришлось бы вырезать перед хэшем, и формат
  `strategy-graph` разошёлся бы между стендом и редактором;
- отдельный файл `<имя>.layout.json`: два файла на один сигнал легко рассинхронизировать при переименовании.

### 2. Библиотека сигналов в `ProfitFox.Bench`, контроллеры в Presentation

`ProfitFox.Bench.Signals.SignalLibrary` над папкой `bench/signals/`:

- список;
- чтение;
- создание, при котором занятое имя — ошибка;
- замена существующего;
- переименование;
- удаление.

Запись идёт во временный файл рядом и переименованием, чтобы оборванная запись не оставила половину JSON. Граф перед
записью проверяется `StrategyGraph.ReadSignal`; при ошибке файл не трогается. API пишет файлы, но не коммитит: коммит
остаётся за владельцем.

Контракт:

- `GET /api/signals` — `[{ name, description?, error? }]` в порядке имени;
- `GET /api/signals/{name}` — `{ name, description?, graph, layout }`, `404` если нет, `422` с `error` если файл не
  читается (редактор открывает его только для чтения и показывает ошибку);
- `POST /api/signals` — создать `{ name, description?, graph, layout }`. Ответы:
  - `201`;
  - `409`, если имя занято;
  - `400` с `errors`, если имя недопустимо или в графе есть ошибки;
- `PUT /api/signals/{name}` — заменить `{ description?, graph, layout }`: `200`, `404` или `400` с `errors`;
- `POST /api/signals/{name}/rename` — `{ to }`: `200`, `404` или `409`;
- `DELETE /api/signals/{name}` — `204` или `404`;
- `POST /api/signals/validate` — `{ graph }` → `200 { errors }`. История не читается, граф с ошибками — обычный ответ.

Копирование — это `GET` и `POST` под новым именем с фронтенда, отдельного эндпоинта не нужно. Ошибки — те же
`RequestError`, что у предпросмотра, плюс `field` = `name` для имени.

*Отвергнуто:* `PUT` как «создать или заменить» — тогда первое сохранение нового сигнала молча перезаписало бы
существующий с тем же именем.

### 3. Каталог узлов для редактора

`GET /api/nodes` отдаёт для каждого вида:

- `kind`, `title`, `group`;
- `inputs` и `outputs` — `[{ name, type }]`;
- `settings` — `[{ name, values, default? }]`;
- `pinsFromGraph` — `parameters` или `outputs` у двух особых узлов.

В движке `NodeCatalog` получает публичный `All`, перечисление видов; расчёт узлов не меняется. Пины обычных видов
берутся у `NodeKind.Inputs`/`Outputs` на пустом графе.

Названия и группы по-русски («Данные»: свеча, фандинг, предыдущее; «Логика»: сравнить, и, или, не, впервые) хранит
`ProfitFox.Bench.Presentation` в одной таблице. Тест проверяет, что у каждого вида каталога есть название. Так новый
узел из `add-indicator-nodes` требует правки только бэкенда, а фронтенд строит палитру, пины и выпадающие списки
настроек из ответа.

*Отвергнуто:* названия в движке — это слова интерфейса, а движок читают стенд и бот.

### 4. Кэш истории предпросмотра в памяти

`SignalPreview` получает `PreviewHistoryCache`: до 5 записей по ключу «id пары + таймфрейм», вытеснение давно не
использованных. Запись — свечи, окна покрытия и выплаты фандинга разведки, то есть всё, что сейчас читает `Run`.

Работает это так:

- одновременные запросы одного ключа ждут одно чтение (`Task` в словаре под замком);
- упавшее чтение из кэша убирается, чтобы следующий запрос попробовал снова;
- проверка графа и пары идёт до кэша, как сейчас, поэтому неверный запрос по-прежнему не читает историю.

Кэшу ничего не грозит устареть: разведка кончается `2026-05-16 00:00`, и её история уже покрыта. Объём записи мал: у
4USDT на 4h это 1 074 свечи и 1 318 выплат, на 1h свечей примерно вчетверо больше.

*Отвергнуто:*

- кэш на диске: он переживал бы перезапуск, но это второе хранилище истории, которое надо сбрасывать при перекачке на
  soyo-02;
- ускорять сервис данных здесь: это задача `profit-fox-market-data`, кэш её не отменяет.

### 5. Фронтенд: роутер, модуль редактора, страницы

Добавляются `@tanstack/react-router` (как в v2) и `@xyflow/react`. Раскладка:

- `src/modules/graph-editor/model` — чистые функции без React:
  - граф ↔ узлы и провода xyflow;
  - раскладка по глубине;
  - свободный `id` нового узла;
  - переименование `id` вместе с проводами и `layout`;
  - сопоставление ошибок местам;
  - сравнение черновика с файлом.
- `src/modules/graph-editor/ui` — холст, узел, палитра, карточки «Узел», «Параметры», «Ошибки», «JSON», плавающие
  панели.
- `src/modules/graph-editor/document.ts` — правила вида документа. У сигнала они такие: выходы — ровно `entry` типа
  «событие», узлы `parameters` и `outputs` по одному и не удаляются, палитра без них. Стратегия в шаге 5 добавит свой
  вид, не трогая холст.
- `src/pages/signals` — список и редактор; `src/pages/hypotheses` — гипотеза только для чтения.
- `src/preview` превращается в панель предпросмотра. `CandleChart`, `EventList`, `ErrorList` и функции `preview.ts`
  остаются, `PreviewPage` и поле JSON уходят.

Маршруты:

- `/` ведёт на `/signals`;
- `/signals` — список сигналов и гипотез;
- `/signals/new/<id черновика>` — новый сигнал;
- `/signals/<имя>` — редактор сигнала;
- `/hypotheses/<id>` — граф гипотезы только для чтения.

Редактор открывается без шапки приложения, во весь экран, как в v2.

### 6. Холст и правка

- **Раскладка.** Узел без положения ставится ступенчато: колонка — глубина от источников, порядок в колонке — по
  порядку узлов в графе. Ширина узла фиксирована (200 px), поэтому DOM мерить не нужно. Первая правка закрепляет
  положения всех узлов. Кнопка «Разложить» очищает `layout`, и это обычная правка.
- **Провода.** xyflow `isValidConnection` пропускает только пины одного типа. Новый провод на занятый вход заменяет
  прежний: на вход по формату приходит не больше одного провода, а «провод и значение сразу» — ошибка формата, поэтому
  при подключении значение входа из `inputs` убирается.
- **Значения на пине.** Поле на неподключённом входе числа или длительности; для логического — переключатель. Число
  хранится строкой до отправки и пишется в JSON числом без потери точности: `0.0005` остаётся `0.0005`, как требует
  `strategy-graph`.
- **Id узла.** Новый узел получает `<вид>-<n>` со свободным `n`. Переименование в карточке «Узел» переносит провода и
  `layout`. Совпадение id ловит серверная проверка, отдельного правила на фронтенде нет.
- **Проверка.** `POST /api/signals/validate` идёт через 0,4 с после последней правки. Предыдущий запрос отменяется,
  ответ сверяется со счётчиком правок. «Сохранить» и «Показать» доступны, только когда последняя проверка вернулась
  без ошибок.

### 7. Черновики

localStorage, ключи `profit-fox:draft:signal:<имя>` и `profit-fox:draft:signal-new:<id>`, значение
`{ savedAt, description, graph, layout }`. Черновик пишется через 300 мс после правки и удаляется при сохранении или
«Отбросить». При открытии он сравнивается с файлом по графу и расположению. Если есть разница, редактор показывает
вопрос «Восстановить или отбросить» с числом отличающихся узлов и проводов. Уход со страницы с несохранёнными правками
перехватывают `beforeunload` и блокировщик роутера.

Переименование сохранённого сигнала переносит его черновик на новый ключ. Новый сигнал при первом сохранении спрашивает
имя, после `201` черновик `signal-new` удаляется и открывается `/signals/<имя>`.

### 8. Панель предпросмотра

Нижняя панель на всю ширину, сворачивается, высота перетаскивается и запоминается в localStorage:

- **Строка запуска:** поиск пары, таймфрейм (`1h`, `4h`, `1d`) и «Показать». Пара и таймфрейм запоминаются в
  localStorage для каждого сигнала.
- **Слева:** график свечей с метками.
- **Справа:** список событий в UTC.
- **Над графиком:** подпись «Разведка до 2026-05-15 включительно, история пары с …».

Клик по событию ставит видимый диапазон графика вокруг метки. Запрос идёт в тот же `POST /api/preview` с графом из
редактора. Если граф изменился после показанного результата, панель пишет «Граф изменён, нажмите Показать» и оставляет
прежние метки.

### 9. `bench/signals/` не делает дерево грязным

`GitRepository.Changed` исключает пути под `bench/signals/` так же, как журнал и отчёты. Сигнал в прогоне не
участвует: `bench run` читает только папку гипотезы, а гипотеза держит свою копию графа. Без исключения любое сохранение
в конструкторе блокировало бы прогон до коммита.

### 10. Тесты

- **Интеграционные** (`ProfitFox.Tests.Integration/Bench/Presentation`, поддельный сервис данных из шагов 1–2):
  - сигналы: создание, замена, отказ с ошибками, занятое имя, переименование, удаление, испорченный файл в списке;
  - `validate` без запросов истории;
  - каталог;
  - кэш: поддельный сервис считает запросы, шестая пара вытесняет первую.
- **Unit:** `GitRepository.Changed` с путями `bench/signals/`; запись сигнала не оставляет временных файлов.
- **Vitest:**
  - модель редактора: граф ↔ xyflow туда и обратно без потерь, раскладка H0001, id и переименование, ошибки по местам,
    сравнение черновика;
  - страницы: черновик восстанавливается, «Сохранить» недоступна при ошибках, ответ на старую правку не показывается,
    «Граф изменён».

Сам холст xyflow в jsdom не рисуется — его проверяет ручная проверка на реальных данных.

## Risks / Trade-offs

- **[API пишет в рабочее дерево репозитория]** → пишет только в `bench/signals/`, имя проверяется до пути, поэтому
  `../` невозможен. API по-прежнему слушает только localhost.
- **[Удалённый незакоммиченный сигнал не вернуть]** → удаление спрашивает подтверждение с именем. История правок есть
  только у закоммиченных файлов, и это видно в git.
- **[Узлы налезают друг на друга, когда растут: новый параметр добавляет выход]** → как в v2, кнопка «Разложить».
- **[Кэш держит историю, а сервис данных на soyo-02 перекачали]** → история разведки неизменна по правилам стенда.
  Перезапуск API очищает кэш, если что-то всё же поменялось.
- **[Две вкладки на один сигнал перезапишут друг друга]** → один владелец на одной машине. Конфликт версий вводится с
  базой в шаге 4.
- **[Названия узлов в Presentation могут отстать от каталога]** → тест падает на виде без названия.
- **[`422` для испорченного файла — нестандартный ответ]** → редактору нужно отличать «нет файла» от «файл не
  читается», а `400` значил бы ошибку запроса.

## Migration Plan

Миграций данных нет. Папка `bench/signals/` создаётся при первом сохранении. Страница предпросмотра заменяется
редактором; её возможности сохраняются: гипотеза открывается по `/hypotheses/<id>`, JSON вставляется карточкой.
Откат — вернуть ветку: файлы сигналов стенд не читает.
