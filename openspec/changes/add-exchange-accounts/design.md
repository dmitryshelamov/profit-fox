# Design

## Context

Мотив и объём — в `proposal.md`. Здесь только то, что определяет подход.

- Стенд ходит наружу только в сервис данных (`Clients/MarketData`: gRPC и REST). Клиента Bybit и пакета `Bybit.Net` в
  репозитории нет, подписанных запросов стенд не делал.
- Хранение — Dapper + Npgsql + FluentMigrator, PostgreSQL 17. Схему накатывает API при старте (`MigrateBench`), Worker
  ждёт её (`BenchSchema.WaitFor`). Единицы работы и outbox нет: каждый вызов репозитория целый в своей транзакции.
- Ошибки запроса контроллер отдаёт сам: `422` с `ErrorResponse` (код, причина, поле), `404` — `ProblemDetails`, `502` —
  недоступный сервис данных. Общего обработчика исключений нет.
- Секрет в production один — `PROFIT_FOX_DB_PASSWORD` в `~/profit-fox/.env.prod` на firebat-01 (режим 600). База
  опубликована на LAN-адресе firebat-01, и Worker'ы firebat-02 ходят в неё тем же пользователем: они смогут прочитать
  таблицу аккаунтов.
- Страница и `/api` открыты в локальной сети без входа. Владелец оставил так и для торговли («Без защиты»).
- В `profit-fox-v2` аккаунты уже делались (`2026-11-02-add-exchange-accounts`). Оттуда взяты проверенные там факты о
  Bybit: пакет, запрос прав ключа, коды отказа. Решения о продукте приняты заново, список — в `proposal.md`.
- Правило слоёв и папок — README, «Слои»; его держит сборка (`Directory.Build.targets`). Из образца не взят NSubstitute:
  подделки пишутся руками.

## Goals / Non-Goals

**Goals:**

- Секрет ключа нельзя получить ни из ответа API, ни из журнала, ни из дампа базы без мастер-ключа.
- Ключ, которым можно вывести деньги, в стенд не попадает.
- Клиент Bybit в тестах не ходит в интернет: адрес биржи подменяется.
- `take-idea-trades` получает готовое: аккаунт по идентификатору и расшифровку секрета на один запрос.

**Non-Goals:**

- Вход по паролю, проверка Origin, разграничение прав.
- Ротация мастер-ключа и перешифровка секретов.
- Кэш баланса и фоновая проверка ключей.
- Общий ограничитель запросов к Bybit: запросов единицы, и все по клику.

## Decisions

### 1. Секрет шифруется AES-256-GCM мастер-ключом из настроек

Порт `ISecretProtector` в `Application/Ports/Security` с `Protect(accountId, secret)` и `Reveal(accountId, protected)`;
адаптер `AesGcmSecretProtector` в `Infrastructure/Security`. На каждое шифрование — свежий случайный nonce 12 байт, тег
16 байт. Связанные данные — `exchange-account:{id}:secret`: зашифрованный секрет, переписанный в чужую строку, не
расшифруется. Открытый текст после запроса затирается.

Мастер-ключ — `ExchangeAccounts:MasterKey`, base64 ровно 32 байт. Проверяется при старте (`ValidateOnStart`): без ключа
или с ключом другого вида API не поднимается, сообщение называет настройку и не содержит значения. Ключ разработки лежит
в `appsettings.Development.json`, как пароль dev-базы; в общем `appsettings.json` ключа нет. В production значение
приходит переменной `ExchangeAccounts__MasterKey` из `.env.prod` (`PROFIT_FOX_MASTER_KEY`).

Почему не «секрет в настройках сервера без базы»: владелец выбрал ввод в интерфейсе и несколько аккаунтов. Почему не
шифрование средствами PostgreSQL (`pgcrypto`): ключ пришлось бы передавать в каждом запросе к базе, и он попал бы в её
журнал.

### 2. Мастер-ключ получает только API

Worker'ы в этом изменении ключ не получают и стартуют без него. База доступна Worker'ам firebat-02, но без мастер-ключа
строка аккаунта для них — шифртекст. `take-idea-trades` даст ключ торговому Worker'у на firebat-01 и только ему.

### 3. Таблица `exchange_accounts`

`id uuid`, `name text`, `api_key text`, `secret_nonce bytea`, `secret_ciphertext bytea`, `secret_tag bytea`,
`uid bigint`, `created_at timestamptz`. Уникальные индексы: `lower(name)` и `uid`. Шифруется только секрет: ключ API
показан в интерфейсе целиком и без секрета бесполезен.

Сущность `ExchangeAccount` в `Domain/Entities/Accounts` секрета не несёт. Репозиторий `IExchangeAccountRepository`:
`AllAsync`, `FindAsync`, `AddAsync(account, protectedSecret)` (ложь — имя или UID заняты, по `23505` и имени
ограничения), `RenameAsync`, `DeleteAsync`, `SecretAsync(id)`. Зашифрованный секрет наружу отдаёт только `SecretAsync`,
и зовут его обработчики, которым нужен запрос к бирже.

### 4. Клиент Bybit — `Bybit.Net`, клиент на вызов

Порт `IExchangeKeyInspector` в `Application/Ports/Exchange`: `InspectAsync(apiKey, secret)` → права, UID, вид аккаунта;
`FreeAsync(apiKey, secret)` → свободные деньги. Адаптер `BybitAccountClient` в `Infrastructure/Clients/Bybit` на каждый
вызов строит `BybitRestClient` поверх типизированного `HttpClient` с учётными данными этого вызова и освобождает его.
Провайдер клиентов пакета не используется: он кэширует клиента вместе с секретом и создаёт свой `HttpClient`, который в
тесте не подменить.

Версия пакета — последняя стабильная на день применения, не ниже `7.7.0` (на ней работал v2); `NU1903`/`NU1904` в
сборке — ошибки, уязвимая версия не пройдёт. Адрес Bybit — `Bybit:RestAddress`; пусто — боевой.

Почему не свой HTTP-клиент с подписью: `take-idea-trades` нужны заявки, позиции и исполнения — писать и проверять
подпись и модели руками дороже зависимости, а поведение пакета на этих запросах в v2 уже проверено.

### 5. Правила ключа и порядок проверок

Запрос — `/v5/user/query-api`. Правила в `Domain/Services/Accounts/ExchangeKeyRules`, проверяются в этом порядке, первая
причина — ответ: ключ «только чтение»; аккаунт не единый торговый; у ключа есть право вывода
(`Wallet` содержит `Withdraw`); нет торговли контрактами (`ContractTrade` без `Order` или без `Position`). Права спота
не нужны и не мешают.

Порядок обработчика `AddAccountCommandHandler`: правила полей (без сети) → запрос к Bybit → правила ключа → шифрование →
запись. Занятые имя и UID ловит уникальный индекс при записи: два одновременных добавления одного аккаунта не пройдут
оба.

### 6. Ответы на отказ Bybit

| Что случилось | Исключение Application | Ответ |
|---|---|---|
| Bybit отклонил ключ: `retCode` 10003, 10004, 10005, 10010, 33004 | `ExchangeKeyRejectedException` | `422`, поле `apiKey`, причина от Bybit |
| Нет ответа, HTTP 403, HTTP 5xx, превышен лимит | `ExchangeUnavailableException` | `503` |
| Любой другой отказ (например 10002 — расхождение часов) | `ExchangeException` | `502` с причиной от Bybit |
| Секрет не расшифровался | `SecretUnreadableException` | `409`: аккаунт надо добавить заново |

При запросе баланса отклонённый ключ — тоже `422` с причиной: строка таблицы показывает её вместо числа. Полный ответ
`query-api` в журнал не пишется — в нём есть секрет.

### 7. «Свободно» — доступный остаток единого аккаунта

`/v5/account/wallet-balance` с `accountType=UNIFIED`, поле `totalAvailableBalance`: то, что Bybit готов дать под новую
позицию с учётом залога открытых. Bybit считает его в долларах; стенд показывает число как USDT. Разбивки по монетам и
общего капитала нет: экрану и будущей проверке «хватает ли денег» нужно одно число.

Почему не «остаток USDT минус заблокированное»: в v2 так и было, и залог открытых позиций единого аккаунта не
вычитался — число завышало свободные деньги.

### 8. API

`AccountsController`, `api/accounts`: `GET` — список; `POST` — добавить (`name`, `apiKey`, `secret`); `PUT {id}` —
переименовать; `DELETE {id}`; `GET {id}/balance`. Ответ `AccountResponse`: `id`, `name`, `uid`, `apiKey`, `createdAt`.
Поля секрета в контрактах ответа нет вовсе. Права ключа в ответе не хранятся и не отдаются: принят может быть только
один набор прав, и таблица пишет его текстом.

### 9. Фронтенд

Страница `pages/accounts/AccountsPage.tsx`, маршрут `/accounts`, раздел в `AppShell`. Таблица на `Table`, меню строки на
`Menu`, диалог на `Dialog` с `TextField`; поле секрета — `type="password"`, `autocomplete="off"`, очищается после
любого отказа сервера. Баланс — запрос по кнопке без автообновления, результат живёт в состоянии страницы до ухода с
неё. Макет — `mockups/15-accounts.png`.

### 10. Тесты без Bybit

- Модульные: `ExchangeKeyRules`, правила имени, обработчики на подделках `MemoryExchangeAccountRepository`,
  `FakeKeyInspector` и `FakeSecretProtector`.
- Интеграционные: `AesGcmSecretProtector` (круг, чужая строка, другой ключ); репозиторий на Testcontainers;
  `BybitAccountClient` на `StubHttpHandler` — очередь готовых ответов и запись запросов, чтобы проверить путь, подпись
  в заголовках и разбор `retCode`; контроллер на `BenchTestApplication` с `FakeKeyInspector`.
- Фронтенд: Vitest с `fakeApi`.

Настоящий Bybit в тестах не участвует. Первая проверка на нём — владелец добавляет свой ключ на dev-стенде (задача
группы 7).

## Risks / Trade-offs

- [Сайт без пароля хранит ключи с правом торговли: любой в локальной сети может добавить и удалить аккаунт] → решение
  владельца; вывод денег исключён правилом ключа; секрет наружу не отдаётся.
- [Потерян или сменён мастер-ключ — все секреты не читаются] → `409` с просьбой добавить аккаунт заново; ключи Bybit
  перевыпускаются за минуту. Резервной копии мастер-ключа стенд не делает: он лежит в `.env.prod`.
- [Поведение Bybit на неверном ключе известно по v2 и документации, а не по тесту с настоящим ключом: v2 не проверил
  ответ HTTP 401] → неизвестный код отказа уходит в `502` с текстом Bybit, а не в падение; задача 7.2 записывает, что
  ответила биржа.
- [Права ключа могут измениться на Bybit после добавления, например владелец включит вывод] → стенд этого не увидит.
  Повторная проверка при каждом входе в сделку — в `take-idea-trades`.
- [Bybit считает `totalAvailableBalance` в долларах, а не в USDT] → расхождение — доли процента на курсе USDT; экран
  называет число «свободно», решение о входе повторно проверяет биржа.

## Migration Plan

1. Владелец кладёт `PROFIT_FOX_MASTER_KEY` в `~/profit-fox/.env.prod` на firebat-01 (`openssl rand -base64 32`) до
   выкладки версии. Команду он вводит сам; ключ не попадает ни в репозиторий, ни в чат.
2. Выкладка обычным `deploy.sh`: API накатывает миграцию `exchange_accounts` и стартует с ключом.
3. Откат — предыдущая версия: таблица остаётся и ей не мешает; миграция `Down` удаляет таблицу вместе с секретами.

Если ключа в `.env.prod` нет, `docker compose` остановится на `${PROFIT_FOX_MASTER_KEY:?}` до замены контейнеров:
работающая версия остаётся на месте.
