# Design

## Context

`ProfitFox.Engine.Strategy` пуст (заготовка `Class1.cs`). Engine запрещает часы, файлы, консоль и сеть
(`BannedSymbols.Engine.txt`) и ни на что вне себя не ссылается (`Directory.Build.targets`). Формат графа взят из
`profit-fox-v2` (ADR 0011), правило «узел не меняет поведения» — ADR 0005.

Эталон сигнала — `hypotheses/H0001-funding-short-4h/event.py` Python-стенда. Что он видит (проверено по `market.py`):

- свеча 4 ч имеет `ts` = время закрытия (`open_time + 4h`); оставляются только свечи `complete & minutes_traded > 0`, и
  этот отбор идёт до сдвига, поэтому «прошлая ставка» — ставка на прошлой оставленной свече пары;
- выплата известна в момент выплаты (`PUBLISHED_AFTER_MS["funding"] = 0`), и `join_asof(..., strategy="backward")`
  берёт последнюю выплату с `paid_at ≤ ts`, включая выплату ровно в момент закрытия;
- событие — `rate ≥ 0.0005` и `previous_rate < 0.0005`; `null` в любом из них даёт не-событие (первая свеча пары, пара
  до первой выплаты);
- ставки в снимке — `Float64`.

## Goals / Non-Goals

**Goals:**

- Формат, чтение и проверка составного узла; сигнал H0001 записывается в этом формате.
- Исполнитель с API, которое стенд 1.3 вызывает напрямую из потока `History` без пересборки данных.
- Совпадение событий H0001 с Python на выгрузке из снимка.

**Non-Goals:**

- Значения свечи (OHLCV) в узлах: H0001 их не читает, узел свечи придёт с первой гипотезой, которой он нужен.
- Объявленные входы составного узла, узел `inputs`, вложенность по `ref`: им нечего подавать, пока нет вложения.
- Узлы по всему рынку: в API момента место для них есть, самих узлов нет.
- Отбор свечей (неполные, без сделок): это решает тот, кто подаёт данные.

## Decisions

### Формат — v2 без того, что читает только конструктор или бот

Определение: `formatVersion` (1), `outputs` `[{ "name", "type" }]`, `nodes` `[{ "id", "kind", "settings"?, "inputs"? }]`,
`wires` `[{ "from": "узел.пин", "to": "узел.пин" }]`. Типы пинов `number` и `boolean`; `duration` из v2 войдёт с первым
узлом, который его читает. Неизвестное поле — ошибка, а не пропуск: опечатка в файле гипотезы не должна молча менять
сигнал, а `layout` и прочие поля v2 войдут вместе с кодом, который их читает.

Числа неподключённых входов читаются из JSON сразу в `decimal` (`Utf8JsonReader.GetDecimal`), без `double`.

Альтернатива — пропускать неизвестные поля ради совместимости с файлами v2: отвергнута, файлов v2 здесь нет, а цена
молчаливой опечатки в гипотезе — неверный вердикт.

### Чтение возвращает результат, а не исключение

`StrategyGraphReader` (рабочее имя) принимает строку JSON и возвращает либо определение, либо список ошибок проверки
(узел, пин, настройка или поле и причина). Отдельный вход «читать как сигнал» добавляет проверку «ровно один логический
выход». Engine файлов не читает: стенд читает `hypothesis.json` сам и передаёт текст сигнала.

### Узлы — каталог видов с объявленными пинами и настройками

Каждый вид объявляет входы, выходы, настройки с допустимыми значениями и создаёт экземпляр с состоянием на одну пару.
Проверка графа идёт по этим объявлениям, поэтому новый узел — новый вид в каталоге без правки проверки.

| Вид | Входы | Выходы | Настройки |
|---|---|---|---|
| `funding-rate` | — | `value`: number | — |
| `previous` | `value`: number | `result`: number | — |
| `compare` | `a`, `b`: number | `result`: boolean | `operation`: `ge` \| `lt`, обязательна |
| `and` | `a`, `b`: boolean | `result`: boolean | — |
| `outputs` | объявленные выходы | — | — |

`compare` — один узел с операцией, как в v2, а не узлы `ge`/`lt`: конструктор потом показывает одну карточку. Операции
`gt`, `le` и другие добавляются новыми значениями настройки; прежние значения при этом не меняются (ADR 0005).

«Впервые достигла порога» собирается из `previous`, двух `compare` и `and`, а не отдельным узлом пересечения: узел
`cross` из v2 считает `≤ / >`, а H0001 — `< / ≥`, и под каждый вариант понадобился бы свой узел.

### Отсутствующее значение — `decimal?`, логическое значение — `bool`

Числовой провод несёт `decimal?`; сравнение с `null` даёт `false`, как в v2 и как `null` в фильтре Polars. Логических
`null` нет, поэтому `and` не нужна трёхзначная логика.

### Исполнитель — момент за моментом, состояние по паре

```text
executor.AddFundingPayment(instrumentId, time, rate)
executor.Close(closeTime, candles) → [(instrumentId, closeTime, outputs)]
```

- Граф сортируется топологически один раз при создании исполнителя; на каждой свече момента узлы считаются в этом
  порядке на состоянии её пары. Состояние пары создаётся при первой её свече.
- `previous` хранит значение входа на прошлой поданной свече пары, поэтому пропуск свечи (как отбор Python до `shift`)
  даёт то же, что Python.
- Выплаты хранятся по паре в порядке времени; `funding-rate` на закрытии T берёт последнюю с `time ≤ T`. Выплата со
  временем `≤` последнего посчитанного закрытия отклоняется: иначе результат уже выданного закрытия был бы другим.
- Свеча несёт инструмент, время открытия и закрытия; цены добавятся с узлом свечи.
- Время — UTC (`DateTimeOffset` со смещением 0), инструмент — строковый `instrument_id` каталога market-data, как его
  отдаёт `History`.

Стенд 1.3 читает поток свечей по `open_time`, затем `instrument_id`, собирает свечи одного времени открытия в момент,
перед ним подаёт все выплаты со временем `≤` времени закрытия и вызывает `Close`. Насколько далеко идут данные, решает
он; исполнитель часов не имеет.

Альтернатива — `Close` по одной свече: проще сейчас, но узлам по всему рынку нужен момент целиком, и API пришлось бы
менять под стендом. Альтернатива — исполнитель сам сливает два потока: тогда Engine знает про поток `History`, а он
должен знать только про свечи и выплаты.

### Сверка с Python — по событиям на выгрузке, без исходов

Скрипт выгрузки запускается в `profit-fox-bench` (`uv run`) и пишет фикстуру в тесты:

- окно внутри разведки (ADR 0008), например 2026-01-01 – 2026-03-01, пары — те, у кого в окне есть события `event.py`,
  плюс столько же без событий, всего до 40, чтобы фикстура была в сотни КБ;
- свечи 4 ч после отбора `complete & minutes_traded > 0` (пара, `open_time`, `ts`), выплаты этих пар (пара, `ts`,
  `rate` через `repr` — кратчайшая запись `Float64`, которая читается в `decimal` и сравнивается с `0.0005` так же, как
  `Float64`); выплаты — с начала окна минус 8 ч, чтобы первая свеча окна видела ставку;
- события `event.py`, посчитанные на этой же выгрузке, а не на полных данных: на первой свече окна прошлой ставки нет,
  и это тоже проверяется.

Тест строит граф H0001 из JSON, кормит исполнитель выгрузкой и сравнивает множество (пара, закрытие) с событиями.
Исходы событий не считаются нигде: ни в скрипте, ни в тесте. Скрипт лежит рядом с фикстурой, чтобы выгрузку можно было
повторить.

## Risks / Trade-offs

- [Сигнал на стенде зависит от того, какие свечи подаются: Python отбрасывает неполные и без сделок] → в 1.3 стенд
  подаёт тот же отбор; в этом изменении это записано в спецификации как «прошлое закрытие = прошлая поданная свеча».
- [Пробел в покрытии фандинга делает «последнюю выплату» устаревшей: и Python, и узел видят старую ставку] → как в
  эталоне; покрытие фандинга проверяет стенд в 1.3.
- [Строгий отказ на неизвестных полях ломает чтение файлов v2 с `layout`] → файлов v2 здесь нет; `layout` войдёт с
  конструктором.
- [Фикстура из снимка, которого нет в CI, повторяется только локально] → фикстура коммитится целиком; скрипт нужен
  только для её пересборки.
