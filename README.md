# profit-fox

## Стенд

Стенд — это служба: одна база Postgres, API `ProfitFox.Presentation` для фронтенда и CLI, и от одного до N
процессов `ProfitFox.Worker`, которые считают прогоны стратегий из очереди в базе. Стенды на разных машинах (Мак,
firebat-01) никак не связаны: у каждого своя база и свои Worker'ы. Спецификации — `openspec/specs/strategy-backtest`,
`bench-run-queue`, `strategy-constructor`, `signal-constructor`, `signal-preview`, `strategy-preview`, а для идей и
рынка — `strategy-ideas`, `idea-labels`, `market-live-feed`, `market-overview`, `saved-filters`.

База — единственное хранилище: сигналы и стратегии с версиями, прогоны и их результаты. Новая база пуста: из git в неё
ничего не переносится. Таблицы прежнего стенда гипотез (`hypothesis_versions`, `runs`, `ledger`, `reports`) остаются в
базе как есть, код их не читает.

### Стенд на Маке

Нужны .NET 10, Node 22+, Docker и доступ к сервису данных на soyo-02 (`192.168.8.213`, порты 5237 и 5236).

1. База стенда на `127.0.0.1:5435`:

   ```bash
   docker compose up -d --wait bench-db
   ```

2. API на `http://localhost:5240`. При старте мигрирует базу:

   ```bash
   dotnet run --project backend/src/ProfitFox.Presentation
   ```

3. Worker:

   ```bash
   dotnet run --project backend/src/ProfitFox.Worker
   ```

   Второй Worker — тот же запуск в другом терминале с другим именем:

   ```bash
   Worker__Name=mac-2 dotnet run --project backend/src/ProfitFox.Worker
   ```

4. Страница — Vite на `http://localhost:5173`, запросы `/api` уходят на API:

   ```bash
   npm --prefix frontend install
   ```

   ```bash
   npm --prefix frontend run dev
   ```

Все процессы есть в `.claude/launch.json` (`bench-db`, `bench-api`, `bench-worker`, `frontend`). API и Worker, запущенные
превью Claude Code, могут не видеть локальную сеть; для реальных данных их лучше запускать в терминале. После сна Мака их
перезапускают: соединения с сервисом данных остаются мёртвыми.

Начать с чистой базы — удалить её том:

```bash
docker compose down -v
```

### Прогон

У сохранённой стратегии в редакторе и в меню строки списка есть «Прогнать»: форма запуска с таймфреймами, значениями
параметров (несколько значений дают наборы), началом и концом истории, парами и ставками. Раздел «Прогоны» показывает
очередь, идущие прогоны с ходом по парам и отменой и законченные прогоны; страница прогона — настройки и таблицу наборов,
страница набора — его пары и «Прогнать на остатке истории».

То же из командной строки:

```bash
dotnet run --project backend/src/ProfitFox.Cli -- run funding-short --timeframe 4h --param threshold=0.0005,0.001 --wait
```

Команды `bench`:

- `run <стратегия> [--version N] [--timeframe 1h,4h] [--param имя=v1,v2]… [--from дата] [--until дата] [--pairs A,B]
  [--wait]` — прогон стратегии; `--timeframe` — таймфреймы через запятую из `5m`, `15m`, `1h`, `4h`, `1d`, по умолчанию
  `4h`; с `--wait` печатает таблицу наборов;
- `runs` — очередь и последние прогоны;
- `cancel <id прогона>` — снять из очереди или остановить.

Справка — `bench --help` и `bench <команда> --help`. Адрес стенда — `--bench <адрес>`, иначе `Bench:Url` в `appsettings.json` CLI или переменная `Bench__Url`, по умолчанию
`http://localhost:5240`.

### Как считается прогон

Прогон считает сохранённую версию стратегии на истории каждой пары: свечи таймфреймов и фандинг пары читаются один раз
для всех наборов. У стратегии на паре одна позиция; заявка, пришедшая при открытой позиции, пропускается. У стратегии
вида «категория идей» минутные свечи читаются только в неделях с заявками, и на каждую заявку берётся 20 случайных
входов той же недели: разница со случайным входом — подсказка, а не вердикт. У стратегии вида «для бота» минутные свечи
читаются по всей истории прогона. Прогон несёт номер версии движка (сейчас 4).

**Кэш истории.** У Worker'а и API с папкой кэша (`MarketData:HistoryCache:Path`) закрытая история берётся с диска: один
сжатый файл на пару, вид данных (свечи одного интервала или фандинг) и календарный месяц UTC. Месяц, которого в папке нет,
читается у сервиса данных целиком, даже если прогону нужна одна его неделя, и сохраняется, когда сервис покрыл его целиком
и он кончился раньше текущих суток UTC. Первый прогон пар заполняет кэш, следующие прогоны и предпросмотры тех же пар
читают у сервиса только то, что сохранить нельзя: текущий месяц, месяц листинга, месяцы до него и месяцы с дырой. Ответ
тот же, что у сервиса: хэш данных и числа прогона с кэшем и без него равны, и после конца прогона в расчёт не входит
ничего. В строке журнала Worker'а об окончании прогона — сколько месяцев взято из кэша, сколько сохранено и сколько
запросов ушло сервису (`…, cache: 120 months from the cache, 0 saved, 9 requests to the service`). Битый файл читается у
сервиса заново и заменяется; папка, в которую нельзя писать, даёт `Warning` «The cache of history did not keep …» не чаще
раза в минуту, и история приходит от сервиса. Если сервис данных исправил уже покрытую историю, кэш об этом не узнает:
папку тогда удаляют (на Маке — `rm -rf ~/.cache/profit-fox/history`, на проде — том, см. «Production»). Прогрев сканера
идёт мимо кэша.

### Идеи и рынок

Стратегию вида «категория идей» можно включить на таймфреймах из `5m`, `15m`, `1h`, `4h`, `1d` — колонка «Идеи» в
списке стратегий. Включённая стратегия считается на всех бессрочных USDT-парах Bybit по живым данным: её заявка на
закрытой свече даёт идею — вход по цене минуты после свечи, стоп, цель и срок из узлов выхода, итог по сроку, стопу или
цели с фандингом за время идеи. Раздел «Идеи» показывает открытые идеи с результатом «сейчас» и журнал закрытых со
сводкой по стратегии и таймфрейму; раздел «Рынок» — снимок пар (цена, изменения за 1, 4 и 24 часа, оборот, OI,
фандинг) с открытыми идеями; страница пары — график с живой свечой, метками и линиями идей, OI и фандингом. У сигнала
можно включить метку на идеях (колонка «Метка на идеях» в списке сигналов); встроенная метка «⚡ всплеск» ставится, когда
одна стратегия на одном таймфрейме дала на одной свече не меньше порога идей одной стороны. Над «Рынком» и «Идеями» —
сохранённые фильтры.

**Сканер в Worker'е.** Живые данные ведёт одна служба сканера в одном из Worker'ов: кто первым взял аренду
`scanner_lease` в базе, тот подписывается на живые ленты сервиса данных (минуты, выплаты и ставки фандинга, OI), держит
в памяти последние 25 часов минут всех пар, прогревает графы включённых стратегий историей REST сервиса данных
(`Scanner:WarmupCandles` свечей на пару) и на каждой закрытой свече считает стратегии, метки и снимок рынка. Второй
Worker ждёт и берёт аренду, когда первый перестал её продлевать. Прогоны из очереди Worker считает как прежде, сканер
рядом с ними. На Маке сканер поднимается вместе с Worker'ом (шаг 3 выше): в журнале Worker'а видно взятие аренды и
прогрев, раздел «Идеи» пишет «идёт прогрев: N из M пар», потом — с какого момента идеи считаются без перерыва. Worker
без сканера — `Scanner__Enabled=false`.

**Живые сутки и прогон.** Идея считается так же, как сделка прогона той же версии на той же свече: вход, стоп, цель,
срок и фандинг по тем же правилам. Отличия — в данных: свеча идеи собрана из живых минут ленты, а прогон читает
сохранённую историю, поэтому минута, пришедшая после расчёта свечи, или исправленная сервисом позже история могут дать
другое значение; идея не меняется задним числом.

**Простой сканера.** Пока никто не держит аренду (Worker'ы остановлены, деплой), новых идей нет — раздел «Идеи»
предупреждает об этом через минуту. После старта сканер догоняет ленты за последние 24 часа: открытые идеи закрываются
по минутам простоя (стоп, цель, срок), свечи, закрытые в простое, идей не дают. Разрыв дольше 24 часов исключает
открытые идеи («нет данных»): их итог не считается и в сводку не входит.

**Молчащая лента.** Если поток минут молчит дольше `Scanner:FeedSilence` без ошибки (полуоткрытое соединение, зависший
сервис данных), Worker обрывает его и подписывается снова с последней минуты, как после разрыва; в журнале — строка
`Warning` «The feed minutes told nothing for …». Канал gRPC сам проверяет связь каждые 30 секунд. Пока минут нет, свечи
не закрываются, и раздел «Идеи» пишет, что лента догоняет или молчит. Когда лента вернулась, свечи, закрытые за время
молчания, считаются по её догону и дают идеи, как живые; без перерыва идеи считаются с момента возврата. Обычный обрыв
потока короче этого срока (перезапуск сервиса данных) перерывом не считается: лента подписывается снова с последней
минуты минус пять минут, и этот повтор сканер считает догоном, пока лента не затихнет.

**Выплата фандинга и свеча.** Выплата со временем `T` относится к свече, закрытой после `T`, — в прогоне, в
предпросмотре и вживую (версия движка 4): сервис данных отдаёт выплату через одну–три минуты после её времени, и свеча,
закрытая в `T`, о ней ещё не знает. Живое закрытие свечи выплату не ждёт; выплата, пришедшая после закрытия, видна графу
на следующей свече. Позиция платит или получает выплату, время которой позже входа и не позже выхода, как и прежде.

Живая свеча страницы пары идёт потоком `GET /api/market/pairs/{пара}/live` от API, а не от Worker'а: API подписывается
на минуты с незакрытыми свечами, только пока страница пары открыта.

### Настройки

API (`backend/src/ProfitFox.Presentation/appsettings.json`) и Worker
(`backend/src/ProfitFox.Worker/appsettings.json`):

- `ConnectionStrings:Bench` — база стенда; для Мака она в `appsettings.Development.json`;
- `MarketData:GrpcUrl`, `MarketData:RestUrl` — адреса сервиса данных;
- `MarketData:HistoryCache:Path` — папка кэша истории прогонов и предпросмотров; пустая — кэша нет, всё читается у
  сервиса данных; `~/` в начале — домашняя папка. В `appsettings.json` пустая, в `appsettings.Development.json` API и
  Worker'а — `~/.cache/profit-fox/history`: одна папка на оба процесса Мака и на все рабочие копии репозитория. Несколько
  процессов одной машины могут делить одну папку;
- `MarketData:HistoryCache:MaxSizeGb` (40) — сколько гигабайт может занять папка кэша; больше — удаляются месяцы, которые
  дольше всех не читались. Значение не больше нуля не даёт процессу запуститься;
- `Worker:Name`, `Worker:LeaseDuration` (30 с), `Worker:LeaseRenewal` (10 с), `Worker:PollInterval` (1 с) — Worker;
  аренда сканера берёт те же длительность и продление;
- `Scanner:Enabled` (`true`) — может ли Worker вести живые данные; `Scanner:CloseDelay` (15 с) — сколько после конца
  свечи ждать её последних минут; `Scanner:WarmupCandles` (500) — свечей истории на прогрев графа;
  `Scanner:WarmupParallelism` (4) — пар прогревается сразу; `Scanner:WarmupRetry` (1 мин) — когда снова спросить пару,
  которую сервис данных ещё догружает; `Scanner:ReconcileInterval` (5 с) — как часто перечитывать включённые стратегии и
  метки; `Scanner:ExitWait` (90 с) — сколько закрытая идея ждёт выплату в момент выхода; `Scanner:ExitPaymentWait`
  (10 мин) — сколько идея, чей выход приходится на время выплаты её пары, ждёт эту выплату: прогон считает выплату в
  момент выхода, а сервис данных отдаёт её через одну–три минуты; дольше — идея закрывается без неё, в журнале `Warning`
  «No payment of … came within …»; `Scanner:TickInterval` (1 с) — шаг часов сканера при молчащей ленте;
  `Scanner:QueueCapacity` (20 000) — сколько записей живых лент ждут сканер: одна настройка на обе очереди, очередь
  чтения лент и очередь сканера; полная очередь останавливает чтение, ничего не теряя;
  `Scanner:FeedSilence` (3 мин) — сколько лента минут может молчать: дольше — поток обрывается и подписывается снова с
  последней минуты, а раздел «Идеи» перестаёт писать, что идеи считаются без перерыва; одна настройка на сторожа ленты и
  состояние сканера;
- `ExchangeAccounts:MasterKey` — мастер-ключ секретов аккаунтов Bybit, у API и у торгового Worker'а (разделы «Аккаунты» и
  «Сделки»); `Bybit:RestAddress` и `Bybit:SocketAddress` — адреса REST и потока Bybit, пустые — боевой Bybit; тесты ставят
  туда адрес, до которого не доходит ни один запрос, и подменяют порты своей подделкой;
- `Trading:Enabled` (`false`) — может ли Worker быть торговым; `Trading:Tick` (1 с), `Trading:PollInterval` (3 с),
  `Trading:ControlInterval` (1 мин), `Trading:StreamOpenWait` (5 с), `Trading:StreamIdle` (1 мин), `Trading:CloseWait`
  (30 с), `Trading:EntryDrift` (`0.005`, доля) — раздел «Сделки»;
- `Ideas:Burst:5m` (60), `Ideas:Burst:15m` (25), `Ideas:Burst:1h` (8), `Ideas:Burst:4h` (4), `Ideas:Burst:1d` (4) —
  пороги «⚡ всплеск»: сколько идей одной стороны одной стратегии на одной свече таймфрейма. API берёт пороги из той же
  секции, чтобы показать их в списке сигналов.

Их можно задать переменными окружения, например `ConnectionStrings__Bench`, `MarketData__GrpcUrl`, `Worker__Name`,
`Scanner__Enabled`, `Ideas__Burst__1h`, `MarketData__HistoryCache__Path`, `ExchangeAccounts__MasterKey`, `Trading__Enabled`.

Типы API для фронтенда генерируются из OpenAPI работающего API:

```bash
npm --prefix frontend run generate:api
```

## Production (firebat-01 и firebat-02)

Прод стенда — две машины, не связанные со стендом на Маке: своя база и свои Worker'ы. Проект `profit-fox` в
`~/profit-fox` на обеих, роль машины — в файле `~/profit-fox/role` (`main` или `workers`, без файла — `main`).

**firebat-01** (`192.168.8.163`, пользователь `firebat`, роль `main`) — `docker-compose.prod.yml`:

- `db` — Postgres 17 (том `profit-fox-db`, 1 ГБ). Порт `5432` открыт только на адресе `192.168.8.163`: к базе ходят
  Worker'ы firebat-02, с паролем из `.env.prod`;
- `api` — API со страницей, образ `ghcr.io/dmitryshelamov/profit-fox:<N>`, порт `5240`, 512 МБ. При старте
  мигрирует базу; новая база пуста. Держит кэш истории для предпросмотров (том `profit-fox-history-cache`);
- `worker-1`, `worker-2` — образ `ghcr.io/dmitryshelamov/profit-fox-bench-worker:<N>` (не `profit-fox-worker`: это имя с
  номерами 1–50 занято старым проектом), имена `firebat-01-1` и `firebat-01-2`, по 8 ГБ, `Worker__TakeRuns=false` —
  только сканер идей: прогон и сканер в один процесс не помещаются. Сканер держит минуты всех пар за сутки и графы всех
  включённых стратегий — около 4,5 ГБ на 14 стратегиях. Идёт в том Worker'е, что взял аренду; второй берёт её, если
  первый остановился. Они же — торговые Worker'ы (`Trading__Enabled=true`, раздел «Сделки») и поэтому получают мастер-ключ
  `ExchangeAccounts__MasterKey`: сделки ведёт тот, кто держит аренду `trader_lease`, второй подхватывает её.

**firebat-02** (`192.168.8.181`, пользователь `firebat`, роль `workers`) — `docker-compose.workers.yml`:

- `worker-1`, `worker-2` — тот же образ, имена `firebat-02-1` и `firebat-02-2`, по 5 ГБ, `Scanner__Enabled=false` и
  `Trading__Enabled=false` — только прогоны; мастер-ключа у них нет. База — на firebat-01 (`192.168.8.163:5432`), пароль тот же, что в `.env.prod` firebat-01.
- Том `profit-fox-history-cache` — кэш истории прогонов, один на оба Worker'а: месяц, сохранённый одним, читает второй.
  Предел — 40 ГБ. Том переживает деплой и откат.

Оба Worker'а обеих машин берут данные у сервиса данных на soyo-02 (`192.168.8.213`, порты `5237`, `5236`). Очистить кэш
(например, если сервис данных исправил уже покрытую историю) — на нужной машине убрать контейнеры, которые держат том,
удалить том и поднять те же службы снова; база не трогается. На firebat-02:

```bash
cd ~/profit-fox && N="$(cat current)" && PROFIT_FOX_VERSION="$N" docker compose --file "releases/$N/docker-compose.workers.yml" --env-file .env.prod rm --stop --force worker-1 worker-2
```

```bash
docker volume rm profit-fox-history-cache
```

```bash
cd ~/profit-fox && N="$(cat current)" && PROFIT_FOX_VERSION="$N" docker compose --file "releases/$N/docker-compose.workers.yml" --env-file .env.prod up --detach worker-1 worker-2
```

На firebat-01 — те же команды с `docker-compose.prod.yml` и службой `api`. Выключить кэш без отката — пустая
`MarketData__HistoryCache__Path`.

Страница — `http://192.168.8.163:5240/`. Без авторизации, как остальные службы в локальной сети.

### Как идёт деплой

1. Push в `main` запускает CI (`.github/workflows/ci.yml`: сборка и тесты бэкенда, проверки фронтенда, `shellcheck`
   и тест `deploy/deploy.sh`).
2. После зелёного CI `.github/workflows/deploy.yml` даёт коммиту следующий номер `N` (тег `vN`), собирает на GitHub оба образа
   и кладёт их в GHCR как `:N` с меткой коммита.
3. Задача `deploy` ждёт Approve владельца в окружении `production`, затем раннер на soyo-03 по SSH вызывает на
   firebat-01, затем на firebat-02 `deploy <N> 1`.
4. Ключ может запустить только `deploy.sh`. Тот берёт коммит тега `vN` на GitHub, принимает его лишь из `main`,
   проверяет метку коммита у обоих образов и поднимает: `db` (ждёт готовности), `api` (ждёт `/health` до 120 с), затем
   `worker-1` и `worker-2`. В конце пишет `~/profit-fox/current` и чистит старые образы. Том базы никогда не удаляется.

### Откат

## Аккаунты

Раздел «Аккаунты» (`/accounts`) хранит ключи Bybit, которыми стенд торгует от имени владельца; спецификация —
`openspec/specs/exchange-accounts`. Аккаунт добавляют по имени, ключу API и секрету; стенд спрашивает у Bybit права ключа
(`/v5/user/query-api`) и запоминает UID аккаунта: второй ключ того же UID не принимается. Сменить ключ — удалить аккаунт и
добавить заново. «Показать» в строке читает у Bybit свободные деньги единого аккаунта (`totalAvailableBalance`), баланс
нигде не хранится.

Подходит только ключ реального единого торгового аккаунта (UTA), без демо и testnet:

- не «только чтение»;
- права «Контракты» — «Заявки» и «Позиции» (`ContractTrade`: `Order`, `Position`); права спота не нужны и не мешают;
- без права вывода (`Wallet`: `Withdraw`) — ключ с ним стенд отклоняет.

Секрет ключа шифруется AES-256-GCM мастер-ключом сервера и лежит в базе только зашифрованным; API его не отдаёт никогда.
Мастер-ключ — настройка `ExchangeAccounts:MasterKey`, ровно 32 байта в base64. Без неё или с ключом другого вида API не
стартует, а сообщение называет настройку, но не значение. Из Worker'ов мастер-ключ нужен только торговому
(`Trading:Enabled=true`, раздел «Сделки»): без ключа такой Worker не стартует; остальные стартуют без него. Новый ключ:

```bash
openssl rand -base64 32
```

- В разработке ключ лежит в `backend/src/ProfitFox.Presentation/appsettings.Development.json`, как пароль dev-базы; в
  общем `appsettings.json` его нет. Тесты API берут свой ключ.
- В production — строка `PROFIT_FOX_MASTER_KEY=<ключ>` в `~/profit-fox/.env.prod` на firebat-01 (режим 600);
  `docker-compose.prod.yml` передаёт её API и обоим Worker'ам firebat-01 как `ExchangeAccounts__MasterKey`. Без неё `docker compose` останавливается
  до замены контейнеров, и работающая версия остаётся на месте.

Потерян или сменён мастер-ключ — секреты не читаются: баланс отвечает, что аккаунт надо добавить заново. Ключи Bybit
перевыпускаются за минуту; ротации мастер-ключа нет.

Сайт открыт в локальной сети без входа: любой в ней может добавить и удалить аккаунт. Вывести деньги ключами стенда
нельзя — ключ с правом вывода не принимается.

## Сделки

Раздел «Сделки» (`/trades`) — сделки по идеям реальными деньгами на Bybit, раздел «Риск» (`/risk`) — их пределы;
спецификации — `openspec/specs/idea-trades` и `openspec/specs/trade-risk`. Сделка открывается кнопкой «Войти» у открытой идеи:
рыночная заявка по бессрочному USDT-контракту пары идеи, стоп и цель идеи уходят вместе с ней как стоп и цель позиции и
срабатывают на бирже, работает стенд или нет. В срок идеи стенд закрывает сделку по рынку. Торговать можно только аккаунтом
в режиме изолированной маржи, только в одностороннем режиме позиции и одной сделкой на пару аккаунта. Ни одна стратегия
проверку после комиссий не прошла: раздел даёт инструмент и пределы потерь, а не прибыль.

**Риск.** Пока в «Риске» не сохранены плечо, предел суммы на сделку, предел числа открытых сделок, предел общей суммы, предел
потери на сделку и предел убытка за день, войти нельзя. Стоп сделки — стоп идеи, если он не дальше предела потери от цены
клика, иначе цена на пределе. Предел потери меньше половины пути до ликвидации: `X % < 100 / (2 × плечо)`. Три параметра
«Сроки и попытки» имеют умолчания: не входить, если до срока идеи меньше минуты; ждать приёма входа 30 секунд; три попытки
вернуть стоп. Ожидание и попытки, как и плечо, сделка берёт при клике и дальше не меняет.

**Торговый Worker.** Заявки на биржу отправляет и сделки ведёт только Worker с `Trading:Enabled=true` — один на стенд:
строка `trader_lease` берётся и продлевается, как аренда сканера, второй торговый Worker подхватывает её, когда первый
остановился. API перед входом только читает Bybit (цена, правила пары, права ключа, режим маржи, позиция, свободные USDT),
записывает сделку и заявку входа одной транзакцией и отвечает; пока ни один торговый Worker не держит аренду, войти нельзя.
Перед каждой отправкой входа Worker заново читает цену Bybit: вход отменяется, если цена прошла стоп или цель, если до
срока меньше запаса, если стоит запрет, если стоп не ближе половины пути до ликвидации от цены сейчас или если цена ушла от
цены клика в сторону сделки дальше `Trading:EntryDrift` (0.5 %) — стоп считается от цены клика, и потеря на стопе
не больше предела потери плюс этот сдвиг.
Заявка записана до отправки и несёт номер `t…-n`, поэтому повтор не создаёт второй заявки. Торговому Worker'у нужен мастер-ключ.

**Поток и опрос.** На каждый аккаунт со сделками торговый Worker держит поток Bybit (темы `order`, `execution`, `position`) и
один на весь Worker поток цен маркировки (`tickers.{пара}`). Поток открывается с первой сделкой аккаунта и закрывается через
`Trading:StreamIdle` после последней; без сделок нет ни соединений, ни запросов. Сразу после подписки, после каждого разрыва и
раз в `Trading:ControlInterval` Worker дочитывает по REST исполнения с курсора, позиции и незавершённые заявки. Поток не открылся
за `Trading:StreamOpenWait` или оборвался — аккаунт сразу ведётся опросом раз в `Trading:PollInterval`, а «Сделки» пишут, какой
аккаунт на опросе и с какого момента; поток вернулся — одна сверка REST, и аккаунт снова на потоке. Пустая позиция без
закрывающих исполнений дольше `Trading:CloseWait` закрывает сделку по результату `closed-pnl` Bybit с причиной «на бирже».
Каждые `Trading:Tick` Worker читает базу: заявки к отправке, сделки с вышедшим сроком, аккаунты, которым пора открыть или
закрыть поток.

**Стоп-кран.** Убыток за день — итоги сделок, закрытых в текущие сутки UTC (после снятия запрета — с момента снятия), плюс
результат открытых сделок по цене маркировки. Когда он достигает предела, Worker одной транзакцией записывает запрет, ставит
всем открытым сделкам заявки закрытия по рынку и отменяет ещё не отправленные входы. Сделку в «Ошибке» стоп-кран не
закрывает. Запрет держится и через сутки, снимает его только владелец кнопкой «Снять запрет» в «Риске», когда ни одна
сделка не закрывается. Стоп-кран работает, только пока работает торговый Worker: без него сделки защищены только своими
стопами на бирже, а после запуска стоп-кран срабатывает при первой проверке.

**Состояния.** «Ждёт входа» — заявка входа записана и не исполнена; «Открыта» — позиция на бирже есть; «Закрывается» —
записана заявка закрытия; «Закрыта» — позиции нет, записаны причина и итог; «Отменена» — вход не состоялся (отказ Bybit,
«вход не ушёл вовремя», стоп-кран); «Ошибка» — позиция на бирже больше сделки или другой стороны. Сделку в «Ошибке» стенд не
ведёт: не закрывает по сроку и стоп-краном и не трогает её стоп; владелец закрывает позицию на Bybit и нажимает «Разобрана».

**Причины закрытия.** «по цели» и «по стопу» — сработали цель или стоп позиции на бирже; «по сроку» — срок идеи; «вручную» —
кнопка «Закрыть по рынку»; «стоп-кран»; «без стопа» — стоп не удалось вернуть на биржу за все попытки сделки;
«ликвидирована» и «закрыта биржей (ADL)» — ликвидация и автоделевередж Bybit; «на бирже» — позицию закрыли на Bybit мимо стенда.
Итог — по ценам исполнений с комиссиями биржи и фандингом; рядом показан итог идеи из журнала.

Сайт открыт в локальной сети без входа: любой в ней может войти в сделку и сменить пределы. Потери ограничены пределами
«Риска» и стопами на бирже; вывести деньги ключами стенда нельзя.

## Конструктор сигналов

Раздел «Сигналы» собирает граф сигнала на холсте и показывает, где он срабатывает на паре в разведке (до начала текущих
суток UTC): график свечей с метками событий и их список.

- `/signals` — сохранённые сигналы;
- `/signals/<имя>` — редактор сигнала с панелью предпросмотра внизу;
- `/signals/new/<id>` — новый сигнал, черновик до первого сохранения;
- `/runs`, `/runs/<id>`, `/runs/<id>/sets/<n>` — прогоны, прогон и набор прогона.

Сигнал хранится в базе стенда: граф в формате `strategy-graph`, расположение узлов и номер версии. Правка графа даёт новую
версию, перемещение узлов — нет. Несохранённые правки живут черновиком в браузере.

Первый предпросмотр пары идёт несколько секунд: столько сервис данных отдаёт свечи и фандинг с начала данных. API держит в
памяти историю последних 5 пар с таймфреймом, поэтому повторный предпросмотр той же пары, в том числе с другим графом,
идёт доли секунды. С папкой кэша истории закрытые месяцы берутся с диска и после перезапуска API: у сервиса данных
читается только то, что сохранить нельзя, прежде всего текущий месяц.

## Конструктор стратегий

Стратегия — граф, который открывает и закрывает позицию: узел «Вход» (`enter`) с шортом или лонгом на событии, узел
«Закрыть через» (`close-after`) со сроком и, по желанию, «Стоп» и «Цель». Раздел «Стратегии» собирает такой граф на том же
холсте, что у сигналов, хранит его в базе с версиями (как сигнал) и проверяет без истории.

- `/strategies` — сохранённые стратегии;
- `/strategies/<имя>` — редактор стратегии;
- `/strategies/new/<id>` — новая стратегия, черновик до первого сохранения;
- `/strategies/<имя>/run` — форма запуска прогона.

У стратегии есть вид, его выбирают при создании, и он не меняется: «для бота» — любой граф стратегии, «категория идей» —
вход узлами «Вход» по событию, срок «Закрыть через», стоп и цель по желанию, без заявок по условию и без чтения состояния
позиции.

Сохранённый сигнал входит в стратегию узлом сигнала: он ссылается на сигнал и номер его версии, его входы — параметры этой
версии, выход — событие `event`. Вход без провода и без значения берёт значение параметра из сигнала — оно видно на входе
серым. Перед расчётом узел сигнала заменяется узлами графа своей версии, так что считается стратегия так же, как граф,
собранный вручную.

Версия сигнала в стратегии закреплена: правка сигнала даёт ему новую версию, а стратегия по-прежнему ссылается на старую и
считает по ней. Узел показывает, что есть версия новее, и кнопка «Обновить до версии N» в его карточке переводит ссылку —
это правка графа, после сохранения у стратегии новая версия. Переименовать сигнал можно: стратегия ссылается на него по
идентификатору и показывает новое имя. Удалить сигнал, на который ссылается хоть одна версия стратегии, нельзя — отказ
называет стратегии; удаление стратегии снимает запрет.

Стратегия H0001 — шорт на первом за день пересечении фандингом порога, выход через четыре часа:

1. В разделе «Сигналы» нажать «Новый сигнал», вставить в карточке «JSON» граф сигнала H0001 (он записан в
   `backend/tests/ProfitFox.Tests.Unit/Domain/Services/Graph/Graphs.cs`, константа `H0001`) и сохранить под именем
   `funding-high`.
2. В строке `funding-high` или в его редакторе нажать «Создать стратегию»: откроется новая стратегия с узлом сигнала
   `funding-high`, проводом от его `event` ко входу `when` узла «Вход» и узлом «Закрыть через».
3. У узла «Вход» выбрать `side` = `short`, у узла «Закрыть через» вписать срок `4h`. Счётчик «Ошибки» станет 0.
4. Нажать «Сохранить» и дать имя `funding-short`: стратегия появится в разделе «Стратегии» с версией 1.

Новую стратегию можно собрать и с нуля: «Новая стратегия» спрашивает вид; «категория идей» начинается с узлов «Вход» и
«Закрыть через», «для бота» — с узла «Позиция», а сохранённые сигналы лежат в палитре (кнопка «+») в группе «Сигналы».

## Сетапы

Сетапы v2 перенесены как 12 стратегий вида «категория идей» и одна метка (изменение `add-setup-strategies`, спецификация
`setup-strategies`). В базу они не засеваются: их создают руками на стенде, который назовёт владелец. Тела запросов
лежат эталоном тестов в `backend/tests/ProfitFox.Tests.Integration/Fixtures/Setups`:

- `<имя>.signal.json` — 19 сигналов-состояний: тело `POST /api/signals` (`name`, `description`, `graph`, `layout`);
- `<имя>.strategy.json` — 12 стратегий: тело `POST /api/strategies` с `"kind": "idea"`. Узел сигнала стратегии ссылается
  на сигнал местозаполнителем `{{signal_<имя сигнала через _>}}`, например `{{signal_breakout_up}}`: перед отправкой
  его заменяют на `id` созданного сигнала, версия — `1`;
- `H0001/` — сигнал `funding-high` и стратегия `funding-short` в том же виде, для проверки помощника тестов.

Пороги сетапа и плана — параметры графа со значениями v2: у стратегии они же подаются на входы её сигналов, поэтому
прогон может перебирать, например, `move` стратегии `impulse`. План у всех общий: вход по рынку на событии сетапа, стоп —
от `close` до экстремума окна сетапа против входа плюс `stopBuffer` = 1.5 ATR 14 прошлой свечи, долей `close`; цель —
`targetR` = 2 стопа; срок — `lifeCandles` = 24 свечи таймфрейма (узел «Срок в свечах»); размер — `size` = 100 USDT.

Условие с зоной (`breakout-up`, `breakout-down`, `false-breakout-long`, `false-breakout-short`) ложно, а не неизвестно,
когда зоны с нужной стороны нет: сравнения с краем зоны идут через логический узел `is-true` «Истинно» (ложь при ложном
и при отсутствующем входе). Поэтому событие пробоя приходит и сразу после свечи без зоны, а у двусторонних стратегий
`breakout` и `false-breakout` сторону стопа выбирает состояние лонговой стороны. Пока окно зон в 200 свечей не набрано
или нет ATR, от которого считается край, условие с зоной тоже ложно; часть условия про объём остаётся трёхзначной.

| --- | --- |

| `breakout` | `breakout-up`, `breakout-down` |
| `drop` | `drop` |
| `early-drop` | `early-drop` |
| `early-impulse` | `early-impulse` |
| `exhaustion` | `exhaustion-bottom`, `exhaustion-top` |
| `false-breakout` | `false-breakout-long`, `false-breakout-short` |

Сигнал `high-volatility` — не стратегия, а метка «↑ волат.»: его включают меткой на одном таймфрейме (в эталоне `1h`),
и она ставится идеям любого таймфрейма. Метке и сетапам нужен прогрев сканера в 500 свечей (`Scanner:WarmupCandles`, так
и стоит по умолчанию).

Создать всё на стенде — запросы раздела «setups» в `backend/src/ProfitFox.Presentation/ProfitFox.Presentation.http`
(HTTP-клиент JetBrains: сигнал запоминает свой `id` в переменной `signal_<имя>`, стратегия берёт тело через `<@` с
подстановкой переменных; сначала все сигналы, потом стратегии). То же из терминала, с `curl` и `jq`, из корня репозитория:

```bash
bench=http://localhost:5240; ids=(); cd backend/tests/ProfitFox.Tests.Integration/Fixtures/Setups && for file in *.signal.json; do name=${file%.signal.json}; id=$(curl -sSf -H 'Content-Type: application/json' --data-binary @"$file" "$bench/api/signals" | jq -r .id) || break; ids+=(-e "s/{{signal_${name//-/_}}}/$id/g"); done; for file in *.strategy.json; do sed "${ids[@]}" "$file" | curl -sSf -H 'Content-Type: application/json' --data-binary @- "$bench/api/strategies" | jq -r '.name + " v" + (.version | tostring)'; done; cd -
```

Проверка на стенде: в разделе «Стратегии» открыть `impulse` и в панели предпросмотра выбрать `BTCUSDT` и `1h` —
предпросмотр отвечает без ошибок (заявок может не быть). Перед включением идей каждую стратегию прогоняют с перебором
порогов. Таймфреймы включения и таймфрейм метки выбирает владелец.

## Слои

Стенд и бот — одно приложение с одним набором слоёв в `backend/src`; отдельных зон `bench`, `engine` и `bot` больше нет.
Раскладка та же, что в `profit-fox-market-data` (его `docs/conventions.md`): внутри слоя папка называет сначала вид типа,
потом тему (`Backtests`, `Runs`, `Signals`, `Graph`, ...), а пространство имён совпадает с папкой. Ссылки идут только
внутрь:

- `ProfitFox.Domain` — расчёт и правила без ввода-вывода. `Entities/<тема>` — сущности: прогон стратегии `Backtest`,
  сохранённые сигнал `SignalDocument` и стратегия `StrategyDocument`, их общая база `Entities/Base/AggregateRoot` и
  `Events/IDomainEvent`, как в образце; перечисления сущности — в `Entities/<тема>/Enums`. `ValueObjects/<тема>` — значения
  (настройки и наборы прогона, числа набора, проверенный граф, сигнал, стратегия, минутный путь), перечисления — в
  `ValueObjects/<тема>/Enums`. `Repositories` — порты хранения `ISignalRepository`, `IStrategyRepository`,
  `IBacktestRepository`. `Services/<тема>` — то, что считает: чтение и проверка графа, узлы, исполнение сигнала и
  стратегии, позиция пары, сделка, случайные входы, наборы и расчёт прогона на паре; `Exceptions`. Ни на что не
  ссылается. Взять прогон, продлить аренду и отменить — по одному оператору `IBacktestRepository` со временем базы, а не
  «прочитал сущность, изменил, сохранил»: очередь обслуживают несколько Worker'ов.
- `ProfitFox.Application` — команды и запросы MediatR с обработчиками. Команда лежит в `Commands/<тема>/<Имя>/` рядом с
  обработчиком и результатом (`Backtests/EnqueueBacktest/EnqueueBacktestCommand`, `EnqueueBacktestCommandHandler`); общий код обработчиков одной
  темы — в `Commands/<тема>/Base`. Запрос и его обработчик — рядом в `Queries/<тема>` (`Backtests/GetBacktestQuery`,
  `GetBacktestQueryHandler`). Обработчики `internal sealed`, их видит `ProfitFox.Tests.Unit`. `Contracts/<тема>` — то, что
  отдают запросы и команды и показывает API, с именами `<Имя>Internal` (`BacktestInternal`, `SignalInternal`) и конвертерами из
  домена в `Contracts/<тема>/Converters`. `Ports/MarketData` — порты сервиса данных `IHistorySource` и `IInstrumentCatalog`,
  `Exceptions`.
- `ProfitFox.Infrastructure` — адаптеры портов и регистрация: `InfrastructureRegistrar.AddInfrastructure` собирает
  `Mediatr/MediatrRegistrar`, `Clients/MarketData` (gRPC и REST сервиса данных, его `Protos`, `MarketDataRegistrar`) и
  `Persistence/Postgres` (`PostgresRegistrar`; репозитории `<Имя>Repository` в `Dapper/Repositories/<тема>` со строками
  `Contracts/<Имя>Db`, SQL в `Queries/<Имя>RepositoryQueries`, переводом строки в домен в `Converters/<Имя>DbConverter`;
  миграции в `FluentMigrator/Migrations`, их запуск — `FluentMigrator/BenchMigrations`). Репозитории `internal sealed`,
  их видит `ProfitFox.Tests.Integration`.
- `ProfitFox.Presentation` (API: `Controllers`, `Contracts/<тема>` с запросами и ответами) и `ProfitFox.Worker`
  (`BackgroundServices`) — точки входа. Обе зовут `AddInfrastructure`, контроллеры и служба Worker'а зовут Application
  только через `ISender`; служба шлёт `RunNextCommand` в своей области на каждый шаг. `NodesController` и проверка графа
  в `SignalsController` зовут чистые функции домена напрямую.
- `ProfitFox.Cli` (`bench`) — клиент REST, на остальные проекты не ссылается.

Из образца не взято: папка транзакций и соединение на область (каждый вызов репозитория и так целый в своей транзакции),
обработчики запросов с SQL в Infrastructure (на все запросы отвечают репозитории), общий обработчик исключений Presentation
(тела ошибок разные по маршрутам и записаны в OpenAPI), проверка базы в Infrastructure (`DatabaseHealthCheck` остаётся в
Presentation), NSubstitute (подделки `MemorySignalRepository` и `FakeHistorySource` держат состояние), имена портов
`I<Биржа><Что>Client`, перечисления вместо строк статусов, периода и вида прогона, `Guid` как идентификатор,
`scripts/verify-format.sh` и хук `pre-commit` (design `match-market-data-structure`, решение 8).

Тесты лежат так же, как код, который они проверяют: `ProfitFox.Tests.Unit/Domain/...` и `ProfitFox.Tests.Unit/Application/...`
(тесты обработчиков — `Commands/<тема>/<Обработчик>Tests`, `Queries/<тема>/<Обработчик>Tests`; `Tests.Unit` ссылается только
на Domain, Application и `Tests.Shared`), `ProfitFox.Tests.Integration/Infrastructure/...`,
`ProfitFox.Tests.Integration/Presentation/...`. Интеграционные тесты шлют команды через поставщик служб `AddInfrastructure`
с поддельным сервисом данных (`BenchServices`). Генераторы сущностей — в
`ProfitFox.Tests.Shared/Generators/Domain/Entities/<тема>` (`BacktestGenerator`, `SignalDocumentGenerator`). Эталоны — в папках
`Fixtures` рядом со своими тестами.

Общие свойства сборки и версии пакетов — в `backend/Directory.Build.props` и `backend/Directory.Packages.props`; `.csproj`
перечисляют только свои пакеты и ссылки. `backend/Directory.Build.targets` держит правило ссылок слоёв: проект может
ссылаться только на перечисленные там проекты, иначе сборка падает. Стиль кода — `.editorconfig` в корне и
`backend/.globalconfig`; нарушение правила с уровнем `error` роняет обычную сборку.

Внутренности расчёта (`internal`: `CompiledGraph`, `CompiledNode`, `InputSource`, `NodeContext`, `Node` и узлы
`Services/Nodes`, `GraphJson`, `GraphValidator`, `StrategyRun`) закрыты от остальных слоёв компилятором. Остальной код Domain
пользуется теми же открытыми входами, что и другие слои: `StrategyGraph`, `SignalExecutor`, `StrategyExecutor`,
`CycleRun`, `PairPosition`, `Cycle`, `EntryPlan`.

«Версия движка» — номер версии расчёта, а не проекта: `EngineVersion.Number`. Его поднимают вместе с любым изменением
сделок, случайных входов или чисел результата. Эталонный тест `EngineVersionTests` считает прогоны двух стратегий, H0001
и H0002 с наложением заявок, и падает, если результат любой из них изменился, а номер нет. Интеграционным тестам нужен Docker.
